핵심 변경 — 주최자가 명단을 관리하지 않는다

v3는 H1에서 참여자 이름을 5개 입력하게 했다. 그런데 주최자가 이름을 적으려면 누가 있었는지 기억하거나 메모장을 켜야 한다. 이 앱이 없애려던 부담이 바로 그것이다.
항목v3v4
참여자 명단H1에서 이름 전부 입력 입력하지 않음. 링크로 각자 들어와 로그인
동명이인이름만으론 구분 불가로그인 계정이 곧 신원
반올림 단위10원 / 100원 선택 화면에서 제거. DB 컬럼과 계산 엔진은 그대로 (10원 고정)
결제자차수마다 선택 "전부 내가"가 기본. 다른 사람이 낸 차수만 예외 지정
빠진 사람(방지 수단 없음) 확정 직전에 인원 수 비교로 경고
W0 참여하기없음 (W1에서 이름 선택) 신규. 로그인 → 참여 버튼 → Participant 생성

왜 "명단 관리"가 아니라 "확정 시 경고"인가

빠진 사람을 막는 방법은 두 가지였다.
방식주최자가 하는 일판정
명단을 상시 관리 누가 들어왔는지 계속 확인하고, 안 들어온 사람을 그때그때 추가 기각
확정 시 숫자 비교 아무것도 안 함. 확정 버튼 누를 때 경고가 뜨면 그때 판단 채택
"누가 안 들어왔지?"를 사람이 기억하는 대신 숫자 비교로 대체했다. 안 들어오는 원인은 먹튀가 아니라 단톡방 스크롤하다 링크를 놓치는 것이라, 확정 직전 경고 한 번이면 "지원아 링크 눌러"로 해결된다.
초과도 같은 비교 한 줄로 잡힌다. 5명이라 했는데 6명이 들어왔다면 모르는 사람이 참석자 실명과 금액을 다 보고 있다는 뜻이다. 부족한 경우는 돈 문제로 끝나지만 초과는 정보 유출이라 이쪽이 더 위험하다. SPEC §2-b의 "주최자는 참여자를 제거할 수 있어야 한다"가 이 경고에서 트리거된다.

이름으로 추가한 사람은 어떻게 처리되나

항목동작
차수 체크 전체 참석·음주가 기본값 (SPEC §5). 대부분 이름 세 글자 입력이 전부다. 다르면 주최자가 H5에서 수정
계산 일반 참여자와 완전히 동일하다. 계산 엔진은 로그인 여부를 모른다
입금 표시 본인이 [보냈어요]를 누를 수 없다. 주최자가 [받았어요]만 누른다. §5-b 양방향 체크가 이 사람에게만 반쪽이 된다
나중에 로그인하면 W0에서 본인 이름을 고르면 연결된다. 그때부터 양방향 체크가 살아난다
연결 단계가 필요한 이유 — 없으면 지원이가 나중에 링크를 눌렀을 때 6번째 참여자가 새로 생겨 분모가 바뀌고 전원 금액이 틀어진다. 미리 등록된 이름이 하나도 없으면 이 단계는 아예 나타나지 않으므로, 대부분의 참여자는 버튼 한 번이면 끝난다.

스키마에 미치는 영향

항목변화
gathering.expected_count 추가. SMALLINT NULL — 경고용이며 계산에는 쓰지 않는다
gathering.rounding_unit 유지. NOT NULL DEFAULT 10. 화면에서만 안 보인다
