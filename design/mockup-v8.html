시나리오 — 참여자가 하는 일은 "로그인 → 이름 확인 → 체크"

  1. 동규가 모임을 만들고 내 이름과 참여자 수 5명(본인 포함)을 적는다
  2. 차수·금액과 기타 항목 금액을 넣는다. 사람 지정은 아직 안 한다
  3. 카카오톡으로 링크를 뿌린다 → 로그인하고 이름을 확인한 뒤 각자 체크. 4명이 들어왔고 지원이는 링크를 놓쳤다
  4. 사람이 모였으니 H3에서 결제자·기타 항목 부담자를 지정한다
  5. 확정하려니 "5명이라 하셨는데 4명입니다" 경고 → [링크 다시 공유] → 지원이 들어와 체크
  6. 5명으로 확정. 합계 220,000원. 이후 앱을 열면 H0 목록에 "확정됨 · 입금 2/4" 로 보인다
이름은 표시용이고 신원은 계정이 맡는다. 두 사람이 같은 이름을 적어도 계정이 다르므로 서로 다른 참여자이며, 프로필 사진으로 구분된다 (SPEC §2).

⑮ 확정 후 참여 요청 — FCM이 처음으로 제 역할을 한다

ADR-003에서 FCM은 주최자 전용으로 정했다. 참여자는 웹이라 디바이스 토큰이 없기 때문이다. 그런데 주최자에게 보낼 알림이 뭐가 있나가 애매했다. 이 케이스가 답이다.
흐름 — 확정 후 들어온 사람이 [주최자에게 알리기] → 서버가 참여 요청을 기록하고 FCM 발송 → 주최자가 H4에서 [되돌리고 추가] → CONFIRMED → COLLECTING 전이와 참여자 생성이 한 번에 일어난다.
요청을 기록하는 것이 핵심이다. 알림만 보내면 주최자가 되돌린 뒤 그 사람에게 "다시 눌러봐" 라고 해야 하고, 그 사람은 주최자가 되돌렸는지 알 방법이 없다 (참여자는 FCM을 못 받는다). 기록해두면 되돌리는 순간 자동으로 참여 처리된다.
주최자가 받는 FCM시점
전원이 응답했어요마지막 참여자가 체크를 제출
○○님이 입금을 보냈다고 표시했어요NONE → SENT
○○님이 뒤늦게 참여를 요청했어요확정 후 진입 (신규)
이 세 가지가 전부 "주최자가 앱을 안 열어도 되게" 만드는 알림이라 §5의 부담 경감과 결이 맞는다.

⑬ 참여자가 이름을 직접 적는다

v6은 계정 닉네임을 그대로 이름으로 썼다. 그런데 카카오 닉네임은 실명이 아니다. 🌸봄이🌸, ㅋㅋㅋ, Kim 으로 들어오면 총무가 누가 누군지 모른다.
로그인은 두 가지를 주는데, 하나만 준다.
로그인이 주는 것이 서비스에 필요한가
신원 (providerId) 준다. 동명이인이 있어도 계정이 다르면 다른 사람이다
알아볼 수 있음 (닉네임) 못 준다. 닉네임은 총무가 알아보라고 지은 이름이 아니다
해결 — 로그인 직후 W0-2 이름 확인 화면에서 이름을 적는다. 기본값은 닉네임이라 대부분 그냥 넘기고, 알아보기 어려운 사람만 고친다. W1에서 나중에 수정할 수도 있다.
동명이인은 여전히 문제없다. 이름은 표시용이고 신원은 계정이 맡는다. 두 사람이 "재훈"을 적어도 서로 다른 Participant이고, 화면에서는 프로필 사진으로 구분된다 — SPEC §2가 이미 "동명이인 구분(프로필 사진·닉네임)" 이라고 적어둔 그대로다.

⑫ 주최자가 이름을 미리 등록하는 기능을 없앴다

이 기능은 원래 명세에 없었다. "빠진 사람이 정산에서 제외되면 공짜로 먹는다"는 우려 때문에 v4에서 넣었던 것인데, 흐름에 맞지 않았다.
정산은 다 먹은 다음날 이뤄지고 단톡방이 살아 있다. 링크를 놓친 사람은 악의가 아니라 스크롤하다 못 본 것이라, 확정 직전 경고에서 [링크 다시 공유] 한 번이면 들어온다.
그리고 이름 등록 없이도 극단 케이스가 해결된다. 확정 후에 나타난 사람은 주최자가 되돌리기(reopen)를 누르면 참여할 수 있고, §5-c의 추가금·환불 차액 처리가 그대로 작동한다. 이미 있는 기능이다.

⑪ §6 고정 문구가 계산 규칙과 어긋난다

SPEC §6 — "모든 금액은 올림 처리되며, 주최자의 부담을 조금이나마 덜기 위함입니다."
SPEC §7.4 — "원칙: 결제하느라 고생한 사람이 덜 낸다."
올림 이득을 가져가는 사람은 대표결제자 = 결제 총액이 가장 큰 사람이지 주최자가 아니다. 대부분 같은 사람이지만, 2차를 민지가 크게 결제하면 민지가 대표결제자가 된다. 그때 화면은 "주최자의 부담을 덜기 위함"이라고 말하는데 정작 주최자는 이득을 못 본다.
수정안 — "10원 단위로 올림 처리되며, 가장 많이 결제한 분의 부담을 조금이나마 덜기 위함입니다."
§7.4의 원칙과 정확히 일치하고, 대표결제자가 누구든 참이 된다.
SPEC §6은 "고정 문구"라고 못 박은 항목이므로 명세 수정이 필요하다. 이 문구는 신뢰를 만들려고 넣은 것인데, 틀린 설명이면 반대로 작동한다.

확인된 것 — 주최자도 분모에 포함된다

계산 엔진은 이미 그렇게 동작한다. 주최자도 Participant이고 참석했으면 분모에 들어간다. 목업의 안주 89,000 ÷ 5명이 동규를 포함한 5명이다. 엔진도 테스트도 바꿀 것이 없다 — T1의 A, T5의 A가 전부 결제자이면서 참석자다. 화면에는 H1 라벨로만 명시했다.
