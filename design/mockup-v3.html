F5 해결 — 근거 화면의 세로합이 맞아떨어지게 하는 규칙

코드 리뷰에서 "차수별 금액을 더하면 최종 금액과 다르다"는 문제가 나왔다. 차수별 금액은 반올림 전 원부담이라 소수가 나오기 때문이다. 이 서비스는 근거를 파는데, 근거 화면의 숫자가 안 맞아 보이면 존재 이유가 훼손된다.
결정 — 차수·기타 항목 금액은 원 단위로 반올림해 표시하고, 올림 조정 = 최종 금액 − 표시된 항목들의 합 을 한 행으로 드러낸다. 조정이 0원이면 그 행을 숨긴다.
참여자화면 표시세로합
재훈 1차 29,800 + 2차 20,667 + 올림 조정 +350,470 ✓
동규 (대표결제자) 1차 29,800 + 2차 20,667 + 올림 조정 −750,460 ✓
지원 1차 17,800 + 택시비 10,500 (조정 행 없음)28,300 ✓
숨기지 않고 드러내는 쪽을 고른 이유 — §6 고정 안내 문구가 이미 "모든 금액은 올림 처리되며"라고 말하고 있다. 말해놓고 화면에서 감추면 그 문구가 거짓말이 된다. 그리고 대표결제자의 조정이 음수(−7원)로 보이는 것이 곧 "결제한 사람이 덜 낸다"는 규칙의 증거가 된다.

F4 해결 — 반올림 단위가 강등됐을 때

1인당 금액이 작으면 100원 단위로는 대표결제자가 음수가 되어 엔진이 10원 단위로 강등해 재계산한다. 주최자는 100원을 골랐는데 결과가 10원 단위로 나오므로, 말해주지 않으면 "설정한 대로 안 되네"가 된다.
결정 — H3-b 확정 미리보기에 안내 한 줄을 넣는다.
"1인당 금액이 작아 100원 단위로는 계산할 수 없어 10원 단위로 정산했습니다."
W2·W3에는 넣지 않는다. 단위를 고른 사람은 주최자이고, 참여자에게는 소음이다.

다음 — 이 화면들이 요구하는 API

화면이 정해지면 어떤 엔드포인트가 필요한지가 기계적으로 따라 나온다. 이것이 SPEC §11-6 API 명세의 입력이다.
화면필요한 호출
H1 → H2POST /gatherings · POST /gatherings/{id}/rounds · POST /gatherings/{id}/extras — 저장 시점 검증만 적용
H2 하단POST /gatherings/{id}/share-token
H3GET /gatherings/{id}/responses — 응답 3/5
H3-bGET /gatherings/{id}/settlement/preview → inputHash
POST /gatherings/{id}/confirm { inputHash } — 확정 시점 검증
H4GET /gatherings/{id}/settlement · PUT /participants/{id}/payment { status: RECEIVED }
H5DELETE /participants/{id} · PATCH /participants/{id} { exempt } · POST /gatherings/{id}/share-token (재발급)
W1GET /g/{token} · PUT /g/{token}/me/attendance
W2GET /g/{token}/me — breakdown 포함 · PUT /g/{token}/me/payment { status: SENT }
W3GET /g/{token}/all
주목할 점 — GET 계열이 전부 계산 엔진을 호출한다. 계산 결과를 저장하지 않기 때문이다(ADR-005). 그래서 "한 모임 전체를 5~6 쿼리로 로드하는 조립 함수" 하나가 이 API 전부의 공통 기반이 된다.
