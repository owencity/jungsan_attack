> 구현 에이전트가 읽는 문서다. 결정 사항만 적는다. 여기 없는 것은 **만들지 않는다.**

> MSA(k3s)로 전환했다. `Gathering`(1회성 정산)의 기존 동작은 전부 그대로다 —
> `Group`은 그 위에 얹는 컨테이너다. 새 내용은 `§4-b`·`§4-c`, `§9` 추가 항목,
> `§10` 전체에 있다. **기존 번호는 유지한다** — 교차 참조(`§5-b`, `§7.4` 등)가
> 문서 곳곳에 있어 통째로 재번호하면 그 참조가 다 깨진다.
>
> ⚠️ **이 문서에는 별개로 누적된 미반영 변경 목록이 있다** (계좌→`participant`
> 이동, `expectedCount` 필수, `PENDING`/승인·거부, 모임 삭제 2트랙, `shareToken`
> 12자·62종, 본인 탈퇴 없음 등 — 대화 중 결정됐으나 이 파일엔 아직 반영 안 됨).
> **이번 v4 개정은 그 목록을 다루지 않는다.** Group/채팅/MSA 확장만 반영했다.

## 1. 무엇을 만드는가

**모임**에서 쓴 비용을 차수별 참석 여부와 음주 여부에 따라 나눠 정산하는 서비스.

기존 N빵 앱과의 차이는 두 가지다.

1. **입력을 총무 혼자 하지 않는다.** 총무는 차수와 금액만 넣고, 누가 몇 차에 있었고 술을 마셨는지는 각자가 링크에서 체크한다.
2. **결과에 근거를 함께 보여준다.** "너 12,340원"이 아니라 "1차 참석·음주 / 2차 불참 → 그래서 12,340원"을 보여준다. **이 서비스의 존재 이유가 여기 있다. 금액만 보여주면 만들 이유가 없다.**

용어는 **모임(Gathering)** 으로 통일한다. "정산"은 모임에 딸린 결과다.

**모임은 1회성으로 쓸 수도, 영구 모임(`Group`) 안에서 반복될 수도 있다.**
"신림팸"처럼 계속 만나는 사람들이 매번 새 모임을 만들되 같은 `Group`으로 묶는
것을 지원한다(`§4-b`). 실시간으로 채팅하며 지출을 기록하는 모임방도 지원한다
(`§4-c`). 둘 다 기존 1회성 정산 흐름 위에 얹는 것이지, 그 흐름을 바꾸지 않는다.

## 2. 로그인 정책

**주최자·참여자 모두 로그인한다.** 카카오 또는 구글.

로그인으로 얻는 것: 동명이인 구분(프로필 사진·닉네임), 입금 알림, 내 모임 이력, 그리고 "누가 체크했는지"의 신뢰.

### 가입과 앱 설치는 다른 문제다 — 반드시 구분할 것

| | 마찰 | 참여자에게 요구하는가 |
|---|---|---|
| 카카오/구글 로그인 | 3초, 탭 두 번 | **예** |
| 앱 설치 | 30초 + 저장공간 + 결심 | **아니오** |

**참여자는 웹에서 로그인하고 웹에서 체크한다.** 카카오·구글 로그인은 웹에서 그대로 동작하므로, 로그인을 받으면서 앱 설치는 요구하지 않을 수 있다. 앱 설치는 결과 화면에서 권유만 한다.

로그인을 전원에게 요구하는 것과 앱 설치를 전원에게 요구하는 것은 완전히 다른 요구다. 후자는 하지 않는다.

### 사용하지 않는 카카오 기능

**카카오 친구 목록 API와 친구에게 메시지 보내기는 쓰지 않는다.** 비즈앱 등록과 별도 검수가 필요하고, 상대방도 앱에 로그인해 친구목록·메시지 권한에 동의해야만 조회된다. 권한 취득 후에도 발신자–수신자 쌍당 20건 제한이 있다. **공유는 카카오톡 공유(링크 카드)로만 한다.**

## 2-b. 모임 생성 시점 — 강제하지 않는다

술자리는 계획될 수도 있고 즉흥일 수도 있다. **둘 다 지원한다.**

| 방식 | 흐름 |
|---|---|
| **사전 개설** | 주최자가 모임을 만들고 명단을 넣은 뒤 링크 공유 → 각자 체크 |
| **사후 개설** | 술 다 먹고 주최자가 모임을 만들어 링크만 뿌림 → 들어온 사람이 **스스로 이름 등록** 후 체크 |

`Gathering`은 두 경우 모두 동일한 구조다. 차이는 `Participant`가 언제 생기느냐뿐이다.

- 주최자가 미리 넣으면 `userId = null` 상태로 생성되고, 그 사람이 로그인해 자기 이름을 고르면 연결된다.
- 참여자가 스스로 들어오면 로그인 계정으로 `Participant`가 즉시 생성된다.

**가드 하나:** 링크만 알면 아무나 들어올 수 있으므로, **주최자는 명단에서 참여자를 제거할 수 있어야 한다.** (COLLECTING 상태에서만) 승인 절차는 만들지 않는다 — 마찰만 늘고 실제 오남용은 드물다.

## 3. 플랫폼

| 역할 | 플랫폼 |
|---|---|
| 주최자 | 앱 (Android 우선, iOS 후속) |
| 참여자 | **웹** — 설치 없이 링크로 진입. 서버 렌더링. 웹에서 로그인·체크·결과 조회 모두 가능 |

### 공유 링크는 반드시 웹 URL이어야 한다

카카오톡으로 보내는 링크를 앱 스킴(`jeongsan://...`)으로 만들면 **앱이 없는 사람에게는 아무 일도 일어나지 않는다.** 링크를 눌렀는데 아무 반응이 없는 것이 최악의 경험이다.

따라서 공유 링크는 항상 `https://jeongsan.app/g/{token}` 형태이고, **그 웹 페이지가 라우터 역할**을 한다.

```
링크 클릭
  └─ 웹 페이지 진입 (여기서 이미 모든 기능이 동작한다)
       ├─ 앱 설치됨  → "앱에서 열기" 버튼 노출 (선택)
       └─ 앱 없음    → 웹에서 그대로 진행. 하단에 설치 권유 배너
```

**Deferred Deep Link(설치 후 원래 목적지로 복귀)를 직접 만들지 말 것.** Firebase Dynamic Links는 종료됐고, 대체 서비스(Branch, AppsFlyer OneLink 등)는 MVP에 과하다. 웹이 완전히 동작하면 애초에 필요가 없다.

Android에서 카카오톡 인앱 브라우저는 커스텀 스킴을 차단하는 경우가 있으므로, 앱 열기는 `intent://` 스킴을 사용한다.

## 4. 도메인 모델

```
User
  id, provider(KAKAO|GOOGLE), providerId
  nickname, profileImageUrl
  tier: FREE | PRO               // 지금은 전원 FREE. 자리만 확보(§9)
  tierExpiresAt                  // null

Gathering (모임)
  id, name                       // "8월 팀 회식"
  groupId → Group.id | null      // 영구 모임 소속. 없어도 1회성으로 유효(§4-b)
  hostUserId → User.id
  hostParticipantId              // 주최자 본인도 Participant로 존재한다
  gatheringDate                  // 모임 날짜
  status: COLLECTING | CONFIRMED
  shareToken                     // 추측 불가한 랜덤 문자열. 재발급 가능(§8)
  roundingUnit                   // 10 | 100. 기본 10. 1000 불허(§7.4)
  payoutBankName, payoutAccountNo, payoutAccountHolder   // 주최자 입금 계좌
  revision                       // 확정할 때마다 +1. 재정산 감지용(§5-c)
  confirmedAt                    // 마지막 확정 시각

Participant
  id, gatheringId, name
  userId → User.id | null        // 로그인했으면 연결
  exempt: Boolean                // 면제자 (§7.3)
  responded: Boolean, respondedAt
  paymentStatus: NONE | SENT | RECEIVED        // §5-b
  paidAmount: Long | null        // SENT/RECEIVED로 표시된 시점의 부담액(§5-c)
  sentAt, receivedAt

Round (차수)
  id, gatheringId, seq, label
  totalAmount
  alcoholAmount                  // 직접 입력 또는 DrinkItem 합계로 산출
  payerId → Participant.id       // 수정 가능

DrinkItem (술병)                  // 선택. 있으면 alcoholAmount를 이걸로 계산
  id, roundId, name              // "소주"
  bottleCount, unitPrice         // 5, 5000

ExtraItem (기타 항목)
  id, gatheringId, label         // "택시비"
  amount
  payerId → Participant.id
  bearerIds: [Participant.id]    // 이 항목을 부담할 사람들

Attendance
  participantId, roundId
  attended, drank                // attended=false면 drank는 반드시 false
```

### 설계 제약

- **계산 결과를 저장하지 않는다.** `Attendance`로부터 매번 계산한다. 근거 화면과 재계산이 여기에 의존한다.
- `alcoholAmount`는 차수 단위 금액 하나다. 메뉴별 분할은 범위 밖이다.
- `DrinkItem`이 하나라도 있으면 `alcoholAmount = Σ(bottleCount × unitPrice)`로 덮어쓴다.

## 4-b. Group — 영구 모임 (`ADR-009`)

같은 사람들이 반복해서 만나는 모임을 지원한다. 예: "신림팸", "대학 동기",
"회사 개발팀". `Group` 안에 여러 `Gathering`(각 회차)이 생긴다.

```
Group
  id, name                       // "신림팸"
  createdByUserId → User.id
  createdAt

GroupMember
  groupId, userId
  role: OWNER | MEMBER
  joinedAt
```

**`Group`은 참여를 자동화하지 않는다.** 소속돼 있어도 다음 `Gathering`에
자동으로 `Participant`로 등록되지 않는다 — `§2-b`(모임 생성을 강제하지 않는다)와
`§5`(자기신고 신뢰)의 원칙을 그대로 지킨다. `Group`이 하는 일은 둘뿐이다.

- `Gathering` 생성 시 `Group`을 지정하면 이전 회차 참여자 이름을 자동완성 후보로 보여준다
- H0(내 모임) 화면에서 `Group`별로 묶어 볼 수 있다

`Group` 목록·통계·활동 타임라인은 이 버전의 범위 밖이다(`§9`).

## 4-c. 실시간 채팅 (`ADR-010`)

`Gathering` 진행 중 실시간 모임방을 제공한다. 채팅, 입장/퇴장, 현재 접속자
표시, 지출 등록 이벤트("민수님이 84,000원의 지출을 등록했습니다")가 채팅에
함께 뜬다.

```
ChatMessage (MongoDB — 관계형 스키마 밖. groupId/meetingId 는 각각
             Group.id / Gathering.id 를 가리킨다)
  groupId, meetingId, memberId
  type: TEXT | IMAGE | EXPENSE | SETTLEMENT | JOIN | LEAVE | NOTICE
  message
  createdAt
```

**REST API 서버와 별도 프로세스(Netty + WebSocket)로 둔다.** 메시지 저장은
MongoDB(관리형 오프로드, `ADR-012`), 접속 상태·마지막 읽음 위치는 Redis에
둔다. 인증은 WebSocket 핸드셰이크에서 JWT를 서브프로토콜로 검증한다(쿼리
파라미터 금지 — 로그에 토큰이 남는다). 자세한 아키텍처는 `ADR-010` 참조.

## 5. 상태 전이

```
COLLECTING ──(주최자 확정)──> CONFIRMED
     ^                             │
     └──────(주최자 수정하기)───────┘
```

| 상태 | 참여자 | 주최자 |
|---|---|---|
| COLLECTING | 자기 체크 입력·수정 | 차수/금액/결제자 수정, 미응답자 대신 체크, 확정 |
| CONFIRMED | 결과 조회, 입금 | 결과 공유, 입금 확인 체크, 되돌리기 |

### 확정은 두 단계다 — 미리보기 후 수락

확정 버튼을 누르면 바로 전이되지 않는다. **주최자가 계산된 금액을 먼저 확인하고 수락해야 한다.**

```
[확정하기] → 미리보기(계산 결과 + §6 안내 문구) → [수락] → CONFIRMED → 알림 발송
```

수정 비용을 사후 통보가 아니라 **사전 고지**로 옮기기 위해서다. 확정 후 입력을 고치면 전원이 재계산되어 이미 입금한 사람에게 추가금·환불이 발생한다(§5-c). 그걸 누르기 전에 알려야 한다.

**미리보기 문구 (최초 확정)**

> 계산이 완료되었습니다. 수락하면 참여자에게 금액이 공개됩니다.
> 이후에도 수정할 수 있지만, 수정하면 전원이 다시 계산되어
> 이미 입금한 사람에게 추가금이나 환불이 발생할 수 있습니다.

재확정일 때는 추측이 아니라 **실제 수치**를 보여준다 — `추가 입금 필요 3명 · 9,450원` / `환불 필요 1명 · 3,000원`.

#### 미리보기와 수락 사이의 경합 — 반드시 막을 것

두 단계로 나누면 **그 사이에 참여자가 체크를 바꿀 수 있다.** 그러면 주최자가 확인하고 동의한 금액과 실제로 확정되는 금액이 달라져, 게이트를 만든 목적 자체가 무너진다.

**미리보기 응답에 계산 입력 전체의 해시(`inputHash`)를 실어 보내고, 수락 요청에 그것을 되돌려받아 검증한다.** 불일치하면 거부하고 미리보기를 갱신한다.

> `"수아님의 응답이 변경되었습니다. 금액을 다시 확인해주세요."`

**여기서는 재확인을 요구해도 된다.** 주최자는 앱 앞에 있고, 금액이 바뀌었다면 마땅히 다시 봐야 한다. 참여자에게 재시도를 요구하지 않는 것(§5-c)과는 대상이 다르다.

### 미응답자 처리 — 최대 리스크

**전원이 체크할 것이라 가정하면 안 된다.** 반드시 잠수타는 사람이 나오고, 정산이 그 사람 손에 인질로 잡히면 서비스가 멈춘다.

주최자는 언제든 확정할 수 있어야 한다. 미응답자는 주최자가 대신 체크하거나 "전체 참석·음주"로 일괄 처리한다. 주최자 화면에 `응답 3/5`가 항상 보여야 한다.

### 자기신고 신뢰

전원 로그인이므로 남의 이름을 대신 누르는 것은 막힌다. 다만 **자기에게 유리하게 거짓 체크하는 것**은 여전히 가능하다 (실제로 2차를 갔는데 불참으로 찍기).

**기술로 막지 않는다.** 결과 화면에서 **전원의 체크 내역을 모두에게 공개**한다. 서로 아는 사이이므로 공개성이 자정작용을 한다. 의도된 설계다.

## 5-b. 입금 상태 — 양쪽이 누른다

입금 여부는 **보낸 사람과 받은 사람이 각각 표시**한다. 자동 확인은 불가능하다(오픈뱅킹·마이데이터는 개인 개발자가 붙일 수 없다).

```
NONE ──(참여자: "보냈어요")──> SENT ──(주최자: "받았어요")──> RECEIVED
  └──────────────(주최자: "받았어요")──────────────────────────┘
```

| 전이 | 누가 | 비고 |
|---|---|---|
| NONE → SENT | 참여자 본인 | 취소 가능 (RECEIVED 전까지) |
| SENT → RECEIVED | 주최자 | |
| NONE → RECEIVED | 주최자 | 현금으로 받았거나 참여자가 표시를 안 한 경우 |
| RECEIVED → 해제 | **주최자만** | 참여자는 해제할 수 없다 |

**이 두 단계 분리가 핵심이다.** `SENT`인데 `RECEIVED`가 아닌 상태가 화면에 그대로 보이면, "나 보냈는데?" vs "안 왔는데?" 분쟁이 대화가 아니라 화면에서 드러난다. 그리고 주최자가 일일이 확인하지 않아도 참여자가 먼저 표시하므로 주최자의 부담이 준다.

주최자 화면에는 `입금 3 / 5` 진행률과, 상태별로 구분되는 목록이 보여야 한다.

**`SENT`/`RECEIVED`로 표시하는 순간 그 시점의 부담액을 `paidAmount`에 기록한다.** 자기신고가 아니라 서버가 계산해 박는다. 조작 여지가 없고, 이 값이 §5-c의 차액 계산 근거가 된다.

## 5-c. 확정 후 재정산 — 추가금과 환불

**N빵은 한 사람만 고쳐도 전원이 흔들린다.** 분모가 바뀌기 때문에 피할 수 없다.

```
5명 확정 → 4명 입금 완료
  → "재훈이 2차 안 갔대" 한 줄 수정
      → 재훈 금액 ↓ · 나머지 4명 금액 ↑
          → 이미 입금한 4명 전원에게 차액 발생
```

계산 결과를 저장하지 않으므로 금액은 매번 새로 나오지만, `paymentStatus`는 저장된다. **저장된 상태가 어느 금액에 대한 것인지 알 수 없는 것이 문제다.** `paidAmount`가 그 간극을 메운다.

```
차액(p) = 현재 최종부담액(p) − paidAmount(p)

  > 0   추가 입금 필요    "이미 19,150원 보내셨고, 3,150원이 더 필요합니다"
  < 0   환불 대상        "3,000원을 돌려받으실 예정입니다"
  = 0   완료
```

**컬럼 하나로 추가금과 환불이 같은 식으로 처리된다. 부호만 다르다.**

### 실제 송금은 하지 않는다

**앱은 "얼마를 더 주고받아야 하는지"까지만 알려준다.** 실제 송금은 당사자끼리 한다(§9 — 전자금융거래법). 주최자가 정리를 마치면 `RECEIVED`를 다시 눌러 `paidAmount`를 갱신하고, 차액이 0이 된다.

- W2 참여자 화면 — 차액과 방향 표시
- H4 주최자 화면 — **`환불 대상 2명`** 목록

### 되돌리기 경고

`CONFIRMED → COLLECTING` 요청이 오면 **이미 입금한 인원 수를 세어 경고한다.**

> `4명이 이미 입금했습니다. 수정하면 전원의 금액이 바뀌어 추가 입금이나 환불이 발생합니다.`

`COUNT(*) WHERE payment_status <> 'NONE'` 한 줄이지만, **이 경고가 없으면 주최자가 무심코 눌러서 단톡방이 뒤집힌다.**

### 참여자에게는 재시도를 요구하지 않는다

참여자 체크 제출과 주최자 확정이 경합하면, 낙관적 락 충돌로 `"다시 시도해주세요"`를 띄우게 된다. **술자리 다음날 아침의 사용자에게 재시도를 요구하는 것은 이탈이다.**

상태를 UPDATE 조건에 넣어 한 번에 처리하고, 갱신된 행이 없으면 재시도가 아니라 **명확한 종료**를 보여준다.

> `"이미 정산이 확정되었습니다."`

## 6. 안내 문구 (고정)

결과 화면과 체크 화면에 **반드시** 표시한다.

> 모든 금액은 올림 처리되며, 주최자의 부담을 조금이나마 덜기 위함입니다.

계산 규칙을 숨기지 않는 것이 신뢰를 만든다.

## 7. 계산 규칙 (개요)

정확한 정의와 검증된 테스트 케이스는 **`CALC_RULES.md`** 에 있다.

### 7.1 차수별 부담
```
비주류 = total - alcohol
참석자(면제자 제외) 각각에게  비주류 / 참석자수
음주자(면제자 제외) 각각에게  alcohol / 음주자수
```

### 7.2 기타 항목
`bearerIds` 중 면제자를 뺀 인원끼리 균등 분담.

### 7.3 면제
`exempt = true`인 참여자는 **부담 0**이며 **모든 분모에서 제외**된다. 그의 몫은 나머지가 나눠 낸다.
**면제자는 대표결제자가 될 수 없다.** (대표결제자는 잔액을 흡수하므로 부담 0과 모순)

### 7.4 반올림 — 대표결제자 규칙
> 원칙: **결제하느라 고생한 사람이 덜 낸다.**

1. 대표결제자 = 면제자를 제외하고 결제 총액이 가장 큰 참여자 (동률이면 id 사전순)
2. 대표결제자를 뺀 전원의 부담액을 `roundingUnit` 단위로 **올림**
3. 대표결제자 = `전체 총액 − 나머지 전원의 합`

합계가 원금과 **항상 정확히 일치**한다. 구조로 보장되므로 별도 보정 로직을 넣지 말 것.

`roundingUnit`은 **10과 100만 허용한다.** 1000은 대표결제자를 음수로 만든다 (`CALC_RULES.md` T7).

다만 **unit=100에서도 인원이 많고 금액이 작으면 대표결제자가 음수가 된다** (15명 / 18,100원 이하). 예외 처리 대신 `모든 최종 금액 ≥ 0` 불변식으로 막고, 위반 시 unit을 10으로 강등해 재계산한다.

### 7.5 송금 목록
```
순잔액(p) = p의 결제 총액 − p의 최종 부담액
```
채권자·채무자를 각각 금액 내림차순 정렬 후 큰 쪽부터 greedy 상계. **최적화하지 말 것.**

## 8. 화면

### 주최자 앱

**H1 · 모임 만들기** — 모임 이름, 날짜, 참여자 이름 추가(칩), 반올림 단위(10/100)

**H2 · 차수 입력**
- 차수 카드: 라벨, 총액, 결제자(수정 가능)
- 술값 입력 방식 두 가지 — **직접 금액** 또는 **술병 계산**
  - 술병: `소주 [5]병 × [5,000]원`, `맥주 [3]병 × [6,000]원` → 자동 합산
  - 영수증에 병 수가 찍히므로 금액 계산보다 쉽다
- 기타 항목 추가: 항목명, 금액, 결제자, **부담할 사람 선택**
- 면제자 지정 (참여자 목록에서 토글)
- 하단: "링크 만들기" → shareToken 생성

**H3 · 수집 현황** — `응답 3/5` 진행률, 응답자 요약, 미응답자 "대신 체크", **[지금 확정하기]** 항상 활성

**H3-b · 확정 미리보기** (§5)
- 참여자별 최종 금액과 송금 목록
- §6 안내 문구 — **주최자가 대표결제자 규칙을 처음 마주하는 지점이다**
- 재확정일 때는 `추가 입금 필요 3명 · 9,450원` / `환불 필요 1명 · 3,000원`
- **[다시 볼게요] / [수락]** — 수락이 곧 알림 발송 트리거

**H4 · 결과 / 입금 관리**
- 참여자별 금액 + 프로필 사진
- 송금 목록
- **입금 현황** — `입금 3/5` 진행률. 각 참여자의 상태를 배지로 구분
  - `미입금` (NONE) / `보냈다고 함` (SENT) / `확인됨` (RECEIVED)
  - 주최자는 각 행에서 "받았어요" 토글, 해제도 가능
- **환불 대상 목록** — 재정산으로 차액이 음수가 된 사람들 (§5-c)
- 공유 버튼 두 개: **단톡에 전체 공유** / **개인별 링크 복사**

**H5 · 참여자 관리** (COLLECTING 상태에서만)
- 명단에서 참여자 제거 (링크로 아무나 들어온 경우 대비, §2-b)
- 면제자 지정 토글
- **[링크 재발급]** — 기존 `shareToken`을 무효화하고 새로 만든다

### 링크 재발급이 필요한 이유

정산 링크에는 **참석자 실명과 금액이 전부 들어 있다.** 잘못된 단톡방에 뿌렸을 때 주최자가 할 수 있는 일이 없으면 안 된다. 토큰 하나를 갱신하는 것으로 끝나므로 비용은 거의 없다. §2-b의 "참여자 제거" 권한과 짝을 이룬다.

### 참여자 웹

**W1 · 체크** — `/g/{shareToken}`
- 이름 선택 → 차수별 `참석` 토글, 켜지면 `술 마심` 토글 활성
- 하단에 §6 안내 문구
- 제출 → W2

**W2 · 내 결과** — `/g/{shareToken}/me`
- CONFIRMED 이전: "아직 정산 중입니다"
- CONFIRMED 이후:
  - **내 금액** (크게)
  - **근거** — 차수별 `1차 참석·논알콜 → 10,400원`, `2차 불참 → 0원`. **이 영역이 제품의 핵심이다. 축약하지 말 것.**
  - **입금 정보** — 은행명(텍스트), 예금주, 계좌번호 + **[계좌번호 복사]**
  - **[보냈어요]** 버튼 — 누르면 `SENT`. 주최자가 확인하면 `확인됨`으로 바뀐다
  - **차액** (재정산된 경우만, §5-c) — `이미 19,150원 보내셨고, 3,150원이 더 필요합니다` 또는 `3,000원을 돌려받으실 예정입니다`
  - 앱 설치 권유 배너 (§2 — 로그인은 이미 했으므로 설치만 권유)
  - **후원 링크** (최하단) — 정산이 끝나 만족한 순간이 유일하게 권할 만한 타이밍이다. **후원의 대가로 어떤 기능도 주지 않는다** (§9)

**W3 · 전체 내역** — `/g/{shareToken}/all`
- 전원의 체크 내역과 금액
- 차수별 총액·술값·결제자
- 단톡에 공유되는 링크가 이것이다

### 계좌번호 복사 — 반드시 이렇게

**클립보드에는 숫자만 넣는다.** 하이픈·공백·은행명을 전부 제거한다. 은행명과 예금주는 화면에 텍스트로만 표시한다.

```
클립보드 ← accountNo.replace(/[^0-9]/g, "")
```

은행명까지 복사하면 송금 앱 입력란에서 잘린다.

**토스 딥링크(`supertoss://send?bank=..&accountNo=..&amount=..`)는 부가 기능으로만 넣는다.** 토스가 공식 문서로 제공하는 스킴이 아니라 언제든 바뀔 수 있다. 실행 실패 시 계좌번호 복사로 폴백해야 한다.

## 9. MVP에서 만들지 않는 것

여기 있는 것을 구현하면 범위 위반이다.

- **참여 신청·승인 절차** — 링크를 아는 사람은 그냥 들어온다. 주최자의 "제거" 권한만으로 충분하다 (§2-b)
- **참여 취소 승인 흐름** — 모임 날짜가 지난 뒤 빠지려면 주최자 승인, 같은 절차. 실제 오남용 빈도를 보고 판단
- **Deferred Deep Link / 딥링크 대행 서비스** (Branch, AppsFlyer 등) — 웹이 완전히 동작하면 불필요 (§3)
- 카카오 친구 목록 불러오기 / 친구에게 메시지 보내기 (§2)
- 메뉴(항목) 단위 분할, 영수증 OCR
- 부분 참석(먼저 감), 가중치 분담(선배가 더 냄)
- 자동 입금 확인 (오픈뱅킹·마이데이터 — 개인 개발자 불가). 양방향 수동 체크만 (§5-b)
- 실제 송금 중개 (전자금융거래법)
- **실제 환불 처리 흐름** — 차액을 표시하는 데까지만 한다. 송금은 당사자끼리 (§5-c)
- **광고** — 넣지 않는다. 정산 금액 옆에 배너가 붙으면 신뢰를 깎는다. 이건 범위 결정이 아니라 제품 원칙이다
- **인앱결제** — 출시 후 판단. 지금은 `User.tier` 필드 자리만 확보한다
- 다국어, iOS (Android 먼저)
- **`Group` 통계·활동 타임라인(Activity)** — `ADR-009`가 범위 밖으로 명시. `Gathering` 몇 회, 총 지출 같은 집계는 나중
- **`Group` 안에서 `Gathering` 자동 생성·소속 전원 자동 초대** — `ADR-009`. 매번 링크로 들어와 확인하는 흐름은 안 바뀐다
- **채팅 전문 검색** — Elasticsearch 도입 전까지(`ADR-012`가 마지막 단계로 유예)
- **채팅 이미지/파일 첨부** — `type: IMAGE`는 스키마에 자리만 있다. 업로드·스토리지 연동은 범위 밖
- **Eureka·Config Server, Logstash·Kibana** — `ADR-013`·`ADR-012`가 명시적으로 배제. k3s 네이티브 기능과 중복되거나(전자) 이미 있는 관측 스택과 중복(후자)

- 참여자 웹: React(CSR) + Vercel. 카카오톡 미리보기는 백엔드가 별도 OG HTML로 응답(`ADR-007`)
- 로그인: 카카오 로그인, 구글 로그인 (닉네임·프로필 이미지는 기본 동의항목)
- 배포: OCI Always Free **1대** (2 OCPU / 12GB, ARM64). 콘솔 확인 완료 — 추가 인스턴스 없음

### FCM은 주최자 전용이다

**참여자는 웹이므로 디바이스 토큰이 존재하지 않는다.** 로그인 여부와 무관하게 FCM을 보낼 수 없다. 참여자 알림은 **단톡방 카카오톡 링크**가 담당한다 — 한국에서 정산 알림의 실질적 채널은 이미 그쪽이고, 푸시 하나가 그것을 이기지 못한다.

주최자에게는 여전히 쓸모가 있다. `5명 중 5명이 응답했어요`, `수아님이 입금을 보냈다고 표시했어요` — 앱을 계속 들여다보지 않아도 되게 만들어 §5의 주최자 부담 경감과 결이 맞는다. 구현은 §11의 맨 마지막이고, **없어도 서비스는 완결된다.**

### OCI Always Free는 ARM이다

**2 OCPU / 12GB는 Ampere A1, 즉 ARM64 기준이다.** GitHub Actions의 기본 러너는 x86이므로 그냥 빌드하면 **ARM 서버에서 뜨지 않는 이미지가 나온다.** ARM 러너를 쓰거나 `buildx` 크로스 빌드가 필요하다.

### 로그에 shareToken을 남기지 말 것

Loki를 쓰므로 액세스 로그에 URL 전체를 남기면 `/g/{token}`이 로그 저장소에 영구 축적된다. **로그 조회 권한만 있으면 모든 모임의 정산 내역을 볼 수 있게 된다.** 로깅 필터에서 토큰을 마스킹한다. 처음에 안 하면 이미 쌓인 로그를 되돌릴 수 없다.

### 모니터링이 서비스를 죽이지 않게 할 것

k3s·서비스 3개·MySQL·Redis·Kafka·Loki·Prometheus·Grafana를 12GB 한 대에
올린다(개략 6.3~9.2GB, `ADR-012`·`ADR-013` 참조 — 전부 추정치이며 `bench/`로
실측할 것). **컨테이너별 메모리 상한과 스왑 2~4GB를 처음부터 지정한다.** 상한이
없으면 Prometheus가 부풀어 앱을 OOM으로 죽인다 — 감시자가 감시 대상을 죽이는
셈이다. 앱과 MySQL에 우선순위를 주고 모니터링을 조인다.

**MongoDB·Elasticsearch를 이 12GB 예산에 넣지 않는다.** MongoDB는 Atlas
관리형으로 오프로드했고, Elasticsearch는 도입 시점을 마지막으로 유예했다
(`ADR-012`). 이 둘을 자체 호스팅으로 착각하고 예산을 다시 짜면 안 된다.

## 11. 구현 순서 — 반드시 이 순서로

### 설계 단계

1. **문서 정리** — 이 문서, `CALC_RULES.md`, `00-README.md`, `ADR/`
2. **계산 엔진을 순수 함수로 구현하고 `CALC_RULES.md`의 T1~T11 + 불변식 테스트를 전부 통과시킨다.** DB도 UI도 없이
3. **스키마 설계** — Liquibase changelog. **모든 테이블·컬럼에 `remarks` 필수**
4. **ERD** — Mermaid `erDiagram` (`docs/ERD.md`)
5. **테이블 명세서** — `docs/table-spec.xlsx`. DB의 `information_schema`·`pg_description`에서 자동 생성
6. **API 명세** — 엔드포인트 목록, 요청·응답, 에러 코드
7. **화면 ↔ API 매핑 흐름도** — 어느 화면이 어느 엔드포인트를 언제 부르는지

### 구현 단계

8. 도메인 모델 + 저장소
9. 카카오/구글 로그인 (웹 + 앱 공통)
10. 참여자 웹 (W1, W2, W3)
11. 주최자 앱 (H1~H5)
12. 카카오톡 공유 / OG 태그
13. 입금 상태 양방향 체크 + 재정산 차액 (§5-b, §5-c)
14. FCM 알림 (주최자 전용)

2번이 끝나기 전에 화면을 만들지 않는다. **이 서비스의 난이도는 UI가 아니라 계산 규칙에 있다.**

### 확장 단계 — Group · 실시간 채팅 · MSA (`ADR-009`~`013`)

**1~14가 전부 끝난 뒤 시작한다.** 1회성 `Gathering` 정산이 먼저 완결돼야 그
위에 `Group`을 얹는 의미가 있다.

15. **`Group`/`GroupMember` 추가** — `gathering.group_id` 컬럼, H0 화면에 그룹별 묶음 표시
16. **MySQL 전환** — 이 단계 전까지는 PostgreSQL로 개발해도 무방. `ADR-011`의 판단은
    "정산 도메인은 규모상 어느 쪽이어도 무리 없다"이므로 전환 비용이 낮을 때(스키마가
    아직 단순할 때) 미리 해두는 편이 낫다
17. **k3s 전환 · Spring Cloud Gateway** — REST API 서비스를 k3s Deployment로.
    `ADR-013`이 정한 예산(서비스 3개, Eureka·Config Server 없음)을 지킨다
18. **Kafka 도입** — 아웃박스의 발행 대상을 FCM 직접 호출에서 Kafka로 전환(`ADR-002` 확장)
19. **채팅 게이트웨이 (Netty + WebSocket + MongoDB Atlas + Redis)** — 별도 서비스로 배포(`ADR-010`)
20. **Elasticsearch (채팅 검색)** — 남는 인프라 여유로 마지막에(`ADR-012`)

각 단계 전에 `bench/`로 실제 메모리를 재서 `ADR-012`·`ADR-013`의 추정치를 갱신한다.

### 명세서는 손으로 쓰지 않는다

`remarks`로 DB에 코멘트를 박아두면 **5번 명세서를 스키마에서 직접 뽑을 수 있다.** 손으로 관리하는 명세서는 3개월이면 반드시 실제 스키마와 어긋난다. 스키마가 바뀌면 생성 스크립트만 다시 돌린다.
