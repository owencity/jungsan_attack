# ADR-018 · `ADR-013`(k3s)을 발동한다 — 단, 반론을 적어두고 간다

**상태** 제안 (CTO 결정 대기) · **관련** `ADR-006`(무중단 배포 조건), `ADR-012`(예산),
`ADR-013`(발동 대상), `ADR-014`(보류시킨 결정), `ADR-016`·`ADR-017`

> **이 문서는 셋 중 근거가 가장 약하다.** `016`·`017`과 달리 반론이 아직 살아
> 있어서, 확정 전에 §"정직한 반론"을 반드시 읽고 판단해야 한다.

## 맥락

`ADR-014`는 MSA·k3s를 보류시키면서 **발동 조건을 표로 적어뒀다.**

| 조건 | 발동할 ADR |
|---|---|
| 프로세스가 2개 이상이 되어 배포·감시 대상이 늘어날 때 | `ADR-013` (k3s + Spring Cloud) |

`ADR-016`(Redis)과 `ADR-017`(Kafka)을 도입하면 운영 대상이 이렇게 된다.

```
지금          app · MySQL · (Prometheus · Loki · Grafana)
이후          app · 영수증 워커 · MySQL · Redis · Kafka · n8n · (관측 스택)
```

## 결정

**`ADR-013`을 발동하되, MSA 전환이 아니라 "오케스트레이션 전환"으로 범위를 좁힌다.**

- **서비스를 쪼개지 않는다.** `ADR-014`의 모놀리스·feature 패키지 결정은 유효하다.
  `server`는 여전히 단일 Spring Boot 프로세스다.
- **분리되는 것은 영수증 워커 하나뿐이다.** 웹 요청과 자원 성격이 달라서다(§근거).
- **Spring Cloud(게이트웨이·서비스 디스커버리)는 도입하지 않는다.** 서비스가
  하나뿐이라 디스커버리할 대상이 없다. `ADR-013`에서 k3s 부분만 가져온다.

## 근거

### "프로세스 2개 이상"의 약한 해석과 강한 해석

**약한 해석**(컨테이너 수가 늘었다)은 쓰지 않는다. 그 기준이면 `ADR-006` 시점에
이미 app·MySQL·Prometheus·Loki·Grafana로 5개였고, docker compose가 그걸
문제없이 감당해왔다. **컨테이너가 늘었다는 사실만으로 k3s를 정당화할 수 없다.**

**강한 해석은 "독립적으로 배포·확장해야 하는 애플리케이션 프로세스가 둘 이상"**
이고, 이건 실제로 발생한다.

- **영수증 워커**는 OCR·AI 호출 때문에 느리고, 외부 레이트리밋에 묶여 있고,
  메모리 사용이 이미지 크기에 따라 튄다. 웹 요청 프로세스와 같은 컨테이너에
  두면 영수증 한 건이 정산 API 응답을 끌어내린다. **자원 격리가 필요하다.**
- 배포 주기도 다르다. 프롬프트·모델을 바꾸는 일이 정산 로직보다 훨씬 잦다.

### 단일 노드에서도 남는 k3s의 값

`ADR-006`은 *"노드가 하나라 스케줄링·자가치유·롤링 업데이트라는 K8s의 본질이
전부 무의미하다"*고 적었다. 절반은 지금도 맞다 — **스케줄링은 무의미하다.**
남는 것은 셋이다.

- **헬스체크 기반 롤링 업데이트와 롤백.** `ADR-006`이 대가로 인정한
  *"무중단 배포가 안 된다 / 원클릭 롤백이 없다"*가 그대로 해소된다.
- **프로세스별 자원 상한의 선언적 관리.** `ADR-006`이 직접 경고한
  *"감시자가 감시 대상을 죽인다"*(Prometheus가 부풀어 앱을 OOM) 문제를
  컴포넌트가 7개로 늘어난 상태에서 compose로 관리하는 것보다 안전하다.
- **시크릿 관리.** 카카오 키·Gemini API 키·Slack 토큰·DB 비밀번호가 늘었다.

## 정직한 반론 — 확정 전에 읽을 것

1. **`ADR-006`은 이 상황에 Kamal을 먼저 보라고 지정해뒀다.**
   > 무중단 배포·롤백이 필요해질 때 → **Kamal**을 먼저 본다. K8s 없이
   > 헬스체크 기반 무중단 전환과 롤백을 주는, 소수 VM 전용 도구다.

   위 §근거에서 든 값 중 **무중단 배포·롤백은 Kamal로도 얻는다.** 자원 상한과
   시크릿까지 묶어서 보면 k3s가 낫지만, **"Kamal로는 안 되는 이유"를 아직
   실측으로 대지 못했다.** 이 칸이 비어 있는 상태다.
2. **k3s 컨트롤 플레인이 1~2GB를 먹는다.** `ADR-012` 예산표에는 n8n과 영수증
   워커가 빠져 있다. 그 둘(~1GB)을 더하면 상단이 12GB에 닿는다. **실측 전에는
   "들어간다"고 말할 수 없다.**
3. **운영 대상이 줄지 않고 늘어난다.** k3s 자체가 감시·업그레이드 대상이다.
   1인 개발에서 이건 실제 비용이다.

## 대가

- 배포 파이프라인을 다시 짠다 — `scripts/deploy/*.sh`(compose 전제)가 전부
  매니페스트 기반으로 바뀐다. `docs/DEPLOY.md`도 같이 개정해야 한다.
- 로컬 개발이 복잡해진다. `docker compose up -d` 한 줄로 MySQL만 띄우던
  `AGENTS.md` §12 흐름을 유지할지, 로컬도 k3s로 갈지 정해야 한다
  (**권장: 로컬은 compose 유지**).
- k3s 학습·장애 대응 시간이 개발 시간에서 빠진다.

## 재검토 조건 / 확정 전 해야 할 일

- [ ] **Kamal과 비교 실측.** 무중단 배포·롤백·자원 상한·시크릿 네 항목을 두
      도구로 각각 세워보고, Kamal로 안 되는 게 무엇인지 적는다. **이 칸이
      채워지기 전에는 이 ADR을 확정하지 않는다.**
- [ ] **메모리 실측.** n8n·영수증 워커를 포함해 `ADR-012` 예산표를 갱신한다
      (`bench/` 스크립트 활용). 12GB를 넘으면 관측 스택 리텐션 축소 또는
      Kafka→Redpanda 교체(`ADR-017` 퇴로)를 먼저 적용한다.
- 위 둘을 하고도 k3s가 이긴다면 확정한다. 지면 **이 ADR은 기각하고 Kamal로
  간다** — 기각도 기록으로 남긴다.
