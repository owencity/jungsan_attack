# ADR-017 · 아웃박스 뒤에 Kafka를 붙인다

**상태** 확정 · **관련** `ADR-002`(재검토 조건 발동·갱신 절 정리), `ADR-012`(호스팅),
`ADR-013`·`ADR-018`, `REQUIREMENTS.md` §10·§11

## 맥락

`ADR-002`는 브로커 대신 아웃박스 테이블을 선택하면서 **재검토 조건을 미리 적어뒀다.**

> - **이벤트 소비자가 2개 이상**이 될 때 (예: 알림 + 통계 + 외부 연동)
> - 발송 지연이 스케줄러 주기로 감당되지 않을 때
>
> **아웃박스가 있으면 그때 뒤에 브로커를 붙이는 전환이 쉽다.**

그리고 실제로 `ADR-002` 문서 하단에 *"재검토 조건이 실제로 발동했다(`ADR-013`)"*
라는 갱신 절이 이미 붙어 있다. 그런데 그 직후 **`ADR-014`가 `ADR-013`을 보류**
시키면서, `ADR-002`의 그 갱신 절만 공중에 뜬 상태가 됐다 — "Kafka를 붙인다"고
적혀 있는데 붙이기로 한 ADR은 보류인 모순이다. **이 문서가 그 상태를 정리한다.**

그 사이 소비자가 하나 더 늘었다. `REQUIREMENTS.md` §11이 **영수증 OCR·AI 주류
분류를 MVP로 편입**했다 — `ADR-002`를 쓸 당시에는 존재하지 않던 요구사항이고,
성격도 다르다(느리고, 외부 API에 의존하고, 실패·재처리가 일상인 작업).

## 결정

**아웃박스를 유지한 채, 그 뒤에 Kafka를 붙인다.**

```
지금        outbox 테이블 → @Scheduled → FCM 직접 호출
이후        outbox 테이블 → @Scheduled → Kafka 발행 → 컨슈머 N개
```

현재 확정된 소비자는 넷이다.

| 소비자 | 하는 일 | 근거 |
|---|---|---|
| 알림 발송 | FCM 앱·웹 푸시 + 내부 알림함 기록 | `REQUIREMENTS.md` §10 |
| 영수증 파이프라인 | 이미지 업로드 → OCR → AI 분류 → 총무 검토 대기 | `REQUIREMENTS.md` §11 |
| 이의제기 채팅 브로드캐스트 | 1:1 채팅 메시지 전달 | `DOMAIN_DB_DESIGN_V2.md` |
| (향후) 통계 | 정산 규모·응답률 집계 | `ADR-002` 재검토 조건이 예로 든 항목 |

**`ADR-002`의 핵심 근거는 그대로 유지된다** — 발행은 비즈니스 트랜잭션과 같은
커밋에 아웃박스로 남기고, Kafka 발행이 실패해도 아웃박스 재시도가 간극을 메운다.
**아웃박스를 Kafka로 대체하는 게 아니라, 아웃박스가 Kafka의 발행자가 된다.**

## 근거

### 영수증 처리는 아웃박스 폴러로 감당할 모양이 아니다

`ADR-002`가 상정한 작업은 "FCM 한 번 호출"이었다 — 짧고, 실패하면 재시도하면
그만이다. 영수증 파이프라인은 다르다.

- **오래 걸린다.** 이미지 업로드 → OCR → AI 분류가 초 단위로 이어진다. 폴러
  스레드가 이걸 붙잡고 있으면 그동안 알림 발송이 밀린다.
- **단계마다 실패 지점이 다르다.** OCR은 성공했는데 AI 분류만 실패한 경우,
  처음부터 다시 돌리면 OCR 비용을 또 낸다(§`ADR-016` 쿼터 참조).
- **소비 속도를 따로 조절해야 한다.** 알림은 빨리, 영수증은 외부 API 레이트
  리밋에 맞춰 천천히 — 같은 폴러 안에서는 분리가 안 된다.

소비자별로 독립적으로 읽고, 실패 지점부터 재처리할 수 있는 **재처리 가능한
이벤트 로그**가 필요하다. 이게 Kafka를 고른 이유다.

### 왜 Redis 큐나 DB 큐가 아닌가 — 그리고 솔직한 한계

**지금 트래픽만 보면 DB 큐나 Redis 큐로 충분하다.** 이건 인정하고 간다.
Kafka를 고른 이유는 셋이다.

1. **소비자별 오프셋.** 한 이벤트를 알림·통계·영수증이 각자의 속도로 읽는다.
   Redis 리스트는 꺼내면 사라져서 다중 소비자에 맞지 않고, 구현하려면 소비자
   수만큼 큐를 복제해야 한다.
2. **재처리.** 컨슈머 버그를 고친 뒤 오프셋을 되감아 다시 처리할 수 있다.
   DB 큐는 처리 완료 행을 지우거나 상태를 바꿔버려 되감을 원본이 없다.
3. **`ADR-012`가 이미 자리를 잡아뒀다.** Kafka 자체 호스팅과 메모리 예산이
   확정돼 있고, 안 맞으면 Redpanda로 교체하는 퇴로까지 적혀 있다.

## 대가

- **이 규모에 과하다.** 정산 이벤트는 초당 몇 건 수준이다. Kafka는 그보다 몇
  자릿수 위를 위한 물건이고, JVM 프로세스 하나가 통째로 늘어난다(~1GB+).
  **`ADR-002`가 "초당 몇 건 규모의 발송에 브로커 운영 비용을 얹을 이유가 없다"고
  쓴 문장은 트래픽만 놓고 보면 지금도 맞다.** 이 결정은 트래픽이 아니라
  **소비자 수와 작업 성격**이 바뀌어서 내리는 것이다.
- **운영·감시 대상이 하나 더 늘어난다.** 이게 `ADR-018`(k3s)로 이어진다.
- **메시지 순서·중복 처리 책임이 소비자로 넘어온다.** 최소 1회 전달이므로
  컨슈머가 멱등해야 한다 — 알림 중복 발송 같은 사고가 여기서 난다.
- 12GB 예산이 더 빡빡해진다. `ADR-012`의 예산표에는 **n8n(자동 코드리뷰
  파이프라인)과 영수증 워커가 빠져 있다.** 실측으로 갱신해야 한다.

## 재검토 조건

- 실측 결과 Kafka가 단일 인스턴스에서 메모리를 감당 못 하면 → **Redpanda로
  교체**한다(`ADR-012`가 이미 지정해둔 퇴로)
- 소비자가 다시 하나로 줄어들면(예: 영수증 파이프라인을 외부 SaaS로 넘김) →
  아웃박스 직접 호출로 되돌리는 것을 검토한다. **되돌릴 수 있게 아웃박스를
  남겨두는 것이 이 설계의 핵심이다**
- 컨슈머 멱등성 사고(중복 알림 등)가 반복되면 → 이벤트 키 설계와 dedup 저장소를
  다시 본다
