# ADR-024 영수증은 후보만 추출하고 총무가 확인한 값을 입력한다

## 맥락

총무는 촬영·다중 사진 선택으로 금액 입력을 줄이고 싶다. 간단 N빵에는 총액만, 상세 정산에는 총액과 술 항목이 필요하다. 현재 Python 평가 32장 중 모든 조건 일치는 14장이므로 인식 결과만으로 송금액을 확정할 수 없다. 운영 VM은 ARM 2CPU·12GiB이며 기존 Spring·MySQL과 다른 서비스를 함께 실행한다.

## 결정

앱은 최대 5장의 영수증을 한 장씩 Spring에 보낸다. Spring은 사용자·총무·OPEN 상태를 확인하고 내부 Python에 전달한 뒤 숫자·사전 주류 후보만 반환한다. 사용자가 원본과 후보를 대조해 수정·확인하기 전에는 정산 입력으로 쓰지 않는다. 추론 전후 짧은 읽기 트랜잭션만 사용하고 DB 잠금을 잡은 채 Python을 기다리지 않는다.

Python은 별도 내부 컨테이너에서 CPU 1개 상당·메모리 3GiB로 시작한다. 한 번에 1건, 사용자당 60초 10회, 저장 없는 동기 요청이다. 모델은 빌드 시 고정 해시로 포함하며 요청이 40초 이상 멈추면 OCR 프로세스만 종료하고 재기동한다. 사진·원문·키·사용자 식별자는 로그·측정 태그에 남기지 않는다. ARM 실측을 통과해야 운영을 켠다.

간단 N빵은 저장 없이 기존 core에 한 차수·전원 참석을 넘긴다. 송금액 1원 올림과 결제자 잔액 조정 규칙을 재사용한다. 새 계산 엔진이나 가짜 회원·술자리 데이터는 만들지 않는다.

## 근거

기존 직접 Python 공개는 사용자 권한을 중복 구현해야 한다. 파일 보관·대기열은 이번 입력 보조에 필요하지 않다. Spring 안에 모델을 넣으면 CPU 추론 장애가 정산 API에 영향을 줄 수 있다. 별도 컨테이너와 제한으로 영향을 줄이고, 조회·확정·입금 처리 경로는 기존 방식으로 둔다. Redis·Kafka·k3s는 이 규모의 단일 실행에 추가하지 않는다.

## 대가와 재검토 조건

동시에 다른 총무가 요청하면 잠시 후 재시도가 필요하다. 앱 종료 시 미적용 사진은 사라지고 여러 차수 저장은 일부 성공할 수 있다. 사진을 다시 고르면 같은 영수증인지 항상 알아낼 수 없으므로 총무 검토가 필요하다. 인식 오류는 없어지는 것이 아니라 수정 가능한 후보로 제한한다.

실제 대기·거절 비율이 높아지거나 40초 내 처리가 어렵다면 자원·모델·비동기 큐를 비교한다. 영수증 장기 보관이나 적용 후 영수증별 이동 요구가 생기면 저장 모델·삭제 정책·개인정보 동의를 별도로 설계한다.
