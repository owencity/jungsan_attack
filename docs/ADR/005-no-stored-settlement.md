# ADR-005 · 계산 결과를 저장하지 않되 `paidAmount`로 차액을 낸다

**상태** 확정 · **관련** `SPEC.md` §4, §5-b, §5-c

## 맥락

`SPEC.md` §4는 **계산 결과를 저장하지 않고 `Attendance`로부터 매번 계산**하도록 정했다.
근거 화면(W2)과 재계산 일관성이 여기에 의존한다.

그런데 `paymentStatus`는 저장된다. 그래서 **저장된 상태가 어느 금액에 대한 것인지 알 수 없다.**

```
확정 → 카톡 공유 (수아 19,150원) → 수아 입금 → SENT
     → 주최자가 2차 금액 수정 → 재확정 (수아 22,300원)
                                    ↑ 수아는 19,150원만 보냈는데 SENT로 표시돼 있다
```

## 결정

**계산 결과는 계속 저장하지 않는다.** 대신 컬럼 하나를 추가한다.

```
Participant.paidAmount : Long | null
  SENT / RECEIVED 로 표시된 시점의 최종 부담액.
  자기신고가 아니라 서버가 계산해 기록한다.
```

```
차액(p) = 현재 최종부담액(p) − paidAmount(p)
  > 0  추가 입금 필요
  < 0  환불 대상
  = 0  완료
```

**앱은 "얼마를 더 주고받아야 하는지"까지만 알려준다.** 실제 송금은 당사자끼리 한다(§9 — 전자금융거래법).

## 근거

- **계산 레이어와 실행 레이어를 분리한다.** 계산 엔진은 순수하게 두고, 입금 추적을 그 위에 얹는다.
  §4의 "결과 미저장" 원칙이 그대로 유지된다
- **컬럼 하나로 추가금과 환불이 같은 식으로 처리된다.** 부호만 다르다
- 서버가 기록하므로 **조작 여지가 없다.** 자기신고였다면 금액을 낮춰 적을 수 있다

### 검토했다가 버린 안 — `sentForRevision`

`Gathering.revision`과 비교해 "내용이 바뀌었다"를 감지하는 안. **감지는 되지만
"얼마를 더 내야 하는지"를 못 낸다.** `paidAmount`가 상위 호환이라 폐기했다.
(`revision`은 "정산 내용이 변경되었습니다" 배지 용도로 남긴다.)

### `SENT`를 자동 초기화하지 않는 이유

재확정 시 `SENT`를 지우면 *"나 보냈는데?"* 분쟁이 그대로 생긴다.
§5-b가 입금 상태를 두 단계로 분리한 목적이 **분쟁을 대화가 아니라 화면에 드러내는 것**인데,
여기서 지우면 그 설계가 무너진다.

## 대가

- **조회마다 전체를 로드해 계산한다.** 다만 참여자 10명 × 차수 5 = `Attendance` 50행 규모라
  계산 자체는 마이크로초다. **성능은 문제가 아니다**
- 진짜 문제는 **N+1**이다. `Gathering → Participant · Round → Attendance · DrinkItem · ExtraItem`을
  순진하게 로드하면 쿼리가 수십 개 나간다.
  JPA fetch join으로 컬렉션 둘 이상을 조인하면 카테시안 곱이나 `MultipleBagFetchException`이 난다.
  → **조인하지 말고 `gathering_id`로 각 테이블을 따로 긁어 메모리에서 조립한다.** 5~6 쿼리로 고정된다.
  여기가 `JdbcTemplate`이 가장 적합한 자리다
- 부분 입금은 다루지 않는다 (§9 범위 밖)

## 재검토 조건

- 한 모임의 참여자·차수가 수십 배로 커져 계산·로딩이 실제 병목이 될 때
  → 그때도 저장이 아니라 **캐시**(확정 시점 스냅샷)를 먼저 검토한다. 근거 화면이 저장에 의존하면 안 된다
