# ADR-014 · MVP는 모놀리스로 간다. 내부는 feature 패키지로 나눈다

**상태** 확정 · **관련** `ADR-006`(부활), `ADR-010`(보류), `ADR-013`(보류)

## 맥락

`ADR-013`은 Spring Cloud + k3s MSA를 **확정**으로 적고 `ADR-006`(단일 VM)을
대체했다. 그런데 그 근거로 든 것이 *"학습 목적으로 MSA 위에서 운영하기로 했다
(사이드 프로젝트의 명시적 학습 목표)"* 였다.

**즉 신호가 와서 구조를 올린 것이 아니라, 배우고 싶어서 올린 것이다.**
이건 "구조를 위한 프로젝트"이고, 다음 두 가지를 동시에 어긴다.

- 다른 ADR들이 지켜온 방식 — `ADR-002`(브로커 대신 아웃박스), `ADR-006`(K8s 안 씀),
  `ADR-012`(Elasticsearch 유예)는 전부 **"지금 필요 없다"를 근거로 가볍게 간 결정**이다.
  `013`만 반대 방향이었다.
- MVP에서 실제로 아픈 곳이 아직 없다. 사용자도, 트래픽도, 팀도 없다.

## 결정

**MVP는 단일 Spring Boot 프로세스(모놀리스)로 간다. 배포는 `ADR-006`으로 되돌린다.**
**실시간 채팅도 이 프로세스 안에 얹는다** — `spring-boot-starter-websocket`.

```
core     순수 계산 엔진 (Spring 없음, 그대로 유지)
server   단일 Spring Boot 프로세스
  ├ gathering/    정산·모임
  ├ user/         로그인·회원
  ├ chat/         WebSocket (MVP에서 여기 얹는다)
  └ config/
```

**패키지는 layer가 아니라 feature 로 나눈다.** 이미 `gathering/`·`user/`·`config/`가
그렇게 잡혀 있고, 앞으로도 이 방식을 유지한다 — 기능 하나가 한 폴더에 모여 있어야
나중에 `chat/`을 통째로 뽑아 별도 프로세스로 옮길 수 있다(`ADR-010` 발동 시).

## 근거

### 채팅을 같은 프로세스에 얹어도 MVP 규모에선 문제가 없다

`ADR-010`은 *"REST 서버에 얹으면 커넥션 풀·스레드 모델이 서로 간섭한다"* 고 적었다.
틀린 말은 아니지만 **규모가 붙었을 때의 이야기다.** Tomcat NIO는 유휴 WebSocket
연결이 스레드를 붙잡지 않는다. 동시 접속 수십~수백 명 수준에서 체감되는 문제가 없다.

실제로 체감될 차이는 하나뿐이다 — **재배포하면 채팅 연결이 끊긴다.**
재연결 로직은 어느 구조에서든 프론트에 필요하므로(`ADR-010` 대가 항목),
MVP 단계에서 감수할 만하다.

### 분리는 나중에 해도 늦지 않다 — 경계가 이미 잡혀 있기 때문이다

`core`/`server`가 모듈로 분리돼 있어 계산 로직이 인프라에 섞이지 않는다.
`server` 내부도 feature 패키지라 기능별 경계가 있다.
**경계 없이 뭉친 모놀리스는 쪼개기가 지옥이지만, 경계가 있는 모놀리스는 쪼개기 쉽다.**

### `ADR-013`은 폐기가 아니라 보류다

MSA로 갈 이유·구성·메모리 예산 계산이 `013`에 이미 다 적혀 있다.
발동 조건이 오면 **새로 고민할 것 없이 그 문서를 실행하면 된다.**

## 대가

- **학습 기회가 미뤄진다.** Spring Cloud·k3s를 지금 당장 만져보지 못한다.
  **개발(1개월 스프린트)과 역량(6개월 트랙)을 분리해서 간다** — MVP를 빠르게 세우고,
  그 위에서 STAR·코드리뷰·DDD를 반복 훈련한다(`DEVLOG.md` 2026-08-24 참조).
- **재배포 시 채팅이 끊긴다.** 위 근거 참조 — MVP에서는 감수한다.
- 나중에 채팅을 분리할 때 **MongoDB·Kafka 도입이 한꺼번에 몰린다.**
  `ADR-010`·`ADR-012`가 그 설계를 이미 갖고 있어 리스크는 제한적이다.

## 재검토 조건

이 조건이 오면 보류된 ADR을 발동한다.

| 조건 | 발동할 ADR |
|---|---|
| 재배포로 채팅이 끊기는 것이 실제 불편으로 보고될 때 | `ADR-010` (채팅 프로세스 분리) |
| 채팅 트래픽과 정산 API 트래픽을 따로 스케일해야 할 때 | `ADR-010` |
| 프로세스가 2개 이상이 되어 배포·감시 대상이 늘어날 때 | `ADR-013` (k3s + Spring Cloud) |
| 메시지 이력이 MySQL로 감당 안 될 때 | `ADR-010`의 MongoDB 부분, `ADR-012` |

**조건 없이 "배우고 싶어서" 발동하지 않는다** — 학습은 별도 브랜치나 별도
연습 프로젝트에서 한다. 이 저장소의 구조는 실제 필요를 따라간다.
