# ADR-004 · 확정을 2단계로 나누고 `inputHash`로 경합을 막는다

**상태** 확정 · **관련** `SPEC.md` §5, §5-c

## 맥락

`CONFIRMED` 이후에도 주최자는 입력을 수정할 수 있다(§5). 그런데 N빵 구조상
**한 사람만 고쳐도 분모가 바뀌어 전원의 금액이 움직인다.** 이미 입금한 사람에게
추가금이나 환불이 발생한다. 이 비용은 계산 규칙상 제거할 수 없다.

## 결정

제거할 수 없으므로 **사전 동의로 옮긴다.** 확정을 두 단계로 나눈다.

```
[확정하기] → 미리보기(금액 + §6 안내 문구 + 수정 비용 고지) → [수락] → CONFIRMED → 알림 발송
```

그리고 **미리보기 응답에 계산 입력 전체의 해시(`inputHash`)를 실어 보내고,
수락 요청에 되돌려받아 검증한다.**

```
GET  /gatherings/{id}/settlement/preview  → { amounts, transfers, breakdown, inputHash }
POST /gatherings/{id}/confirm             { inputHash }  → 불일치 시 409
```

## 근거

### 2단계로 나누는 이유

- 주최자가 **금액을 눈으로 확인한 뒤** 확정한다. 지금까지는 눌러야 결과가 보였다
- 수정 비용을 사후 통보가 아니라 **사전 고지**로 옮긴다
- **"수락"이 곧 알림 발송 트리거**가 되어, `상태 전이 + 아웃박스 삽입 = 한 트랜잭션`이 자연스럽게 붙는다
- 재확정 시에는 추측이 아니라 **실제 수치**를 보여줄 수 있다 — `추가 입금 3명 · 9,450원` / `환불 1명 · 3,000원`

### `inputHash`가 필요한 이유

2단계로 나누면 **그 사이에 참여자가 체크를 바꿀 수 있다.**

```
T1  주최자가 미리보기 확인 (수아 19,150원)
T2  수아가 웹에서 "2차도 갔었다"로 변경
T3  주최자가 [수락]
      → 주최자가 본 적 없는 금액이 확정되어 단톡방에 뿌려진다
```

**게이트를 만든 목적 자체가 무너진다.** 해시가 다르면 거부하고 미리보기를 갱신한다.

> `"수아님의 응답이 변경되었습니다. 금액을 다시 확인해주세요."`

### 여기서는 재확인을 요구해도 되는 이유

§5-c는 **참여자에게 재시도를 요구하지 말라**고 정했다. 술자리 다음날 아침의 사용자에게
`"다시 시도해주세요"`는 이탈이기 때문이다.

**주최자는 다르다.** 앱 앞에 앉아 있고, 금액이 바뀌었다면 마땅히 다시 봐야 한다.
같은 낙관적 락이라도 **대상이 다르면 판단도 달라진다.**

## 대가

- 확정 API가 두 번 왕복한다
- `inputHash` 계산 로직이 계산 입력 구조와 함께 유지돼야 한다. 필드가 늘면 해시 대상에도 넣어야 한다

## 재검토 조건

- 미리보기–수락 사이 충돌이 실제로 거의 발생하지 않고, 그 왕복이 부담이 될 때
  → 해시 검증은 남기고 화면만 합치는 절충이 가능하다
