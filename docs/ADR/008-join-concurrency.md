# ADR-008 · 참여 동시성 — `gathering` 행 잠금과 복합 유니크로 나눠 막는다

**상태** 확정 · **관련** `SPEC.md` §5, §5-c, `API.md` §5.2, `ADR-004`

## 맥락

참여 링크는 단톡방에 뿌려진다. **여러 사람이 같은 순간에 누른다.** 술자리 다음날
아침에 링크가 올라오면 20명이 몇 초 안에 몰린다.

경합이 넷이고, **성질이 서로 달라 한 가지 장치로 다 막을 수 없다.**

### A · 정원 초과 — 조회와 삽입 사이가 벌어진다

```
정원 5명 · 현재 4명

트랜잭션 A                         트랜잭션 B
COUNT(*) → 4                       COUNT(*) → 4
4 < 5 이므로 통과                   4 < 5 이므로 통과
INSERT participant                 INSERT participant
COMMIT                             COMMIT
                                   → 6명. 정원 게이트가 뚫렸다
```

**둘 다 "아직 자리가 있다"를 본 시점이 옳았다.** 조회 결과가 삽입 시점까지
유효하다는 보장이 없는 것이 문제다.

### B · 중복 참여 — 같은 사람이 두 번 들어온다

카카오톡 인앱 브라우저에서 링크를 열고, 로그인 후 돌아오고, 느려서 한 번 더 누른다.
**두 요청이 같은 `userId` 로 동시에 도착한다.**

A 의 잠금은 이것을 막지 못한다. **순서를 세워줄 뿐 "이미 있는 사람인가"를
판단해주지 않는다.**

### C · 체크 제출과 확정이 겹친다

주최자가 확정하는 순간 참여자가 체크를 제출한다.

### D · 확정이 두 번 눌린다

주최자가 두 창을 열어두었거나 버튼을 두 번 눌렀다.

## 결정

**넷을 한 장치로 묶지 않는다. 성질에 맞는 것을 각각 쓴다.**

| | 경합 | 장치 |
|---|---|---|
| A | 정원 초과 | `gathering` 행에 `SELECT … FOR UPDATE` |
| B | 중복 참여 | `UNIQUE (gathering_id, user_id)` |
| C | 체크 vs 확정 | 조건부 `UPDATE` — 잠금 없음 |
| D | 확정 vs 확정 | 조건부 `UPDATE` — 잠금 없음 |

### A · `gathering` 행을 잠근다

```sql
BEGIN;
  SELECT id, status, expected_count
    FROM gathering
   WHERE id = ?
     FOR UPDATE;                    -- 같은 모임의 참여를 여기서 직렬화한다

  SELECT COUNT(*) FROM participant WHERE gathering_id = ?;
  -- 정원 판단 → JOINED 또는 PENDING

  INSERT INTO participant (...) VALUES (...);
COMMIT;                             -- 잠금이 풀린다
```

**`participant` 가 아니라 `gathering` 을 잠그는 이유** — 우리가 막으려는 것은
"두 사람이 동시에 INSERT 하는 것"인데 **그 행은 아직 존재하지 않는다.
없는 행은 잠글 수 없다.**

`gathering` 행은 값을 바꾸려고 잡는 것이 아니라 **그 모임 전체의 자물쇠**로 쓰는 것이다.
잠금 범위가 모임 하나이므로 다른 모임의 참여는 서로 기다리지 않는다.

> 읽기는 막히지 않는다. PostgreSQL 은 MVCC 라 평범한 `SELECT` 는 `FOR UPDATE` 를
> 기다리지 않는다. **서로 막는 것은 `FOR UPDATE` 끼리다.**

### B · 복합 유니크로 막는다

```sql
ALTER TABLE participant
  ADD CONSTRAINT uq_participant_gathering_user UNIQUE (gathering_id, user_id);
```

위반은 예외가 아니라 **정해진 응답으로 변환한다** — `409 ALREADY_JOINED`.

#### `user_id` 는 `NOT NULL` 이어야 한다

**PostgreSQL 의 `UNIQUE` 는 `NULL` 을 서로 다른 값으로 취급한다.** `user_id` 가
`NULL` 인 행은 몇 개든 들어가므로, 널을 허용하면 이 제약이 조용히 무력해진다.

`SPEC.md` §4 는 아직 `userId → User.id | null` 로 적혀 있다. **낡았다.**
주최자가 이름만 미리 등록하는 기능을 뺐고 참여는 로그인 필수가 되어
(`SPEC.md` §5, `API.md` §5.2) **모든 `Participant` 가 계정을 가진다.**
SPEC 갱신 때 `NOT NULL` 로 고친다.

### C · D · 조건부 `UPDATE` — 여기는 잠그지 않는다

```sql
-- D · 확정
UPDATE gathering
   SET status = 'CONFIRMED', revision = revision + 1, confirmed_at = now()
 WHERE id = ? AND status = 'COLLECTING';
-- 갱신된 행이 0이면 이미 누군가 확정한 것이다 → 409 GATHERING_CONFIRMED
```

```sql
-- C · 체크 제출
UPDATE attendance ... WHERE ... AND (SELECT status FROM gathering WHERE id = ?) = 'COLLECTING';
-- 0행이면 → 409 GATHERING_CONFIRMED
```

**`SPEC.md` §5-c 가 이 방식을 지정했다.**

> 참여자 체크 제출과 주최자 확정이 경합하면, 낙관적 락 충돌로 `"다시 시도해주세요"`를
> 띄우게 된다. **술자리 다음날 아침의 사용자에게 재시도를 요구하는 것은 이탈이다.**
> 상태를 UPDATE 조건에 넣어 한 번에 처리하고, 갱신된 행이 없으면 재시도가 아니라
> **명확한 종료**를 보여준다.

**C 의 "금액이 달라지는" 쪽은 잠금이 아니라 `inputHash` 가 막는다** (`ADR-004`).
미리보기와 수락 사이에 체크가 바뀌면 해시가 어긋나 `409 STALE_INPUT_HASH` 로 거부된다.
**주최자에게는 재확인을 요구해도 된다** — 앱 앞에 있고, 금액이 바뀌었다면 다시 봐야 한다.

## 근거

- **A 만 잠금이 필요하다.** A 는 *"읽은 값이 쓸 때까지 유효한가"* 를 묻는 유일한 경합이다.
  C·D 는 *"지금 상태가 무엇인가"* 만 물으므로 `WHERE` 절 한 줄로 원자적으로 판정된다.
  **필요 없는 곳까지 잠그면 대기만 늘고 막는 것은 없다**
- **B 를 애플리케이션 코드로 막지 않는다.** `if (exists) throw` 는 그 검사와 INSERT
  사이에 또 같은 틈이 생긴다. **제약은 DB 만이 원자적으로 보장한다**
- **잠금 단위가 모임이라 경합 범위가 좁다.** 한 모임의 참여자는 수십 명이고 트랜잭션은
  밀리초다. 서로 다른 모임은 아예 만나지 않는다
- 참여자에게 재시도를 요구하지 않는다 (`SPEC.md` §5-c)

### 검토했다가 버린 안 — `gathering.participant_count` 비정규화

`COUNT(*)` 대신 카운터 컬럼을 두고 `UPDATE … SET participant_count = participant_count + 1
WHERE participant_count < expected_count` 로 원자적으로 처리하는 안. **잠금 없이 A 가 풀린다.**

버린 이유는 **그 컬럼을 갱신해야 하는 경로가 참여 하나가 아니기 때문**이다.

```
참여          +1
명단에서 제거   −1        API.md §6.2
승인          +1 (PENDING → JOINED 로 세는 기준이 바뀐다)
거부          변화 없음 또는 −1
모임 삭제 복구  ?
```

**다섯 경로 중 하나만 빠뜨려도 정원 게이트가 조용히 틀린다.** 그리고 틀린 것이
드러나는 시점은 *"6번째 사람이 승인 없이 들어왔다"* 는 사용자 신고다.
`COUNT(*)` 는 언제나 맞다. **참여자 수십 명 규모에서 `COUNT(*)` 는 병목이 아니다.**

### 검토했다가 버린 안 — 낙관적 락(`@Version`)

A 에 `@Version` 을 쓰면 충돌 시 예외가 나고 **재시도를 해야 한다.**
참여 버튼은 참여자가 누르는 것이므로 `SPEC.md` §5-c 가 금지한 자리다.
재시도를 서버에서 감추면 결국 루프를 도는 비관적 락과 같아진다.

## 대가

- **같은 모임의 참여 요청이 직렬화된다.** 20명이 동시에 눌러도 한 명씩 처리된다.
  트랜잭션이 밀리초라 체감되지 않지만, **트랜잭션 안에서 느린 일을 하면 즉시 문제가 된다**
- **잠금을 잡은 트랜잭션 안에서 외부 호출을 하지 않는다.** 카카오 API 호출·FCM 발송·
  아웃박스 소비는 전부 트랜잭션 밖이다. 네트워크를 기다리는 동안 뒤에 20명이 줄을 선다.
  **로그인 검증은 참여 트랜잭션 이전에 끝나 있어야 한다**
- **잠금 순서를 하나로 고정한다.** 여러 테이블을 잠글 일이 생기면 **항상 `gathering` 을
  먼저 잡는다.** 순서가 엇갈리면 데드락이 난다
- **거부한 사람이 즉시 다시 요청할 수 있다.** 거부는 행을 지우므로(`API.md` §6.3)
  유니크 제약이 풀린다. 주최자를 성가시게 할 수 있지만, 거부 이력을 남기면
  **실수로 거부한 사람을 영영 못 받는** 문제가 생겨 이쪽을 택했다

## 재검토 조건

- **한 모임의 참여자가 수백 명 규모가 될 때** — 잠금 대기가 실제로 보이기 시작하면
  비정규화 카운터를 다시 본다. 그때는 갱신 경로를 트리거나 단일 서비스 메서드로
  강제해 빠뜨릴 수 없게 만드는 것이 전제다
- **애플리케이션 인스턴스가 둘 이상이 될 때** — 지금은 단일 VM(`ADR-006`)이라
  DB 잠금 하나로 충분하다. 인스턴스가 늘어도 DB 가 하나면 이 설계는 그대로 유효하다.
  **DB 를 나누게 되면 그때 다시 본다**
