# ADR-016 · Redis를 도입하되, 용도를 다시 정한다

**상태** 확정 · **관련** `ADR-012`(Redis 용도 대체), `DOMAIN_DB_DESIGN_V2.md` §6,
`REQUIREMENTS.md` §4.1·§8.3·§10·§11

## 맥락

`ADR-012`는 이미 Redis를 **자체 호스팅 대상으로 확정**해뒀다 —
*"풋프린트가 작다(~0.3GB). presence·분산락."* 그런데 그 뒤로 두 가지가 바뀌면서
**거기 적힌 용도가 둘 다 사라졌다.**

1. **분산 락을 쓰지 않기로 정했다.** `DOMAIN_DB_DESIGN_V2.md` §6이 모든 동시성
   지점(참가 중복, 명단 마감 경합, 확정 더블클릭 등)을 DB 유니크 제약 + 조건부
   갱신으로 막도록 설계했다.
2. **presence(접속자 목록)가 필요 없어졌다.** `DOMAIN_DB_DESIGN_V2.md`가 채팅
   범위를 "이의제기 당사자 1:1 텍스트"로 좁혔다. 상시 접속 상태를 들고 있을
   이유가 없다.

즉 Redis는 도입 대상으로 확정돼 있는데 **쓸 자리가 비어 있는 상태**다. 그대로
두면 "인프라는 깔았는데 쓰는 데가 없다"가 된다.

## 결정

**Redis를 도입한다. 용도는 아래 네 가지로 한정하고, 분산 락에는 쓰지 않는다.**

| 용도 | 왜 Redis인가 | 근거 |
|---|---|---|
| 모임 비밀번호 시도 횟수 제한 | 시도 카운터는 **TTL이 본질**이다. DB로 하면 만료 행을 청소하는 배치가 따로 필요하다 | `REQUIREMENTS.md` §4.1 |
| 외부 유료 API(OCR·AI) 호출량 제한 | 사용자·모임 단위 쿼터. 비용이 나가는 쪽이라 실시간 차단이 필요하다 | `REQUIREMENTS.md` §11 MVP |
| 탈퇴·로그아웃 토큰 무효화 목록 | 보관 기간이 JWT 만료 시각까지라 TTL과 정확히 맞는다 | §근거 참조 |
| 알림 미읽음 수 캐시 | 화면마다 조회되는데 값은 자주 안 바뀐다 | `REQUIREMENTS.md` §10 |

**분산 락에는 쓰지 않는다.** `DOMAIN_DB_DESIGN_V2.md` §6의 설계를 그대로
유지한다 — Redis가 생겼다는 이유로 이미 검증된 동시성 설계를 갈아엎지 않는다.

## 근거

### 카카오 로그인을 쓴다고 세션 관리가 사라지는 게 아니다

카카오가 대신해 주는 것은 **로그인 순간의 신원 확인뿐**이다. 그 뒤 발급하는
`jeongsan_token`은 우리 서버가 직접 서명한 JWT이고(`ARCHITECTURE.md` §4.1),
만료·무효화 책임은 전부 우리에게 있다. 카카오는 우리 쪽 계정 탈퇴를 알지 못한다.

구체적으로 지금 벌어지는 일이 하나 있다.

- `REQUIREMENTS.md` §8.3은 **탈퇴 시 로그인 정보를 삭제 또는 익명화**한다고
  정했다. 그런데 이미 발급된 JWT는 그대로 유효하다 — 서버가 그 토큰을 거부할
  수단이 지금 없다. 쿠키를 탈취당한 경우도 마찬가지로, 만료(문서 14일 /
  구현 30일, `API.md` §2.3에 미결로 남아 있다)까지 막을 방법이 없다.

> **강퇴(`GroupBan`)는 여기 해당하지 않는다.** 강퇴되면 `group_members` 행이
> 사라지므로 모임 API의 **권한 검사** 단계에서 막힌다. 토큰 무효화까지 갈
> 문제가 아니다.

### "시도 제한 없음"은 미룬 것이지 필요 없다고 정한 게 아니다

`REQUIREMENTS.md` §4.1은 *"MVP에서는 CAPTCHA나 장기 계정 잠금 같은 고급 방어는
도입하지 않는다"*고 적었다. 그런데 v2에서 **검색 → 비밀번호 입력**이 정식 가입
경로가 됐다. 공격자가 모임을 찾아 비밀번호를 반복 시도하는 것을 막는 장치가
현재 하나도 없다. CAPTCHA 없이 넣을 수 있는 최소 방어가 시도 횟수 제한이다.

### OCR·AI가 MVP로 들어오면서 "돈이 나가는 호출"이 생겼다

`REQUIREMENTS.md` §11이 영수증 OCR과 AI 주류 분류를 MVP에 넣었다. 이건 호출할
때마다 외부에 과금되는 API다. 사용자당·모임당 쿼터가 없으면 한 사람이 영수증을
반복 업로드하는 것만으로 비용이 샌다. **`ADR-012`를 쓸 때는 존재하지 않던
요구사항이다.**

## 대가

- **운영 대상이 하나 늘어난다** — `ADR-012` 추정 기준 ~0.3GB. 12GB 예산에서
  가장 싼 축이지만 공짜는 아니고, 감시 대상도 하나 는다.
- **Redis가 죽었을 때 무엇을 같이 막을지 정해야 한다.** 기본값은 **통과
  (fail-open)** 로 둔다 — 캐시나 시도 제한 때문에 정산 자체가 멈추면 안 된다.
  단 **외부 유료 API 쿼터만 차단(fail-closed)** 으로 한다. 비용이 나가는 쪽은
  모르고 통과시키는 게 더 나쁘다.
- 미읽음 수 캐시는 무효화 타이밍을 틀리면 사용자 눈에 바로 보이는 버그가 된다.
  알림을 넣는 트랜잭션에서 같이 지우는 방식으로 시작한다.

## 재검토 조건

- Redis에 위 네 가지 외의 상태를 얹고 싶어질 때 → **`DOMAIN_DB_DESIGN_V2.md`
  §6(분산 락 안 씀)과 충돌하는지 먼저 확인한다.** 충돌하면 ADR을 새로 쓴다
- Redis 장애가 실제로 정산 기능을 멈추게 한 사례가 나오면 → fail-open/closed
  정책을 다시 본다
- 단일 인스턴스 메모리가 부족해지면 → `ADR-012`의 오프로드 원칙에 따라 관리형
  Redis 전환을 검토한다
