# 2026-10-04 — L2 이름 확인 (실명 + 카카오 닉네임)

웹·Android·iOS 세 플랫폼에 L2 이름 확인 화면을 넣었다(목데이터). 서버가 받쳐야 할 것을 적는다.

## FC-013 첫 로그인 실명 입력 — `needsName`, 실명 저장 API, 닉네임은 따로

- **상태:** 반영됨 (2026-10-04, `feat/user-real-name`: API v4 §2.1·§2.2-a, DOMAIN §4.1, REQUIREMENTS §3.3, changelog 015, UserService·UserController·AuthController)
  - 실명 등록·내 정보 계약을 구현했다. 참여자 이름 조인·타임라인 문구는 해당 API의 후속 구현에서 적용한다.
  - 아래 오타 정정·개인정보처리방침 결정은 이번 구현에 포함하지 않는다.
- **바뀐 흐름:**
  - **L2** — 첫 로그인 뒤 H1로 가기 전에 한 번 **실명을 성까지** 받는다. 안내 문구
    "실명을 정확하게 성까지 적어주세요! 그래야 총무가 헷갈리지 않아요!". 칸은 비어 있다(카카오 닉네임을 채우지 않는다).
  - **왜 실명인가** — 총무가 [받은 돈 확인]을 누를 때 은행 앱의 **입금자명**과 참여자를 맞춰 봐야 한다.
    카카오 닉네임(`🌸봄이🌸`)으로는 누가 보냈는지 알 수 없다.
  - **P1(링크로 처음 들어온 사람)** — 화면을 하나 더 거치지 않게 P1 안에 같은 실명 칸을 둔다.
    [참여하고 응답 완료] 한 번에 **실명 저장 → 참여** 순서로 처리한다. 그래서 타임라인 첫 줄이 실명으로 나간다.
  - 규칙: 앞뒤 공백을 뗀 뒤 **2~10자**, 글자 수는 **유니코드 코드포인트** 기준(이모지 🍺 하나 = 1자).
    형식(한글 몇 자 등)은 검사하지 않는다 — 외국인·복성·영문 이름을 막지 않기 위해서다.
    문구: 빈 값 `이름을 넣어주세요`, 1자 `성까지 적어주세요`, 초과 `이름은 10자까지예요`.
  - **한 번 정한 실명은 바뀌지 않는다.** 카카오 닉네임이 바뀌어도 따라가지 않는다.
  - **표시** — 목록(참여자 줄·R4 관리 시트·R3 금액 목록)은 `김동규(동규짱)`, 문장(타임라인·알림·배너)은 `김동규`만.
- **백엔드 영향:**
  - **DB `users`** — 두 값을 따로 둔다.
    - `display_name` — **실명.** 첫 로그인 UPSERT 때 **NULL**로 둔다. NULL = 아직 안 받음. 별도 플래그 컬럼은 필요 없다.
      한 번 채워지면 바꾸는 API를 두지 않는다.
    - `kakao_nickname`(이름은 백엔드가 정한다) — 카카오에서 받은 닉네임. 로그인할 때마다 갱신해도 된다
      (실명과 달리 화면에서 보조 표시일 뿐이다). `DOMAIN_DB_DESIGN_V2` §4.1의 "`display_name` = 카카오 닉네임 기본값"은
      이 결정으로 바뀐다.
  - **`GET /auth/me`** — 응답 모양.
    ```json
    { "id": 12, "displayName": null, "nickname": "🌸봄이🌸", "needsName": true, ... }
    ```
    - `needsName = display_name IS NULL`
    - `API.md` §2.1의 미정 사항("최초 로그인 안내를 `/auth/me`에 얹을지 리다이렉트 쿼리로 붙일지")을
      **`/auth/me`에 얹는 쪽**으로 프론트가 붙였다. 새로고침해도 다시 알 수 있어서다.
  - **새 API** — `PUT /api/v1/users/me/display-name` `{ "displayName": "김동규" }`
    - 서버도 같은 규칙으로 검증한다(trim, 2~10 코드포인트). 어기면 400 + 위 문구.
    - **이미 값이 있으면 409**(한 번만 정한다). 같은 값으로 다시 부르면 200(재시도 멱등).
    - 성공하면 갱신된 `me`를 돌려준다.
  - **참여자 응답** — 참여자마다 `displayName`(실명)과 `nickname`을 같이 내려준다. `participants.name`은 두지 않고
    `users`를 조인한다(DOMAIN §4.1 그대로). 목록에 `실명(닉네임)`을 붙이는 건 프론트가 한다.
  - **P1 참여** — 프론트는 실명 저장 → 참여(FC-009) 두 요청을 차례로 보낸다. 실명 저장이 실패하면 참여를
    보내지 않는다. 한 요청으로 합칠 필요는 없다(실명은 사용자 단위라 정산방 트랜잭션과 무관).
  - **타임라인** — 시스템 줄 문구("○○님이 들어왔어요")는 만들 때의 이름으로 굳는다(본문 저장).
  - **알림 문구** — 이름 자리에 실명만 쓴다(닉네임을 붙이지 않는다).
- **기존 문서와 충돌:**
  - `API.md` §2.2 — `/auth/me`가 `nickname`만 돌려주고 "카카오에서 닉네임을 바꾸면 바로 반영된다"고 적혀 있다.
    v3에선 화면의 주 이름이 실명(`display_name`)이고 닉네임은 보조다.
  - `API.md` §2.1 — `firstLogin`을 어디에 둘지 미정. 위처럼 `needsName`으로 대신한다.
  - `DOMAIN_DB_DESIGN_V2.md` §4.1 — `display_name`을 "카카오 닉네임 기본값, 한 번 확인·수정"이라 적었다. 실명·닉네임 두 칸으로 바뀐다.
  - `REQUIREMENTS.md` 참여자 절 — "표시 이름은 카카오 닉네임을 기본값으로 한 번 확인한다" → "실명을 한 번 받는다".
- **결정 필요 (남은 것):**
  1. **오타가 나면?** 지금 결정대로면 영영 못 고친다. 추천: 화면엔 "바꿀 수 없어요"로 두고, 고칠 길은
     **진행 중인 정산방이 없을 때만** 내 정보에서 열기(나중 작업). 정산 도중엔 이름이 안 바뀌어 입금 확인이 꼬이지 않는다.
  2. **개인정보처리방침** — 수집 항목에 "이름(실명)"을 넣어야 한다. 예금주명을 이미 받고 있어 새 성격의 데이터는
     아니지만 문구는 추가해야 한다. 카카오에서 실명을 받아오려면 비즈앱 심사가 필요해 직접 입력받는다.
