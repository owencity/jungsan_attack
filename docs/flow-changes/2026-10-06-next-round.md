## FC-015 총무 = 받는 사람 — 다음 차를 다른 사람이 계산하면 새 술자리

- **상태:** 열림 (CTO 결정 2026-10-06)
- **바뀐 흐름:**
  - 현실의 총무는 대부분 모든 차수의 결제자다. 1차 총무가 3차에서 빠지고 4차를 다른 사람(B)이 계산했다면,
    4차는 **B가 총무인 새 술자리**로 완전히 나눈다. 1차 총무는 4차 계산을 신경 쓰지 않는다.
  - 새 술자리에는 사람이 바뀔 수 있다 — 참여자를 옮기지 않고 새 링크로 다시 들어온다.
  - 쉽게 만들 수 있어야 한다 — R1(참여자)의 **[다음 차는 내가 계산했어요]** → 설명 → [새 술자리 만들기] →
    B가 총무인 새 술자리의 1차 입력(R2)으로 바로 간다. 제목은 `{원래 제목} 다음 차`.
  - 같은 자리에서 카드가 안 돼 다른 사람이 대신 낸 **드문 경우**를 위해 차수별 결제자 기능은 남긴다.
    다만 R2에서 기본으로 접어 둔다(낸 사람 = 총무).
- **백엔드 영향:**
  1. **`POST /api/v1/gatherings`가 제목을 선택적으로 받는다** — `{ "title": "9/28 술자리 다음 차" }`(없거나 빈 값이면
     지금처럼 `M/d 술자리`). 규칙은 FC-014 §4 PATCH와 같다(1~20자). 만들고 바로 PATCH하는 두 번 호출을 피하려는 것이다.
     권한은 로그인한 누구나(지금과 같다) — 원래 술자리의 참여자인지 확인하지 **않는다**(두 술자리는 연결되지 않으므로).
  2. **두 술자리를 잇는 데이터는 두지 않는다**(부모 술자리 id 같은 컬럼 없음). 정산·송금·타임라인·알림이 모두 별개다.
  3. 계산 엔진·스키마 변경 없음 — 차수별 결제자(`payer_participant_id`)는 그대로 지원한다.
- **기존 문서와 충돌:**
  - `REQUIREMENTS.md`의 총무·결제자 설명 — "차수마다 결제자가 다를 수 있다"가 주된 흐름처럼 읽힌다. **기본은
    총무가 모든 차수를 내고, 다른 사람이 다음 차를 계산하면 새 술자리**로 고쳐야 한다(결제자 대신 결제는 예외로 남김).
- **반영할 곳:** `API.md`(술자리 생성 본문), `REQUIREMENTS.md`(총무 정의·결제자 예외)
