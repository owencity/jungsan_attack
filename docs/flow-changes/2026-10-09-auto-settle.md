# 2026-10-09 — 인원이 다 응답하면 자동으로 계산한다

## FC-020 총무 인원 입력 · 전원 응답 시 자동 정산 · 입금 요청

- **상태:** 열림 (API v8·018/028·Java/Kotlin 구현 및 실제 MySQL 20건 검증, 인원 밖 결제자 예외·운영 연결 검토 후속)

서버 구현 계약은 [AUTO_SETTLEMENT.md](../AUTO_SETTLEMENT.md)다. 인원 밖 결제자는 REMOVE_PAYER로 자동 확정을 보류한다.
해당 예외와 Core 실패 시 OPEN/응답 보존 규칙은 출시 PR의 확인 사항이다. 나머지 인원 선택·초과 알림·제외·자동 확정은 구현했다.
- **바뀐 흐름:** 총무가 [정산하기]를 누르지 않는다. 총무가 **인원수**를 넣어 두면, 그 수만큼 사람이 들어와
  모든 차수에 응답한 순간 **서버가 자동으로 정산**한다. 총무는 계산된 결과를 보고 단톡방에 입금 요청만 보낸다.

  ```text
  총무: [+ 새 술자리] → R2 1차 금액 + 인원(나 포함 N명) → [저장] → [링크 공유]
  참여자: 링크 → P1 응답 → … (N명째 응답) → 서버 자동 정산 → 각자 알림 "○○님께 얼마 보내주세요"
  총무: 알림 "계산이 끝났어요" → R1 [입금 요청 보내기] → 카톡 공유(사람별 금액 + 계좌)
  ```

  **CTO 결정(2026-10-09):**
  1. 인원은 총무가 처음에 넣는다(총무 포함 N명). 들어온 사람이 모두 응답하고 그 수가 N명이 되면 확정한다
  2. 끝까지 안 들어오는 사람이 있으면 총무가 **[지금 계산하기]**로 마무리한다(지금의 수동 정산을 예비로 남김).
     응답 없는 사람은 지금처럼 전 차수 참석·알코올(AUTO)
  3. 자동 계산은 **바로 확정 + 알림**. 총무 확인 단계 없음. 틀렸으면 아무도 보내기 전까지 되돌리기(기존 기능)
  4. 알림은 출시 때 **앱 안 알림 + 단톡 공유 버튼**. 푸시(FCM·APNs)는 출시 뒤

- **백엔드 영향:**

  **① 정산 단위에 인원수**
  - `settlement_units.headcount` INT NULL — 총무 포함 인원. NULL 이면 자동 정산을 하지 않는다(옛 술자리·인원 미입력)
  - 받기: `POST /gatherings` 본문에 `headcount?`, `POST /gatherings/{gid}/settlement-units` 본문에 `headcount?`
  - 바꾸기: `PUT U/headcount` `{headcount}` — 총무·OPEN. 범위 2~50. 바꾼 뒤 아래 ③ 판정을 한 번 돈다
  - 응답: `settlementUnits[].headcount` 추가

  **② 자동 정산 조건** (단위 하나에 대해, 모두 참)
  - `status = OPEN`, `headcount != null`, 차수 1개 이상
  - 그 단위 명단(ACTIVE) 인원 ≥ `headcount` — 더 들어온 건 막지 않는다
  - 명단 모두가 그 단위의 모든 차수에 응답(빈칸 없음)

  **③ 언제 판정하나** — 응답 칸이 채워지거나 인원이 바뀌는 쓰기 뒤에, **같은 트랜잭션 안에서**
  - `POST /join/{token}`(참여+응답), `PUT U/responses/me`, `PUT U/participants/{pid}/responses`(대리 응답), `PUT U/headcount`
  - 차수 추가는 새 칸이 비므로 판정할 필요 없다. 차수 수정·삭제는 판정한다(삭제로 빈칸이 사라질 수 있다)
  - `DELETE U/settlement`(되돌리기) 뒤에는 판정하지 않는다 — 되돌린 직후 다시 정산되면 고칠 틈이 없다.
    되돌린 뒤 응답이 바뀌면 그때 다시 판정한다
  - 동시에 두 사람이 마지막 응답을 넣어도 한 번만 정산되게 단위 행을 잠근다(`SELECT … FOR UPDATE`)

  **④ 정산 자체** — 지금 `POST U/settlement`와 같은 Core 계산·스냅샷·송금 생성. 입력이 서버 안에서 바로
  읽히므로 `inputRevision`·`inputHash` 비교는 필요 없다. 수동 `POST U/settlement`는 그대로 둔다([지금 계산하기])

  **⑤ 알림·타임라인**
  - 송금하는 사람마다 기존 `SETTLED`(누르면 P3)
  - **새 종류 `SETTLED_HOST`** — 총무에게. 문구 "계산이 끝났어요. 단톡방에 입금 요청을 보내주세요", 누르면 R1
  - 타임라인 SYSTEM: 자동이면 "모두 응답해서 자동으로 계산했어요", 수동이면 지금 문구 그대로

### 추가 결정(2026-10-09 같은 날) — 인원보다 더 들어오면

인원으로 **막지 않고 알려만 준다.** 넘는 사람이 생기면 총무가 확인한다.

- **인원 안·밖** — 그 단위 명단을 **들어온 순서**(단위에 들어간 시각, 같으면 participant id)로 세워 앞에서부터 `headcount`명이
  인원 안, 나머지는 인원 밖. 총무는 늘 맨 앞
- **② 자동 정산 조건 고침** — "명단 모두가 응답"이 아니라 **"인원 안의 사람이 모두 응답"**(인원 밖 사람의 응답은 보지 않는다)
- **④ 자동 정산 때 인원 밖 사람은 뺀다** — 그 단위 명단에서 빼고(`DELETE U/participants/{pid}`와 같은 처리, 공유 참여자 행은 남김)
  응답도 계산에서 제외한다. 타임라인 SYSTEM "○○님은 인원(N명) 밖이라 이번 정산에서 빠졌어요".
  **수동 [지금 계산하기]는 빼지 않는다** — 총무가 명단을 보고 직접 누른 것이다(빼려면 [내보내기])
- **⑤ 알림 추가**
  - `HEADCOUNT_EXCEEDED` — 총무에게, 명단 수가 인원을 **넘는 순간 한 번**. "현재 6명이 참여했어요. 인원이 맞는지 확인해주세요",
    본문 "그대로면 5명으로 계산되고 마지막에 들어온 사람은 빠져요", 누르면 R1
  - `MEMBER_EXCLUDED` — 빠진 사람에게. "○○ 술자리에서 빠졌어요" · "인원(5명) 밖이라 이번 정산에서 빠졌어요", 누르면 내 술자리
- **[포함하기]** = `PUT U/headcount {들어온 사람 수}` — 새 API 없음. 바꾼 뒤 ③ 판정
- 인원이 다 차서 이미 정산된 뒤 들어오려는 사람은 지금처럼 "이미 정산된 술자리". 총무가 되돌리기 → 인원을 늘리면 함께 정산
- **프론트:** 총무 배너 "현재 6명이 참여했어요 · 인원(5명)이 맞는지 확인해주세요" + 보조 "그대로면 5명으로 계산되고 ○○님은 빠져요"
  + [6명 모두 포함하기]. 인원 밖 사람은 "인원이 다 찼어요 · 총무가 포함하면 함께 정산돼요". 웹 2425290 · 앱 34d1228

- **기존 문서와 충돌:** `REQUIREMENTS.md`의 "정산하기는 총무가 누른다" — 이제 기본은 자동이고 수동은 예비.
  `SCREENS.md` §3.1·§4.1·R2·R3(이 PR에서 고침)
- **프론트:** R2에 인원 [−] N [+](총무만, 정산 전). R1에 "5명 중 3명 응답 · 다 모이면 자동으로 계산돼요".
  총무 배너는 정산 뒤 "계산 끝! 단톡방에 입금 요청을 보내주세요" + [입금 요청 보내기](사람별 금액·계좌 공유 문구).
  R3 버튼 이름은 [지금 계산하기]. 서버가 붙기 전까지 목데이터 스토어가 같은 규칙으로 자동 정산한다
