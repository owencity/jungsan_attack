# flow-changes — 프론트 흐름이 바뀌어 백엔드가 알아야 하는 것

> **누가 쓰나:** 프론트(웹·Android·iOS)를 만드는 Claude Code. 흐름이 바뀔 때마다 쓴다.
> **누가 읽나:** 백엔드 시니어(Codex)와 CTO. **백엔드 작업 시작 전에 최신 원격 main의 목록과
> 상태가 `열림`인 모든 항목 본문을 읽는다.** 작업 브랜치·미병합 문서 PR의 추가 FC도 비교한다.

프론트는 목데이터로 먼저 화면을 만들고, 사용해 보며 흐름을 계속 고친다. 그 사이 서버가 받쳐야 할
데이터·상태·API가 조금씩 달라지는데, 그 변화가 `SCREENS.md` 화면 설명 속에만 묻혀 있으면 백엔드는
무엇이 계약 변경인지 알기 어렵다. 이 폴더는 **"그래서 서버는 무엇을 해야 하나"만** 모은다.

## 언제 쓰나

**프론트는 보고서를 쓰기 전에 FC부터 작성하고, 보고에 FC 번호를 붙인다.** 채팅 보고에만 서버 변경을
남기면 백엔드가 찾아낼 수 없다. 백엔드가 보고·연결 시험에서 누락을 발견하면 FC 초안으로 드러내고
제안과 CTO 확정을 구분한다. 이 규칙은 상시 자동 감시가 설정됐다는 뜻이 아니다.

프론트 작업 중 아래 중 하나라도 바뀌면 항목을 쓴다.

- 서버가 주거나 받아야 하는 **데이터 모양**(새 필드, 응답 구조, 목록에 필요한 요약)
- **상태 전이**·권한(누가 언제 무엇을 바꿀 수 있나)
- **알림** 이벤트·대상·문구·누르면 갈 곳
- 기존 백엔드 문서(`REQUIREMENTS`·`DOMAIN_DB_DESIGN_V2`·`API`·`CALC_RULES_V2`)와 **어긋나는** 프론트 동작

화면 배치·문구·애니메이션처럼 서버와 무관한 변경은 쓰지 않는다. 다만 "백엔드는 바뀔 것 없음"을
분명히 해 두는 게 헷갈림을 줄이면 `프론트만`으로 한 줄 남긴다.

## 항목 형식

파일 하나에 같은 날·같은 작업의 항목을 모은다: `YYYY-MM-DD-주제.md`. 항목 번호(`FC-001`)는 폴더 전체에서
이어서 매긴다.

```markdown
## FC-000 제목

- **상태:** 열림 | 결정 필요 | 반영됨(문서·PR) | 프론트만
- **바뀐 흐름:** 사용자 입장에서 무엇이 달라졌나 (화면 ID — SCREENS.md 기준)
- **백엔드 영향:** API · DB · 상태 전이 · 알림 중 무엇이 어떻게
- **기존 문서와 충돌:** 있으면 문서·절을 적는다
- **결정 필요:** CTO가 정할 것과 선택지·추천 (없으면 생략)
- **반영할 곳:** 어느 문서를 고쳐야 닫히나
- **백엔드 반영·근거:** 미반영 | 일부 반영 | 반영됨 · PR/파일 · 실행한 검증 · 남은 범위
```

**상태 규칙**
- `결정 필요` — CTO 결정 전. 백엔드는 이 항목을 근거로 구현하지 않는다.
- `열림` — 결정됐고 백엔드 문서·코드 반영을 기다린다. **모두 읽고 처리 범위를 기록할 대상.**
  일부 구현·계약만 반영·검증 후속·보류가 남으면 열림을 유지하고 남은 범위를 적는다.
- `반영됨` — 해당 FC가 요구한 문서·코드·검증을 완료했다. **같은 PR에서 본문과 목록 상태를 함께 닫고**
  아래 반영 열에 PR·파일·검증 근거를 적는다. 문서만 쓰고 기능 구현을 완료로 처리하지 않는다.
- `프론트만` — 서버는 바뀔 것 없음을 확인해 둔 것.

백엔드 PR에는 **문서 기준 commit / 읽은 열린 FC 번호 / 이번 반영 / 관련 후속·보류 이유**를 남긴다.
현재 작업과 무관한 FC까지 한 PR에 구현하지 않는다. `반영됨`은 구현·검증의 상태이며 PR 병합·운영
적용과는 별개다. 병합 대기·운영 미검증을 함께 표시해서 코드 작성과 배포를 혼동하지 않는다.

아래 초기 반영 열은 2026-10-09의 main 목록과 PR #18·#20의 자체 검증 기록을 구분해 적었다.
기존 `열림`은 임의로 닫지 않았다. 후속 작업에서 실제 계약·검증을 대조해 남은 범위를 갱신한다.
