공유 링크가 안고 있는 두 문제

429 임계값과 OG 응답 — 왜 이 URL 하나가 특별한가
받은 질문

“429 임계값은 무슨 소리일까”

“OG 응답은 무슨 소리일까?”

두 질문은 우연히 같은 URL 에 대한 것이다 — GET /g/{token}

0같은 URL 이 두 방향으로 특별하다

공유 링크는 이 앱에서 유일하게 규칙이 다른 주소다.

https://jungsan.devkdk.com/g/k3f9dq2
                             └─ 이 짧은 문자열이 전부다

다른 모든 API 는 로그인 토큰이 있어야 응답한다. 이 URL 만 문자열 자체가 열쇠다. 링크를 받은 사람이 아직 로그인하지 않았어도 모임 이름을 보여줘야 하기 때문이다.

그 성질에서 두 가지가 따라 나온다.

질문무엇을 묻는 것인가왜 이 URL 만 문제인가
4 429 임계값 열쇠가 짧은 문자열이라 맞춰서 들어올 수 있다. 몇 번까지 시도를 허용할지
5 OG 응답 단톡방에 붙이는 유일한 주소다. 붙였을 때 카드가 제대로 떠야 한다

1429 임계값

“이 주소를 1분에 몇 번까지 부르게 할지” 를 정하는 숫자다.

1.1무엇을 막는 것인가

k3f9dq2 는 7글자다. 공격자는 아무 문자열이나 만들어 계속 요청한다. 하나만 맞으면 남의 모임 정보가 그대로 나온다.

무작위 대입

“확률이 낮다” 는 시도 횟수를 제한할 때만 성립한다. 제한이 없으면 확률이 낮은 사건은 그냥 오래 걸리는 사건이 된다.

1.3그래서 두 가지가 필요하다 — 순서가 있다

무엇효과
근본 토큰을 길게 12자 · 62종 으로 늘리면 가능한 수가 6212 ≈ 3.2 × 1021. 초당 1,000회로 던져도 50% 도달에 5,100만 년
보조 429 제한 길이를 늘려도 대입 시도 자체를 볼 수 없다. 제한을 걸면 로그와 메트릭에 드러나고, 실수로 링크가 유출됐을 때 긁어가는 속도도 줄인다
길이가 먼저다

토큰이 짧으면 429 로 메울 수 없다. 분산해서 던지면 IP 당 제한은 그냥 IP 를 늘려서 피한다. 반대로 길이가 충분하면 429 는 없어도 뚫리지 않는다 — 그래도 두는 이유는 탐지와 비용 방어다.

1.4임계값 — 정상 사용자를 세어서 정한다

임계값은 감으로 정하는 숫자가 아니다. 정상 사용자가 이 주소를 몇 번 부르는지 세고, 거기에 여유를 준다.

로그인하고 돌아옴         1회   myParticipantId 확인
참여 버튼                0회   POST join 은 다른 경로

단톡방에 링크를 뿌리면 같은 회사 사무실의 20명이 같은 공인 IP(NAT) 로 들어온다. 카카오톡 인앱 브라우저는 미리보기까지 요청한다. 성공 응답까지 세면 뒤에 클릭한 사람이 429 를 받는다.

세야 하는 것은 요청 수가 아니라 틀린 요청 수다.

2OG 응답

단톡방에 링크를 붙였을 때 뜨는 카드를 만드는 태그다.

2.1그 카드는 누가 만드나

OG 는 Open Graph다. 카카오톡·슬랙·페이스북이 공통으로 읽는 규격이다. 링크를 붙이면 그 서비스의 크롤러가 URL 을 직접 GET 해서 HTML <head> 의 태그를 읽어 카드를 만든다.

카드가 만들어지는 경로

2.2지금 우리가 주고 있는 것 — 실측

배포된 index.html 을 직접 받아 확인했다.

// C:\dev\profile\index.html · jungsan.devkdk.com 실측
og: 태그          0개
<title>           김동규 | Backend Developer
<meta description> 백엔드 개발자 김동규의 개인 사이트 —
                   개발 철학과 프로젝트(ValkyrieFS, 24시간이모자라)를 소개합니다.
지금 단톡방에 링크를 붙이면

카드에 “김동규 | Backend Developer” 와 포트폴리오 소개문이 뜬다. 모임 이름도, 누가 초대했는지도 없다. 받은 사람은 무슨 링크인지 알 수 없어 누르지 않는다.

2.3왜 JS 로 고칠 수 없나 — 이게 핵심이다

“그럼 화면에서 document.title 을 바꾸면 되지 않나” 가 자연스러운 생각인데, 안 된다.

브라우저와 크롤러가 받는 것이 다르다

크롤러는 JS 를 실행하지 않는다. 우리 프론트는 CSR(Client-Side Rendering) SPA 라 모임 이름이 JS 가 API 를 부른 뒤에야 생긴다. 크롤러가 받는 HTML 에는 그 정보가 아직 없다.

그래서 프론트만으로는 해결할 수 없다

이건 화면 코드의 문제가 아니라 누가 그 HTML 을 만들어 주느냐의 문제다. 백엔드가 /g/{token} 을 HTML 로도 응답해야 한다.

2.4같은 URL 에 두 손님이 온다

// GET /g/k3f9dq2 를 받았을 때
크롤러  →  og: 태그가 든 HTML        모임 이름 · 주최자 · 아이콘
사람    →  정산어택 화면            참여 버튼까지

가르는 방법이 세 가지 있다. 어느 것을 쓸지는 ADR-007 에서 정한다.

방법장점 / 걸리는 점
A 공유 링크를
백엔드 도메인으로
api…/g/{t}		 + 가장 단순하다. 백엔드가 HTML 을 주고 사람은 프론트로 보낸다
− 단톡방에 뜨는 주소가 jungsan.devkdk.com 이 아니다
B Vercel rewrite
/g/* → 백엔드		 + 주소가 그대로 jungsan.devkdk.com/g/…
− 사람을 프론트로 되돌릴 때 같은 경로로 다시 들어와 순환한다. 경로를 하나 더 둬야 한다
C Cloudflare Worker
User-Agent 로 분기		 + 주소도 그대로고 순환도 없다. 크롤러만 백엔드로 보낸다
− jungsan.devkdk.com 을 오렌지 구름으로 되돌려야 Worker 가 붙는다
C 를 쓰면 방금 한 DNS 설정을 되돌려야 한다

jungsan.devkdk.com 을 DNS only(회색 구름) 으로 뒀다. Cloudflare Worker 는 프록시를 지나는 요청에만 붙으므로, C 를 고르면 오렌지 구름으로 바꾸고 SSL/TLS 를 Full (strict) 로 맞춰야 한다. 그 대가로 429 를 서버가 아니라 Cloudflare 가 걸 수 있다 — 질문 4 와 5 가 여기서 만난다.

3정해야 하는 것

두 질문의 답은 셋으로 좁혀진다.

항목제가 권하는 값왜
1 shareToken 길이 12자 · 62종
지금 7자 · 36종		 길이가 근본이고 비용이 0이다. 지금 바꾸면 나중에 마이그레이션이 없다
2 429 임계값 IP당 분당 30회
연속 404 5회 → 10분
성공은 세지 않음		 정상 사용이 2~3회다. 틀린 요청만 세면 NAT 뒤 20명이 안 막힌다
3 OG 방식 A (백엔드 도메인)
또는 C (Worker)		 A 는 지금 당장 되고, C 는 주소가 예쁘다. B 는 순환 때문에 경로가 지저분해진다
토큰 길이는 지금 정하는 게 싸다

아직 발급된 토큰이 하나도 없다. 스키마를 만들기 전에 정하면 컬럼 길이 하나로 끝난다. 운영 중에 바꾸면 이미 단톡방에 뿌려진 링크를 살려두면서 새 형식을 함께 받아야 한다.
