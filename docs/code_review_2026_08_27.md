## 한눈에 보기

결정론과 “실패는 반환값”이라는 계약을 강화한 것이다.

## 처리 흐름

```text
SettlementInput
      │
      ├─ effectiveRounds(): 술병 항목이 있으면 차수 술값을 재구성
      │
      ├─ Validator(CONFIRM): 형식 + 확정 가능 여부 검증
      │        └─ 오류가 있으면 Failure(errors)
      │
      ├─ 원부담 계산: Rational로 차수/기타 항목 몫 누적
      ├─ 대표결제자 선정: 면제 제외, 결제총액 내림차순, ID 오름차순
      ├─ 최종 금액: 나머지 참여자는 올림, 대표결제자는 잔액 부담
      └─ 송금 목록: 채권자와 채무자를 결정론적 greedy 방식으로 상계
```

## 상세 리뷰

### F1 · 차수와 기타 항목의 ID 중복 검증 누락

기존에는 참여자 ID만 중복 검사했다. 같은 `roundId`를 가진 차수가 둘이면
`AttendanceKey(participantId, roundId)` 조회 결과가 두 차수에 같이 적용된다. 이 경우
총액 합계는 여전히 맞기 때문에 합계 불변식 테스트조차 문제를 발견하지 못한다.

현재는 다음 값을 모두 검사한다.

- 참여자 ID
- 차수 ID
- 기타 항목 ID
- 차수 순번(`seq`)

오류에는 가능한 경우 `participantId`, `roundId`, `extraId`를 넣어 사용자가 수정할
대상을 식별할 수 있게 했다.

### F2 · “예외를 던지지 않는다”는 계약의 빈틈

`Rational.ceilTo()`는 마지막에 `longValueExact()`를 호출한다. 입력 금액이 지나치게
크면 `ArithmeticException`이 발생할 수 있어 `SettlementOutcome.Failure`로 실패를
돌려준다는 엔진 계약과 충돌했다.

항목별 금액과 전체 합계에 1조 원 상한을 두어 계산 전에 차단했다. 이 상한은
오버플로 방지뿐 아니라 금액 입력 시 0을 여러 개 더 붙이는 실수도 조기에 잡는다.

단, `Rational.ceilTo(0)`처럼 개발자가 호출 계약을 어긴 경우의 `require()`는 유지한다.
사용자 입력 오류와 프로그래밍 오류를 같은 검증 실패로 위장하지 않기 위해서다.

### F3 · 면제자가 결제자인 경우의 회귀 테스트

면제자는 부담액이 0이고 모든 분모 및 대표결제자 후보에서 제외된다. 하지만 실제
결제자가 될 수는 있으므로, 자신이 선결제한 금액은 송금을 통해 전액 돌려받아야 한다.

추가된 테스트는 아래 세 조건을 함께 고정한다.

1. 면제자의 최종 부담액은 0원이다.
2. 면제자가 결제한 총액은 `paidTotal`에 남는다.
3. 면제자는 가장 많이 결제했더라도 대표결제자가 되지 않는다.

### F6 · 유효 차수는 한 번만 만든다

술병 상세가 있으면 `Round.alcohol` 대신 `병 수 × 단가` 합계를 사용한다. 검증과 계산이
각자 `effectiveRounds()`를 호출하면 현재는 같은 결과가 나오더라도 향후 변경 시 서로
다른 데이터를 볼 위험이 있다. 검증 진입점에서 한 번 계산해 하위 검증에 전달함으로써
“검증한 값을 계산한다”는 관계를 코드 구조로 드러냈다.

### F8 · 대표결제자의 금액은 나눗셈이 아니라 잔액이다

대표결제자를 제외한 참여자 금액만 단위별로 올림한 뒤 아래 식으로 대표결제자의
금액을 정한다.

```text
대표결제자 금액 = 전체 원금 - 나머지 참여자의 최종 금액 합계
```

이 구조 덕분에 별도 보정 없이도 최종 금액 합계가 항상 원금과 일치한다. 대표결제자도
먼저 나눈 뒤 차이를 보정하는 방식으로 바꾸면 핵심 불변식이 코드에서 흐려진다.

## 주석 운영 원칙

GitHub는 같은 브랜치의 소스에서 특정 주석만 숨기는 기능을 제공하지 않는다. 커밋한
주석은 GitHub 소스 화면에도 그대로 보인다. 이 프로젝트에서는 다음처럼 구분한다.

- **코드에 유지:** 불변식, 잘못 바꾸기 쉬운 이유, 외부 계약, 예외적인 도메인 규칙
- **문서로 이동:** 줄 단위 동작 설명, 문법 설명, 긴 학습 노트
- **로컬에서 접기:** IntelliJ의 코드 접기 기능으로 KDoc·주석을 접어 화면 밀도를 낮춤

주석 없는 별도 소스를 생성해 GitHub에 올리는 방식은 소스와 배포본이 달라지고 디버깅이
어려워 권장하지 않는다. 공개 저장소에 노출되면 안 되는 정보는 주석에도 절대 넣지 않는다.
