# 정산어택 — 개발 문서

이 폴더는 구현 에이전트(Claude Code)가 읽는 문서다.

## 읽는 순서

1. **`REQUIREMENTS.md`** — 새 제품 요구사항, 유비쿼터스 언어, 역할·권한, 상태 전이
2. **`ARCHITECTURE.md`** — 이 결정들이 실제로 어떤 모양으로 조립됐는지 한눈에 보는 개요.
   PR이 이 문서의 전략(§2)에서 벗어나거나 아직 v1인 지점(§8)을 몰래 바꾸는지부터 본다
3. **`SPEC.md`** — 기존 구현 기준 제품 명세. 새 요구사항과 충돌하는 절은 개정 예정
4. **`CALC_RULES_V2.md`** — 새 차수 총무별 수취·1원 올림 계산 규칙
5. **`DOMAIN_DB_DESIGN_V2.md`** — 새 도메인 경계·상태·논리 스키마·동시성 설계
6. **`CALC_RULES.md`** — Core v1의 과거 회귀 기준
7. **`API.md`** — 현재 엔드포인트·요청·응답·오류 코드 계약
8. **`ERD.md`** — 현재 Liquibase 스키마를 사람이 읽기 좋게 옮긴 문서
9. **`../design/mockup.html`** — 기존 화면 목업 (브라우저로 열어볼 것)

> [!IMPORTANT]
> `REQUIREMENTS.md`는 앞으로 만들 제품의 기준이고, 나머지 문서는 현재 구현 계약이다.
> 둘이 충돌하면 요구사항만 보고 코드를 먼저 고치지 않는다. 계산 규칙 → 도메인·DB
> 설계 → ADR → changelog → ERD → API 순서로 기술 설계를 갱신한 뒤 구현한다.

`API.md` 의 오류 코드는 `core/Validation.kt` 의 `ErrorCode` enum 을 그대로 쓴다.
**enum 을 고치면 `API.md` §1.4 도 같이 고친다** — 프론트가 그 문자열로 분기한다.

## 작업 시작 지시

> `docs/CALC_RULES_V2.md`를 읽고, 정산 계산 엔진을 Kotlin 순수 함수로 구현해줘.
> DB와 UI는 아직 만들지 마. §6의 테스트 케이스를 전부 Kotest로 작성하고
> 통과시켜줘. §3의 **유리수 요구**(`BigDecimal`도 금지)와 §7의 불변식 테스트,
> 체크리스트를 반드시 지켜줘.

이 단계가 끝나기 전에 화면을 만들지 않는다. 이 서비스의 난이도는 UI가 아니라 계산 규칙에 있다.

## 원칙

- `SPEC.md` §9 "만들지 않는 것"은 명세의 일부다. 거기 있는 걸 구현하면 범위 위반이다.
- 미리보기 계산 결과는 저장하지 않는다. 금액 확정 시에는 입금·분쟁의 기준이 되는
  송금 명세만 불변 스냅샷으로 저장한다(`DOMAIN_DB_DESIGN_V2.md`).
- 동일 수취인 원부담을 합친 뒤 소수 부분이 있을 때만 1원 단위로 올린다.
- 원부담 누적은 **정확한 유리수로만** 한다. `BigDecimal`은 랜덤 30,000건 중 210건(0.70%)에서 틀린 금액을 낸다(`CALC_RULES.md` §2.1).

## 참조 구현

`reference_impl.py` — 테스트 케이스의 기대값을 만든 Python 참조 구현.
Kotlin 구현 결과가 다르면 이 코드로 대조할 것. (제품 코드가 아니라 검증용이다)

**주의 두 가지.**

- **§4의 입력 검증이 하나도 구현돼 있지 않다.** 검증 로직은 참조 구현과 대조할 수 없으므로 전부 새로 작성해야 한다.
- import만 해도 T8~T11 결과를 표준출력으로 찍는다. 실행 스크립트를 겸하고 있어서다.
