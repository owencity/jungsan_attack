# ADR-023 — Python OCR 개발과 독립된 Spring 후보 추출 연결

- 상태: 최소 연결 구현 · Python 실서비스/ARM 실측과 배포는 후속
- 날짜: 2026-10-19

## 맥락

CTO가 Python 개발과 병행해 Spring 연결을 먼저 구현하도록 요청했다. Python PR #34의
57d1ee9는 바이너리 업로드와 schema v2 후보 응답을 제공한다. Python 브랜치의 ADR-021은
Caddy 결정 번호와 충돌하므로 이 연결 결정은 023으로 분리하고 병합 시 번호를 다시 확인한다.

## 결정

단위별 총무·OPEN 권한을 확인한 Spring API가 내부 RestClient로 사진을 전달하고 검증한 후보만
돌려준다. 사진·OCR 원문·후보는 저장하지 않으며 기존 차수 저장·정산과 분리한다. 사용자 입력으로
내부 주소나 키를 받지 않는다. HTTP/JDBC/JSON DTO는 공유 어댑터, 업무 권한·업로드 한도·횟수
정책은 Java/Kotlin 독립 구현 및 기대값 비교 대상이다. 계산 엔진·스키마·새 의존성은 변경하지 않는다.

설정 두 개가 모두 없으면 OCR만 닫고 부분·오류 설정은 기동 시 거절한다. 기동 중 설정 변경은
지원하지 않는다. JVM 안에서 요청 한 개·사용자당 60초 3회·최대 만 개 창으로 제한한다.
최대 8MiB 본문·256KiB 응답·연결 2초/읽기 45초를 사용하며 리다이렉트·자동 재시도·대기열은 없다.
외부 호출 동안 DB 트랜잭션을 유지하지 않고 반환 직전 권한을 다시 확인한다.
공통 multipart 해석은 resolve-lazily로 지연한다. 기존 multipart 공개 계약은 없으며 OCR 핸들러는
parts/parameter에 접근하지 않아 잘못된 multipart도 인증·매체 검사 전에 임시 파일을 만들지 않는다.
근거: [Boot 속성](https://docs.spring.io/spring-boot/appendix/application-properties/index.html).

## 근거

모델 완료까지 Spring 작업을 기다리는 방식과 독립 모의 서버 검증을 비교했다. 이미 존재하는
내부 계약에 맞춰 먼저 만들면 Python의 추론 시간·모델 설치와 독립적으로 인증·자원 한도·JSON
경계를 검증할 수 있다. 비동기 큐·Redis/Kafka 도입은 측정 근거가 없으므로 이번 작업에 넣지 않는다.
기존 ADR-016~018의 제안·재검토 상태를 이 연결만으로 확정하지 않는다.

## 대가

동기 호출 동안 요청 스레드가 점유되고 모델 CPU 작업은 클라이언트 시간 초과로 중단되지 않는다.
업로드의 바이트 수는 제한하지만 느린 전송의 전체 경과 시간은 여기서 보장하지 않는다.
프로세스 재시작 시 횟수는 초기화되고 다중 인스턴스는 한도를 공유하지 않는다. 추론 뒤 권한
재검사는 변경을 발견하는 읽기이며, 응답 직후 상태 변경까지 막는 잠금 보장은 아니다.
사진 속 이름은 후보 상품명에 포함될 수 있다. 명시 필드 제한이 사진 내용 익명화를 뜻하지 않는다.

## 재검토 조건

실제 OCR CPU/메모리·ARM 지연·동시 사용·시간 초과 비율과 실제 사진 정확도를 측정한 뒤 동기
시간 제한·인스턴스 수·큐 필요성을 결정한다. 외부 서비스명/다른 런타임을 쓰면 주소 허용 목록과
격리를 함께 검토한다. Python을 먼저 배포하고 내부 health/키/응답 계약을 확인한 뒤 Spring 환경
설정을 연결한다. 기본 compose와 운영 환경은 이번 구현으로 활성화하지 않는다.

## 확인한 프론트 변경

origin/main 3eb5254에서 열린 FC-005/009/010/011/014/015/020/021을 확인했다. FC-015의 단위별
권한을 적용하고 FC-020의 정산 상태를 OCR로 바꾸지 않는다. 나머지는 이 추출의 신규 요구가 아니며
기존 출시 후속을 유지한다. FC-012는 결정 필요, FC-023은 프론트 목표 인원 수정 후속으로 둔다.
