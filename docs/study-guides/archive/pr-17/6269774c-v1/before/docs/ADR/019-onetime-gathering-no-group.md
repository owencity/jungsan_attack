# ADR-019 · 술자리는 일회용이다 — 모임 계층을 걷어낸다

**상태** 확정 · **대체** `ADR-009`(지속 모임) · **관련** `REQUIREMENTS.md` v3,
`DOMAIN_DB_DESIGN_V2.md`, `ADR-015`, `ADR-016`, `ADR-017`

## 맥락

`ADR-009`는 이런 전제에서 출발했다 — *"지금까지 `Gathering`은 1회성이었다. 그런데
실제로는 같은 사람들이 반복해서 만난다."* 그래서 `Group`(지속 모임)을 `Gathering`
위에 얹었고, v2 요구사항은 그 위에 관리자·권한 이전·검색·비밀번호 가입·강퇴·차단·
보관까지 쌓았다.

프론트 흐름을 다시 점검하면서 이 구조가 **가장 흔한 사용 장면에 가장 큰 마찰**을 준다는
게 드러났다.

- 정산 하나를 하려면 모임부터 만들고(번개/주기 선택), 그 안에 술자리를 또 만들어야 했다.
- 총무가 링크를 보내기까지 화면 7개, 텍스트 입력 10개 이상.
- 공유 링크가 두 종류(`/gr/` 모임 초대, `/g/` 술자리 참여)라 잘못 보낼 위험이 컸다.
- 사용자가 알아야 할 용어가 21개였다.

그리고 결정적으로, **사람들은 지난 정산 기록을 찾지 않는다.** 같은 사람들과 반복해서
만나더라도 필요한 건 "지난번 멤버 불러오기" 정도이지, 모임이라는 영구 컨테이너가 아니다.
`ADR-009`의 관찰("반복해서 만난다")은 맞았지만 거기서 끌어낸 결론("지속 모임이 필요하다")이
틀렸다.

## 결정

**술자리(`Gathering`)를 최상위 애그리거트로 되돌리고, 일회용으로 만든다.**

1. `Group`·`GroupMember`와 모임 관련 기능 전부(관리자, 가입, 검색, 비밀번호, 강퇴·차단,
   보관)를 제거한다. 공유 링크는 술자리 링크 하나뿐이다.
2. 술자리는 **완료 7일 뒤 물리 삭제**한다. 30일간 활동이 없는 미완료 술자리도 삭제한다.
   완료된 술자리는 삭제 전까지 "완료" 뱃지로 명확히 구분해 보여준다.
3. 확정 관문을 [정산하기] 하나로 줄인다. 명단 마감·차수 확정 단계를 없앤다.
4. 미응답 칸은 정산 시점에 자동응답(참석·알코올)으로 채우고 본인과 총무에게 알린다.
5. 이의제기 절차(1:1 채팅, 협상, 오프라인 조율)를 [아직 안 들어왔어요] 버튼 하나로 대체한다.

## 근거

### 가장 흔한 경우를 가장 짧게

정산 서비스의 가치는 "빨리 끝난다"에 있다. 모임 계층은 반복 사용이라는 **드문 경우**를
위해 **모든 경우**에 비용을 물렸다. 일회용 구조에서 총무 흐름은
`[새 술자리] → 금액 → [링크 공유] → [정산하기] → 입금 확인`으로 줄어든다.

### 기록을 지우는 게 기능이다

v2 원칙 6은 "확정된 과거 기록을 지우지 않는다"였다. 그러나 보관하는 기록은 운영 부담
(개인정보·계좌번호 보관, 탈퇴 시 익명화, 삭제 요청 대응)만 늘리고 사용자 가치는 없었다.
7일 삭제는 **보관할 개인정보 자체를 줄이는** 설계다. 탈퇴 처리도 단순해진다 — 정산 FK를
지키려고 익명화할 필요가 없다.

### 한 사람이 전체를 막지 않는다

v2는 "전원 응답 전 확정 불가 + 총무 대리 응답 금지 + 무응답 자동 동의 금지"가 동시에
있어 탈출구가 없었다. 술자리에서 1~2명이 끝까지 응답하지 않는 것은 정산 앱의 가장 흔한
실패다. 자동응답은 멈추지 않게 하되, **본인에게 알리고 화면에 표시해 숨기지 않는다.**
잘못됐다면 아무도 송금하기 전에 총무가 되돌릴 수 있다.

## 대가

- **반복 멤버 편의가 사라진다.** 매번 링크를 새로 뿌려야 한다. 후속 기능으로
  "지난 술자리 멤버 불러오기"를 검토한다 — 모임 계층 없이 해결하는 방향으로.
- **지난 정산을 다시 볼 수 없다.** 7일 뒤에는 "지난달에 내가 얼마 냈더라"에 답할 수 없다.
  사용자 관찰에 근거해 감수한다.
- **이미 만든 것을 버린다.** `main`의 모임 생성·목록·상세 API(`GroupController`)와 스키마
  (`002`·`009`·`011`)를 제거해야 하고, 병합 전이던 모임 관리 기반(`012`~`014`,
  changeSet `018`~`022`)은 쓰지 않는다. 적용된 changelog는 수정하지 않고 새 changelog로
  테이블을 삭제한다.
- **자동응답은 틀릴 수 있다.** 술을 안 마신 사람이 응답을 안 해서 알코올로 계산될 수 있다.
  알림·화면 표시·되돌리기로 완화하지만, 되돌리기가 막힌 뒤(누군가 송금한 뒤)에는
  당사자끼리 조율해야 한다.
- **`ADR-016`(Redis)의 가장 강한 근거였던 "모임 비밀번호 시도 제한"이 사라진다.**
  `ADR-016`에서 남은 용도로 다시 판단한다.

## 재검토 조건

- 사용자가 "지난 정산을 다시 보고 싶다"를 반복해서 요구하면 → 보관 기간 연장 또는
  "내 정산 요약만 남기기"를 검토한다(전체 기록 보관이 아니라).
- 같은 멤버끼리 반복 사용이 대부분이라는 데이터가 나오면 → "멤버 불러오기"를 먼저
  만들고, 그래도 부족할 때만 모임 계층을 다시 본다(`ADR-009`는 기록으로 남아 있다).
- 자동응답으로 인한 금액 분쟁이 잦으면 → 기본값(참석·알코올)을 바꾸거나, 정산하기 전
  미응답자에게 한 번 더 알림을 보내는 단계를 검토한다.
