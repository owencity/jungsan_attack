# ADR-009 · `Group`을 `Gathering` 위에 얹는다 — 이름은 바꾸지 않는다

**상태** 확정 · **관련** `SPEC.md` §4, `report/flow.md`

## 맥락

지금까지 `Gathering`은 **1회성** 모임이었다("8월 팀 회식" 하나). 그런데 실제로는
같은 사람들이 반복해서 만난다 — 대학 친구 모임, 회사 동료 모임, 술자리 멤버.
매번 새 링크를 만들고 참여자를 처음부터 다시 모으는 건 반복 사용자에게 비효율적이다.

`report/flow.md`가 이 문제를 `Group`(영구 모임) → `Meeting`(각 회차)의 2단 구조로 정의했다.

## 결정

**`Group`을 새로 추가하고, `Gathering`은 그 아래 붙는 회차로 쓴다. `Gathering`이라는
이름 자체는 바꾸지 않는다.**

```
Group (신설)
  id, name                       // "신림팸"
  createdByUserId → User.id
  createdAt

GroupMember (신설)
  groupId, userId, role: OWNER | MEMBER
  joinedAt

Gathering (기존 — 이름 유지)
  ...기존 컬럼 전부 그대로...
  groupId → Group.id | null      // ← 추가되는 컬럼 하나
```

**`Gathering`을 `Meeting`으로 리네임하지 않는 이유** — `core` 모듈(계산 엔진 739줄 ·
테스트 741줄 · 46건), 프론트 `types.ts`와 12개 화면, API 계약 24개 엔드포인트가
전부 이 이름에 의존한다. 이름을 바꾸는 것은 **코드가 아니라 어휘만 바꾸는 작업**이고,
그 작업이 버그를 만들 확률만 있고 얻는 게 없다. `flow.md`의 `Meeting`이 하려는 일은
지금 `Gathering`이 이미 다 하고 있다 — 그 위에 `Group`이라는 컨테이너만 씌운다.

### `Group`은 참여를 자동화하지 않는다

**`Group`에 속해도 다음 `Gathering`에 자동으로 참여자로 등록되지 않는다.**
`SPEC.md` §2-b(모임 생성 시점을 강제하지 않는다)와 §5(로그인 후 확인 버튼을 눌러야
참여)의 원칙을 그대로 지킨다. `Group`은 **"누가 이 모임의 일원인가"를 기억하는
껍데기**일 뿐이다 — 매번 링크로 들어와 확인 버튼을 누르는 흐름은 바뀌지 않는다.

`Group`이 실제로 하는 일은 이것뿐이다.

- `Gathering` 생성 시 `Group`을 골라 묶으면, 그 `Group` 소속 목록에서 이전 `Gathering`을
  참고할 수 있다(예: 지난 모임 참여자 이름 자동완성 — 참여는 여전히 본인이 링크로)
- H0 화면에서 `Group`별로 묶어 볼 수 있다

## 근거

- **기존 계산 엔진·API·프론트를 하나도 건드리지 않고 얹는다.** `group_id`가
  `nullable`이라 `Group` 없이 만든 기존 1회성 `Gathering`도 그대로 유효하다
- **참여 흐름의 신뢰 모델이 안 깨진다.** `Group`이 참여를 자동화하면 "링크를 눌러
  본인이 확인해야 참여자로 등록된다"는 자기신고 신뢰(`SPEC.md` §5)가 무너진다

## 대가

- `Group` 목록·통계·활동 타임라인은 이 ADR의 범위가 아니다(`ADR-012`가 정하는
  구현 순서를 따른다). `SPEC.md` §9에 명시적으로 남긴다
- `Participant`(모임 내 좌석)와 `GroupMember`(모임 밖 소속)가 별도 테이블로 존재해
  "이 사람이 이 그룹 소속인가"와 "이 사람이 이번 회차에 참여했는가"를 항상 구분해서
  질의해야 한다 — 섞으면 §2-b 원칙이 깨진다

## 재검토 조건

- `Group` 안에서 `Gathering`을 자동 생성하거나 소속 전원을 자동 초대하는 기능이
  필요해질 때 — 그때는 이 ADR의 "자동화하지 않는다" 결정을 다시 본다

## 이후 갱신 — `Group` 가입 방식 (`API.md` §3-b)

이 ADR은 `Group`이 참여를 자동화하지 않는다는 것만 정하고 **어떻게 가입하는지는
비워뒀다.** `API.md` §3-b가 `Gathering`과 같은 `shareToken` 2단계 패턴
(`GET /gr/{token}` → `POST /gr/{token}/join`)으로 정했다 — 참여자가 이미
`/g/{token}` 흐름에 익숙해 새로 배울 게 없다. 다만 `Gathering`의 OG 최적화
(`ADR-007`)는 적용하지 않았다 — `Group`은 낯선 사람에게 카카오톡으로 뿌리는
게 아니라 이미 아는 사람끼리 쓰는 것이라 우선순위가 낮다.
