# 정산어택 — Core v2 계산 규칙

> **상태:** 제품 요구사항 반영 완료 · Core v2 구현 기준  
> **버전:** v2 · 2026-08-31  
> 기존 `CALC_RULES.md`는 현재 Core v1의 회귀 기준이다. Core v2 전환이 끝날 때까지
> 보존하고, 새 구현과 테스트는 이 문서를 따른다.

---

## 1. 범위

- 차수 개수에는 제한이 없다.
- 차수마다 총무가 정확히 한 명 존재한다.
- 차수 총무는 해당 차수의 유일한 결제자이자 수취인이다.
- 한 사용자가 여러 차수의 총무가 될 수 있다.
- 택시비·대리비 등 기타 항목은 MVP에서 계산하지 않는다.
- 서로 다른 총무 사이의 채권은 상계하지 않는다.
- 앱에서 실제 송금이나 입금 조회를 수행하지 않는다.

## 2. 입력

```kotlin
data class SettlementInput(
    val participants: List<Participant>,
    val rounds: List<Round>,
    val attendance: Map<AttendanceKey, Attendance>,
    val drinkItems: List<DrinkItem> = emptyList(),
)
```

### 2.1 참여 상태

모든 참여자는 모든 차수에 아래 상태 중 하나를 명시적으로 제출한다.

| 상태 | 의미 | 비주류 | 주류 | 분모 포함 |
|---|---|:---:|:---:|---|
| `ABSENT` | 불참 | X | X | 모든 분모 제외 |
| `EXEMPT` | 참석했지만 해당 차수 비용 면제 | X | X | 모든 분모 제외 |
| `SOBER` | 참석·논알코올 | O | X | 참석자 분모 |
| `DRANK` | 참석·알코올 | O | O | 참석자·음주자 분모 |

`ABSENT`와 `EXEMPT`는 모두 0원이지만 결과 근거가 다르므로 구분한다. 전역 면제
필드는 두지 않는다. 화면의 `모든 차수 면제`는 각 차수 응답을 `EXEMPT`로 설정하는
편의 기능이다.

### 2.2 차수와 술 항목

```kotlin
data class Round(
    val id: Long,
    val seq: Int,
    val label: String,
    val total: Long,
    val alcohol: Long,
    val payerId: Long,
)
```

`payerId`는 제품 용어의 차수 총무다. Core에서는 실제 결제자·수취인이라는 계산상
책임을 드러내기 위해 이름을 유지한다.

`DrinkItem`이 한 개라도 있는 차수는 직접 입력한 `alcohol`을 무시한다.

```text
술값 = Σ(병 수 × 병당 가격)
```

### 2.3 식별자와 순서

- 차수 `id`는 영구 식별자이며 재사용하지 않는다.
- `seq`는 화면 표시 순서다.
- 같은 술자리 안에서 `id`와 `seq`는 각각 중복될 수 없다.
- 응답과 술 항목은 `seq`가 아니라 `roundId`를 참조한다.

## 3. 계산

### 3.1 차수별 정확한 원부담

```text
비주류 금액 = 차수 총액 - 술값

비주류 1인 몫
= 비주류 금액 / (SOBER + DRANK 인원)

주류 1인 몫
= 술값 / DRANK 인원
```

| 상태 | 원부담 |
|---|---|
| `ABSENT` | 0 |
| `EXEMPT` | 0 |
| `SOBER` | 비주류 1인 몫 |
| `DRANK` | 비주류 1인 몫 + 주류 1인 몫 |

모든 중간값은 `Rational`로 계산한다. `Double`과 금액 누적용 `BigDecimal`은
사용하지 않는다.

### 3.2 수취인별 합산

동일한 총무가 담당한 모든 차수에서 한 참여자가 부담할 정확한 금액을 먼저 합친다.

```text
raw(P → M)
= 총무 M이 담당한 각 차수에서 참여자 P의 정확한 원부담 합계
```

예:

```text
민수의 1차 원부담 3,333.33원 ┐ 총무 철수
민수의 3차 원부담 6,666.67원 ┘

민수 → 철수 = 10,000원
```

차수마다 따로 올려 `3,334 + 6,667 = 10,001원`으로 만들지 않는다.

### 3.3 1원 단위 올림

10원·100원 선택값은 없다. 정확한 금액에 소수 부분이 있을 때만 다음 정수 원으로
올린다.

```text
3,333.00원 → 3,333원
3,333.01원 → 3,334원
3,333.99원 → 3,334원
```

정수 변환 지점은 `Rational.ceilTo(1)` 하나다.

### 3.4 잔액 조정자

올림 후에도 수취인이 결제한 원금과 정확히 일치하도록 수취인마다 한 명을
`잔액 조정자`로 둔다.

선정 순서:

1. 수취인 본인의 `raw`가 0보다 크면 수취인 본인
2. 수취인 본인의 `raw`가 0이면 `raw`가 가장 큰 비면제 부담자
3. 동률이면 참여자 ID가 작은 사람

조정자를 제외한 참여자의 금액을 먼저 1원 단위 올림한다.

```text
조정자 금액
= 수취인의 결제 총액 - 나머지 참여자의 정수 금액 합계
```

일반적으로 차수 총무가 조정자가 되어 올림 차이만큼 조금 덜 부담한다. 차수 총무가
담당 차수에서 모두 `ABSENT` 또는 `EXEMPT`라면 다른 비면제 부담자가 조정자가 된다.

조정자 금액이 음수면 `NEGATIVE_ADJUSTED_AMOUNT` 실패를 반환한다. 1원보다 작은
단위는 없으므로 단위 강등이나 재계산은 하지 않는다.

### 3.5 최종 부담액과 송금

```text
참여자 P의 최종 부담액
= 모든 수취인 그룹에서 P에게 배정된 정수 금액의 합
```

- 참여자와 수취인이 같으면 송금을 만들지 않는다.
- 배정 금액이 0이면 송금을 만들지 않는다.
- 같은 `송금자 → 수취인` 조합은 최대 한 건이다.
- 서로 다른 수취인의 채권은 상계하지 않는다.
- 수취인 ID, 송금자 ID 오름차순으로 정렬한다.

```text
철수 → 영희 10,000원
영희 → 철수 7,000원

결과도 두 건 그대로다. 3,000원 한 건으로 상계하지 않는다.
```

## 5. 검증

### 저장과 확정 공통

- 참여자·차수 ID 중복 금지
- 차수 `seq` 중복 금지
- 차수 총액은 1원 이상
- 술값은 0원 이상이고 차수 총액 이하
- 차수 총무는 참여자 목록에 존재
- 술 항목의 병 수와 단가는 1 이상
- 항목 및 전체 금액은 1조 원 이하
- 술 항목은 존재하는 차수를 참조
- 응답 키는 존재하는 참여자와 차수만 참조

### 확정 시

- 참여자는 2명 이상
- 모든 참여자가 모든 차수에 명시적으로 응답
- 각 차수에 `SOBER` 또는 `DRANK` 참여자가 한 명 이상
- 술값이 있으면 `DRANK` 참여자가 한 명 이상
- 계산된 모든 정수 금액은 0 이상

Core는 사용자 입력 오류에 예외를 던지지 않고 `SettlementOutcome.Failure`를 반환한다.
개발자 계약 위반은 `require()`로 즉시 실패한다.

## 6. 검증 예제

### T1 · 한 차수 기본 분배

3명, 총액 10,000원, 술값 0원, A 결제, 전원 참석.

| 참여자 | 금액 |
|---|---:|
| A·총무 | 3,332 |
| B | 3,334 |
| C | 3,334 |

송금: `B → A 3,334`, `C → A 3,334`

### T2 · 2차 불참

1차 40,000원은 A·B·C·D 참석, 2차 30,000원은 A·B·D 참석. A가 모두 결제.

| 참여자 | 금액 |
|---|---:|
| A | 20,000 |
| B | 20,000 |
| C | 10,000 |
| D | 20,000 |

### T3 · 논알코올

4명, 총액 40,000원, 술값 20,000원. A·B·C 음주, D 논알코올. A 결제.

| 참여자 | 금액 |
|---|---:|
| A | 11,666 |
| B | 11,667 |
| C | 11,667 |
| D | 5,000 |

### T4 · 차수별 총무가 다름

1차 40,000원은 A가 결제하고 A·B·C·D 참석. 2차 30,000원은 B가 결제하고
A·B·D 참석.

```text
B → A 10,000
C → A 10,000
D → A 10,000
A → B 10,000
D → B 10,000
```

서로 반대 방향인 `A ↔ B`도 상계하지 않는다.

### T5 · 같은 총무 차수는 올림 전에 합산

민수의 1차 원부담이 `10,000 / 3`, 3차 원부담이 `20,000 / 3`이고 두 차수의
총무가 같다면 민수의 송금액은 정확히 10,000원이다. 차수별로 올린 10,001원이 아니다.

### T6 · 차수별 면제

4명, 총액 40,000원. A 결제, D는 `EXEMPT`, A·B·C는 참석.

| 참여자 | 금액 |
|---|---:|
| A·총무 | 13,332 |
| B | 13,334 |
| C | 13,334 |
| D·면제 | 0 |

### T7 · 면제 총무

4명, 총액 40,000원, D 결제. D는 `EXEMPT`, A·B·C는 참석. A가 잔액 조정자다.

| 참여자 | 금액 |
|---|---:|
| A·조정자 | 13,332 |
| B | 13,334 |
| C | 13,334 |
| D·총무·면제 | 0 |

송금 합계는 정확히 40,000원이다.

### T8 · 술병 계산

4명, 총액 91,000원. 소주 `5병 × 5,000원`, 맥주 `3병 × 6,000원`으로 술값은
43,000원이다. A·B·C 음주, D 논알코올, A 결제.

| 참여자 | 금액 |
|---|---:|
| A | 26,332 |
| B | 26,334 |
| C | 26,334 |
| D | 12,000 |

### T9 · 비현실적 초소액 거부

3명, 총액 1원, 전원 참석, A 결제. B와 C를 각각 1원으로 올리면 A가 -1원이므로
`NEGATIVE_ADJUSTED_AMOUNT`로 실패한다.

## 7. 불변식 테스트

랜덤 입력 수만 건에 대해 다음을 검증한다.

1. `Σ 최종 부담액 == 전체 결제 총액`
2. 모든 최종 부담액은 0 이상
3. 같은 입력은 항상 같은 결과와 송금 순서를 생성
4. 수취인별 `ownShare + incomingTotal == paidTotal`
5. 수취인별 `Σ participantAmounts == paidTotal`
6. 참여자 최종 부담액은 모든 수취인의 참여자별 금액 합과 일치
7. 자기 자신에게 보내는 송금 없음
8. 송금액은 항상 양수
9. 같은 송금자·수취인 조합 중복 없음
10. `ABSENT`와 `EXEMPT`의 부담은 항상 0

## 8. 구현 체크리스트

- [ ] `Rational` 누적을 유지했다.
- [ ] 정수 변환은 수취인별 합산 후 `ceilTo(1)`에서만 한다.
- [ ] 기타 항목과 전역 면제 필드를 제거했다.
- [ ] 대표결제자와 greedy 상계를 제거했다.
- [ ] 서로 다른 총무 사이의 채권을 상계하지 않는다.
- [ ] 모든 참여자의 명시적 응답을 검증한다.
- [ ] 면제 총무의 결제액을 정확히 전액 회수한다.
- [ ] 결과 DTO에서 계산 근거를 버리지 않는다.
