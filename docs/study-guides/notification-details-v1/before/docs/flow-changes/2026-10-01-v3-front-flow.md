# 2026-10-01 — v3 프론트 1차 구현에서 드러난 백엔드 영향

웹 목데이터로 H1·R1·R2·R3·P2·P3·N1을 만들며 나온 것들이다(브랜치 `feat/jeongsan-v3`, 프론트
저장소 `profile`). Android·iOS는 같은 흐름으로 옮긴다 — 세 플랫폼이 같은 API를 쓴다.
목데이터 코드에서 해당 동작을 보려면 `src/jeongsan/v3/`의 파일명을 함께 적었다.

## FC-001 내 술자리 목록 — 탭·뱃지에 필요한 요약 데이터

- **상태:** 반영됨 — `feat/backend-v4`, API v6, 단위별 계약에 맞춘 서버 구현 (사용자 병합·프론트 연결 후속)
- **바뀐 흐름:** H1이 탭 세 개 **[내가 총무] [참여 중] [완료]** 로 나뉘고, 각 줄에 "지금 할 일" 한 줄과
  뱃지([입금 확인]·[정산금액 확인]·[응답하기])가 붙는다. (`home.ts`, `nextAction.ts`)
- **백엔드 영향:** 목록 API(`GET /me/gatherings` 류)가 술자리마다 다음을 줘야 화면을 그릴 수 있다.
  상세 API를 방마다 따로 부르면 목록 한 번에 N번 호출이 된다.
  - `id, title, date, status, completedAt`
  - `hostUserId`, `hostDisplayName` — [참여 중] 줄의 "민지 총무"
  - `myParticipantId`, `myRole` (`HOST`/`PARTICIPANT`), 내가 결제자인 차수가 있는가, 내 계좌 등록 여부
  - `roundCount`, `respondedAll`(내가 모든 차수에 응답했나), `unrespondedCount`(총무용)
  - 내 송금: 보낼 것들의 `{toName, amount, status, notReceivedAt}` 요약
  - 받을 것들 중 `SENT` 개수와 첫 송금자 이름, `WAITING` 개수
  - `spoonGiven`(내가 이 방에서 스푼을 줬나)
- **결정 필요:** "지금 할 일" 문구를 누가 만드나.
  - **A. 프론트가 만든다(현재).** 서버는 위 요약 필드만 준다. 규칙(`nextAction`)이 웹·Android·iOS
    세 곳에 복제되고, 세 곳 테스트로 일치를 지킨다.
  - **B. 서버가 만든다.** 목록·상세 응답에 `nextAction: {kind, banner, note?, tone}`을 넣는다. 규칙이
    한 곳(서버)에만 있고 세 플랫폼은 그리기만 한다. 대신 문구 하나 고칠 때도 서버 배포가 필요하다.
  - **추천: B의 `kind`만 서버, 문구는 프론트.** 서버가 `kind`(어떤 할 일인가)와 인자(이름·금액)를
    주고, 문구는 각 플랫폼이 고른다. 판정 규칙의 3중 복제를 없애면서 문구는 앱 배포 없이 못 바꾸는
    문제도 피한다.
- **반영할 곳:** `API.md`(목록·상세 응답), `DOMAIN_DB_DESIGN_V2.md`(조회 모델)

## FC-002 정산 미리보기 응답 모양

- **상태:** 반영됨 — `feat/backend-v4`, API v6, 단위별 계약에 맞춘 서버 구현 (사용자 병합·프론트 연결 후속)
- **바뀐 흐름:** R3에서 총무가 한 사람당 금액을 보고, 미응답자 이름을 눌러 그 자리에서 대신 응답을
  넣으면 금액이 즉시 다시 보인다. [정산하기]는 미리보기의 버전을 같이 보내고, 그 사이 입력이 바뀌었으면
  거절된다. (`SettlePage.tsx`, `mockServer.ts`)
- **백엔드 영향:** 미리보기 응답에 다음이 필요하다.
  - `inputRevision`, `inputHash` — 정산하기 요청에 그대로 돌려보낸다(이미 설계됨, ADR-004)
  - `lines[]`: 참여자마다 `{participantId, total, auto, rounds: [{roundId, type, amount}]}`
    - `auto` — 응답이 없어 자동응답(전 차수 참석·알코올)으로 계산되는 사람. R3 경고 박스와 "자동" 표시
    - `rounds[].type` — 자동응답이 채울 값까지 반영한 응답(`DRANK` 등)
  - `transfers[]`: `{from, to, amount, basis[]}` — 정산하기를 누르면 생길 송금 (FC-003)
  - 금액 단위는 정수 원. 프론트는 더하거나 나누지 않고 그대로 보여준다
  - 불일치 거절은 HTTP 409 + 오류 코드 하나(예: `SETTLEMENT_INPUT_CHANGED`). 프론트는 "그 사이 응답이
    바뀌었어요" 안내 후 미리보기를 다시 부른다
- **반영할 곳:** `API.md`

## FC-003 송금 근거(차수별 금액) — P3

- **상태:** 반영됨 — `feat/backend-v4`, API v6, 단위별 계약에 맞춘 서버 구현 (사용자 병합·프론트 연결 후속)
- **바뀐 흐름:** P3 "보낼 돈" 카드에 [어떻게 나온 금액인가요?]를 누르면 `1차 · 알코올 40,300원 /
  2차 · 알코올 32,000원`처럼 차수별 근거가 펼쳐진다. (`PayPage.tsx`, `model.ts` `Transfer.basis`)
- **백엔드 영향:** 송금 한 건(송금자→수취인)마다 차수별 금액과 그 차수 응답이 필요하다.
  지금 `settlement_transfers`에는 합계 `amount`만 있다.
- **기존 문서와 충돌:** 없음(빠져 있음). REQUIREMENTS 원칙 5 "금액과 근거를 함께 보여준다"를 받치는 데이터.
- **결정 필요:**
  - **A. 정산 시점에 근거를 스냅샷으로 저장**(`settlement_transfer_items` 같은 자식 테이블). 정산 뒤
    입력이 고정이라 값이 바뀌지 않는다. 행이 늘어난다.
  - **B. 조회 때 Core로 다시 계산.** 정산 뒤 입력이 고정(불변식 5)이라 결과가 같다. 저장은 없지만
    조회마다 계산한다.
  - 어느 쪽이든 **1원 올림이 수취인 합계 기준**(CALC_RULES_V2)이라 차수별 금액의 합이 송금액과 1원
    다를 수 있다. 근거 금액을 "올림 전 금액"으로 보여줄지, 차이를 마지막 차수에 붙일지도 정해야 한다.
  - 추천: **A** — ADR-015(확정 송금 스냅샷)와 같은 생각이고, 분쟁 때 "그때 본 근거"가 남는다.
- **반영할 곳:** `DOMAIN_DB_DESIGN_V2.md` §4, `CALC_RULES_V2.md`(근거 반올림 표시), `API.md`

## FC-004 총무 대리 응답 — `source = HOST`의 뜻이 넓어짐

- **상태:** 반영됨 — `feat/backend-v4`, API v6, 단위별 계약에 맞춘 서버 구현 (사용자 병합·프론트 연결 후속)
- **바뀐 흐름:** R3에서 미응답자 이름을 누르면 총무가 그 사람의 차수별 응답(불참·논알코올·알코올)을
  대신 넣는다(SCREENS.md R3 "총무 대리 설정"). 단톡방에서 "나 2차 안 갔어"라고 말만 한 사람을 위해서다.
  목데이터는 이 칸을 `source = HOST`로 저장한다. (`store.ts` `respondAsHost`)
- **기존 문서와 충돌:** `DOMAIN_DB_DESIGN_V2.md` §3.2 — "총무는 `HOST`로 **`EXEMPT`만** 쓰고,
  `HOST`가 쓴 칸은 참여자가 바꿀 수 없다." 대리 응답까지 `HOST`로 쓰면 참여자가 자기 응답을 못 고치게 된다.
- **결정 필요:** 총무가 대신 넣은 응답을 참여자가 나중에 고칠 수 있나.
  - **A. 고칠 수 있다(현재 목데이터).** 잠그는 건 `EXEMPT`+`HOST`뿐. 대리 응답은 `source = HOST`지만
    참여자가 덮어쓰면 `SELF`가 된다. → DOMAIN §3.2를 "HOST가 쓴 **EXEMPT** 칸만 잠긴다"로 고친다.
  - **B. 고칠 수 없다.** 총무 대리 = 확정. 참여자가 틀렸다고 느끼면 총무에게 말해야 한다.
  - **C. 출처를 나눈다.** `source = PROXY`를 새로 두고 잠그지 않는다. 의미가 가장 분명하지만 enum이 하나 는다.
  - 추천: **A** — 본인 응답이 우선이라는 원칙과 맞고 스키마 변경이 없다.
- **반영할 곳:** `DOMAIN_DB_DESIGN_V2.md` §3.2, `REQUIREMENTS.md`(총무 권한 표)

## FC-005 알림 — 이벤트별 대상·문구·링크, 읽음 API

- **상태:** 열림
- **바뀐 흐름:** H1 머리에 🔔(안 읽은 수), N1 알림함 화면이 생겼다. 알림을 누르면 정해진 화면으로
  간다. (`notify.ts`, `NotificationsPage.tsx`)
- **백엔드 영향:**
  - 알림 이벤트·대상은 `REQUIREMENTS.md` §10 표가 기준이다. 프론트는 거기에 **누르면 갈 곳과 문구**를
    정했다 — 알림 행에 `type`(이벤트)과 `gatheringId`가 있으면 프론트가 갈 곳을 고른다:

    | 이벤트 | 받는 사람 | 문구(프론트) | 누르면 |
    |---|---|---|---|
    | 정산하기 | 총무 뺀 참여자 | 정산이 나왔어요! 입금액을 확인해주세요 · `민지님께 41,000원 외 1건` | P3 |
    | 자동응답 처리됨 | 본인 + 총무 | (본인은 위 알림에 덧붙임) / 자동응답으로 계산된 사람이 있어요 | P3 / R1 |
    | [보냈어요] | 수취인 | ○○님이 보냈대요. 입금을 확인해주세요 | R1 |
    | [아직 안 들어왔어요] | 송금자 | ○○님이 아직 입금을 확인 못 했대요 | P3 |
    | 완료 | 참여자 전원 | 정산 완료! 🎉 · 7일 뒤 사라져요 | R1 |

  - **행동한 본인에게는 보내지 않는다.** (예: 마지막 [확인]을 누른 사람은 "완료" 알림을 받지 않음)
  - **"정산 완료"는 `COMPLETED`(모두 입금)에만 쓴다.** 정산하기 직후는 "정산이 나왔어요" — [완료] 탭과
    뜻을 맞추기 위해서다(CTO 결정 2026-10-01).
  - 정산 알림 본문에 **첫 수취인 이름·금액과 나머지 건수**가 들어간다 → 알림 생성 시 송금 요약이 필요.
  - API: 내 알림 목록(최신순), 안 읽은 수, 하나 읽음, 모두 읽음.
  - 목데이터는 §10 표 중 위 다섯 줄만 흉내 낸다. 나머지(응답 남김·[확인]·되돌리기·계좌 필요·스푼)도
    §10대로 만든다 — 프론트가 빠뜨린 것이지 빼기로 한 게 아니다.
- **반영할 곳:** `DOMAIN_DB_DESIGN_V2.md`(`notifications` 컬럼: `type`, `gathering_id`, 표시 인자, `read_at`),
  `API.md`

## FC-006 "정산금액 봤음" 기록 — [정산금액 확인] 뱃지

- **상태:** 반영됨 — `feat/backend-v4`, API v6, 단위별 계약에 맞춘 서버 구현 (사용자 병합·프론트 연결 후속)
- **바뀐 흐름:** 정산이 나왔는데 참여자가 내 금액(P3)을 아직 안 열어봤으면 H1 줄에 **[정산금액 확인]**
  뱃지가 붙고, 그 방을 누르면 정산방이 아니라 P3로 바로 간다. P3를 한 번 열면 둘 다 풀린다. (`home.ts`
  `rowBadge`·`entryRoute`, `store.ts` `paySeen`)
- **백엔드 영향:** 목데이터는 "봤음"을 기기 메모리에만 둔다 → 폰에서 보고 웹에 들어가면 뱃지가 다시 뜬다.
- **결정 필요:**
  - **A. 참여자 행에 `settlement_viewed_at`(NULL 가능)** — P3를 열 때 서버에 기록. 정산 되돌리기 때 지운다.
  - **B. "정산하기" 알림의 읽음 여부로 대신한다.** 새 컬럼이 없지만, 알림을 안 누르고 목록으로 들어와
    P3를 본 경우를 못 잡는다.
  - **C. 기기에만 둔다(현재).** 서버 변경 없음. 여러 기기 쓰는 사람에게 뱃지가 어긋난다.
  - 추천: **A** — 컬럼 하나, 기기 간 일치. FC-001 목록 요약에 `settlementViewed`로 같이 내려준다.
- **반영할 곳:** `DOMAIN_DB_DESIGN_V2.md`(`participants`), `API.md`

## FC-007 응답 단순화·참여자 진입 순서·H1 탭

- **상태:** 프론트만
- **바뀐 흐름:**

  - H1 탭 [내가 총무] [참여 중] [완료] — 분류는 FC-001의 요약 필드로 프론트가 한다.
- **백엔드 영향:** 없음. 위 판단에 필요한 데이터는 FC-001·FC-006에 포함돼 있다.

## FC-008 차수 이름(1차·2차) 누가 붙이나

- **상태:** 반영됨 — `feat/backend-v4`, API v6, 단위별 계약에 맞춘 서버 구현 (사용자 병합·프론트 연결 후속)

- **결정 필요:**

  - 추천: **A** — 타임라인 시스템 소식은 이미 "표시 인자(JSON)"로 저장하므로 `roundSeq`만 넣으면 된다.
