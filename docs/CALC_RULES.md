# 정산어택 — 계산 규칙과 테스트 케이스

> **구현 순서상 이 문서가 1번이다.** DB도 UI도 만들기 전에, 여기 정의된 함수를 순수 함수로 구현하고 아래 케이스를 전부 통과시킨다.
> 아래 기대값은 참조 구현으로 실제 계산해 검증한 값이다. 구현 결과가 다르면 구현이 틀린 것이다.

---

## 1. 입력과 출력

```
입력
  participants: [{ id, name, exempt }]              // exempt: 면제자 여부
  rounds:       [{ id, seq, label, total, alcohol, payerId }]
  drinkItems:   [{ roundId, name, bottleCount, unitPrice }]   // 선택
  extras:       [{ id, label, amount, payerId, bearerIds }]
  attendance:   { (participantId, roundId) -> { attended, drank } }
  roundingUnit: 10 | 100        // 기본 10

출력
  absorberId                     // 흡수자
  amounts:   { participantId -> 최종 부담액(정수) }
  breakdown: { participantId -> [{ roundId, attended, drank, amount }] }   // 근거 화면용
  transfers: [{ fromId, toId, amount }]
```

`breakdown`은 참여자 결과 화면(W2)에서 "왜 이 금액인지"를 보여주는 데 쓴다. 계산만 하고 버리지 말 것.

## 2. 알고리즘

### 2.1 원부담 계산 (반올림 없음)

각 차수 `r`에 대해:

```
비주류 = r.total - r.alcohol
참석자 = attended == true 인 참여자
음주자 = drank == true 인 참여자          // 반드시 참석자의 부분집합

참석자 각각에게  비주류 / len(참석자)  를 더한다
음주자 각각에게  r.alcohol / len(음주자) 를 더한다
```

**반드시 정확한 유리수(분수)로 누적한다.** `Double`은 물론 `BigDecimal`도 쓰지 말 것.

`BigDecimal`이 안 되는 이유는 정밀도가 아니라 구조다. `1/3` 같은 무한소수는 **어떤 진법에서도 유한 자릿수로 표현할 수 없어서**, 나누는 순간 반드시 정보가 버려진다. 그리고 마지막 `올림(ceil)`은 오차의 크기와 무관하게 **0보다 크기만 하면 한 단위를 통째로 밀어올린다.**

```
3명 / 20,000원짜리 차수 3개 / 전원 참석 / 술값 0
정확한 원부담 = 20000/3 × 3 = 20,000원 (딱 떨어짐)

  유리수                    20000              → 올림 20,000원  ✓
  BigDecimal HALF_UP 12자리 20000.000000000001 → 올림 20,010원  ✗
  BigDecimal HALF_UP 100자리 20000.000…001     → 올림 20,010원  ✗  ← 정밀도를 올려도 동일
```

**정밀도를 100자리로 올려도 결과가 1원도 바뀌지 않는다.** 랜덤 정산 시나리오 30,000건(2~8명 / 1~4차수 / unit 10·100)을 유리수 기준과 대조한 결과 **`HALF_UP` 누적은 210건(0.70%)에서 다른 금액**을 냈다. 약 143번에 한 번꼴이다.

더 나쁜 것은 **합계 검증으로 잡히지 않는다**는 점이다. 흡수자가 오차를 흡수해버리기 때문에 `합계 == 원금`은 그대로 통과하고, 엉뚱한 사람이 10원을 더 내고 흡수자가 10원을 더 손해 본 채 근거 화면에 그대로 나간다.

> 버림(`ROUND_DOWN`) 누적은 30,000건 전부 일치했다. 모든 항이 양수라 누적값이 정확값을 넘지 않기 때문이다. 하지만 그 안전성은 **"모든 항이 양수"라는 조건에 의존**하므로, 할인·환불처럼 음수 항이 하나만 들어와도 조용히 깨진다. **조건부 안전에 기대지 말 것.**

Kotlin에는 유리수 타입이 없으므로 `BigInteger` 분자/분모 쌍으로 직접 구현한다. 필요한 연산은 `plus`, `div(Int)`, `ceilTo(unit)` 셋뿐이라 40~60줄이면 충분하다.

참석자가 0명인 차수, 음주자가 0명인데 `alcohol > 0`인 차수는 그 몫을 배분하지 않는다 (§4 검증에서 걸러야 할 입력).

### 2.1-b 술값 산출 (DrinkItem)

해당 차수에 `drinkItems`가 하나라도 있으면 `alcohol`을 무시하고 아래로 덮어쓴다.

```
alcohol = Σ (bottleCount × unitPrice)
```

영수증에 병 수가 찍히므로 금액을 계산해 넣는 것보다 입력이 쉽다. 계산 규칙 자체는 달라지지 않는다.

### 2.1-c 면제자

`exempt == true`인 참여자는 **최종 부담이 0**이고, **모든 분모에서 제외된다.**

```
차수의 참석자 집합 = attended && !exempt
차수의 음주자 집합 = drank   && !exempt
기타 항목의 부담자 = bearerIds 중 !exempt
```

면제자의 몫은 나머지가 나눠 낸다. **면제는 모임 전체 단위다** — 차수별 면제는 지원하지 않는다.

면제자가 결제를 했다면 그 금액은 전액 돌려받는다 (부담 0이므로 순잔액 = 결제액).

### 2.1-d 기타 항목

차수와 별개로 계산해 각자의 원부담에 더한다.

```
부담자(면제자 제외) 각각에게  amount / 부담자수
```

### 2.2 흡수자 결정

```
결제총액(p) = p가 payer인 차수들의 total 합 + p가 payer인 기타 항목들의 amount 합
흡수자 = 면제자를 제외한 참여자 중 결제총액이 가장 큰 사람
        동률이면 participantId 사전순 첫 번째    // 결정론적이어야 함
```

**면제자는 흡수자가 될 수 없다.** 흡수자는 잔액을 흡수하는 역할이므로 "부담 0"과 모순되기 때문이다.

원칙: **결제하느라 고생한 사람이 반올림 이득을 가져간다.**

### 2.3 반올림

```
면제자           : 최종(p) = 0
흡수자·면제자 외  : 최종(p) = ceil(원부담(p) / unit) * unit     // 올림. 반올림 아님
흡수자           : 최종(p) = 전체총액 - (나머지 전원의 최종 합)
```

전체총액 = 모든 차수 `total`의 합 + 모든 기타 항목 `amount`의 합.

이 구조 때문에 **합계는 항상 원금과 정확히 일치한다.** 별도 보정 로직을 넣지 말 것. 만약 어긋난다면 §2.1에서 부동소수점을 썼거나 흡수자 계산이 틀린 것이다.

### 2.4 송금 목록

```
순잔액(p) = 결제총액(p) - 최종(p)
  > 0 : 받을 사람
  < 0 : 보낼 사람

채권자를 금액 내림차순, 채무자를 금액 내림차순으로 정렬한다.
(동률이면 participantId 사전순 — 결과가 결정론적이어야 한다)
가장 큰 채권자와 가장 큰 채무자를 매칭해 min(둘) 만큼 상계하고,
0이 된 쪽을 다음으로 넘긴다. 양쪽이 소진될 때까지 반복.
```

최소 송금 횟수의 최적해가 아니다. **최적화하지 말 것.** 실용적으로 충분하고, 결과가 예측 가능한 것이 더 중요하다.

## 3. 테스트 케이스

기대값은 검증된 값이다. 그대로 테스트로 옮긴다.

### T1 · 기본 N빵 — 나머지가 흡수자에게 간다

3명(A·B·C), 1차만, 총액 10,000, 술값 0, 결제 A. unit=10

| | 금액 |
|---|---|
| **A (흡수자)** | **3,320** |
| B | 3,340 |
| C | 3,340 |
| 합계 | 10,000 ✓ |

10,000 / 3 = 3,333.33 → B·C는 10원 올림으로 3,340. A는 10,000 − 6,680 = 3,320.
**흡수자가 가장 적게 낸다.** 이것이 규칙이 의도한 동작이다.

송금: `B → A 3,340`, `C → A 3,340`

---

### T2 · 2차 불참

4명, 1차 40,000 (전원), 2차 30,000 (C 불참), 둘 다 A 결제, 술값 0. unit=10

| | 금액 |
|---|---|
| A (흡수자) | 20,000 |
| B | 20,000 |
| **C** | **10,000** |
| D | 20,000 |
| 합계 | 70,000 ✓ |

나누어떨어지므로 올림이 발생하지 않고 흡수자도 같은 금액이다. **올림이 없을 때 흡수자가 이득을 보지 않는 것이 정상이다.**

---

### T3 · 논알콜 분리

4명, 1차 40,000 (그중 술값 20,000), D는 논알콜, A 결제. unit=10

| | 계산 | 금액 |
|---|---|---|
| A (흡수자) | 5,000 + 6,666.67 | **11,660** |
| B | 5,000 + 6,666.67 | 11,670 |
| C | 5,000 + 6,666.67 | 11,670 |
| **D (논알콜)** | 5,000 + 0 | **5,000** |
| 합계 | | 40,000 ✓ |

비주류 20,000은 참석자 4명이 5,000씩. 주류 20,000은 음주자 3명이 6,666.67씩.

---

### T4 · 결제자가 두 명 — 송금 방향이 갈린다

4명, 1차 40,000 **A 결제** (전원), 2차 30,000 **B 결제** (C 불참). unit=10

| | 금액 |
|---|---|
| A (흡수자, 40,000 결제) | 20,000 |
| B (30,000 결제) | 20,000 |
| C | 10,000 |
| D | 20,000 |
| 합계 | 70,000 ✓ |

순잔액: A +20,000 / B +10,000 / C −10,000 / D −20,000

송금: `D → A 20,000`, `C → B 10,000`

**T2와 금액은 같지만 송금 목록이 다르다.** 결제자 분리가 제대로 반영되는지 확인하는 케이스다.

---

### T5 · 복합 (통합 테스트)

5명. 1차 87,000 (술 35,000), E는 논알콜, **A 결제**. 2차 42,000 (술 30,000), A·B·C만 참석 전원 음주, **B 결제**. unit=10

| | 금액 |
|---|---|
| A (흡수자) | 33,150 |
| B | 33,150 |
| C | 33,150 |
| D (1차만) | 19,150 |
| E (1차 논알콜) | 10,400 |
| 합계 | 129,000 ✓ |

송금: `C → A 33,150`, `D → A 19,150`, `E → A 1,550`, `E → B 8,850`

**E가 두 사람에게 나눠 보내는 것이 정상이다.** B가 42,000을 결제했고 부담이 33,150이라 8,850을 받아야 하기 때문이다. 이걸 한 명에게 몰아주도록 "고치면" 안 된다.

### T6 · unit = 100

T1과 동일 조건, unit=100

| | 금액 |
|---|---|
| A (흡수자) | 3,200 |
| B | 3,400 |
| C | 3,400 |

단위가 커질수록 흡수자의 이득이 커진다. 의도된 동작이다.

### T7 · 흡수자 음수 — 이 케이스가 발생하면 안 된다

4명, 총액 4,100, unit=**1000**

| | 금액 |
|---|---|
| **A (흡수자)** | **−1,900** ← |
| B | 2,000 |
| C | 2,000 |
| D | 2,000 |

합계는 4,100으로 맞지만 흡수자가 음수다.

**대응: 예외 처리 코드를 넣지 않는다. `roundingUnit`을 10과 100만 허용해 이 입력을 막는다.**

### 다만 unit=100에서도 완전히 봉쇄되지 않는다

발생 조건은 대략 `1인당 금액 < (비면제 인원수 − 1) × unit` 이다. **인원이 늘면 unit=100에서도 음수가 난다.** 전원 참석·술값 0 기준으로 실측한 임계값은 다음과 같다.

| 인원 | 흡수자 음수 발생 총액 | 인원 | 흡수자 음수 발생 총액 |
|---|---|---|---|
| 3명 | 100원 이하 | 10명 | 7,100원 이하 |
| 5명 | 1,100원 이하 | 12명 | 10,900원 이하 |
| 8명 | 4,100원 이하 | 15명 | **18,100원 이하** |

술자리 정산에서는 사실상 발생하지 않지만, **15명이 카페에서 18,000원을 쓰고 unit=100으로 정산하면 흡수자가 음수가 된다.**

**대응: 예외 처리가 아니라 불변식으로 막는다.** §4 검증에 `모든 참여자의 최종 금액 ≥ 0`을 넣고, 위반하면 `unit`을 10으로 강등해 재계산한다. unit=10에서도 위반하면 그때 거부한다.

이 케이스는 **회귀 테스트로 남긴다** — unit=1000이 거부되는지, 그리고 대규모 인원·소액에서 흡수자가 음수가 되지 않는지 두 가지 형태로.

### T8 · 면제자

4명(동규·민지·재훈·수아), 1차 40,000 (술값 0), **수아 면제**, 동규 결제. unit=10

| | 금액 |
|---|---|
| 동규 (흡수자) | 13,320 |
| 민지 | 13,340 |
| 재훈 | 13,340 |
| **수아 (면제)** | **0** |
| 합계 | 40,000 ✓ |

수아가 분모에서 빠져 40,000 / 3 = 13,333.33이 된다. **면제자의 몫을 나머지가 나눠 낸다.**

송금: `민지 → 동규 13,340`, `재훈 → 동규 13,340`

---

### T9 · 기타 항목 — 부담자만 나눠 낸다

4명, 1차 40,000 (전원, 술값 0) 동규 결제 + **택시비 18,000 (재훈·수아만 부담) 재훈 결제**. unit=10

| | 계산 | 금액 |
|---|---|---|
| 동규 (흡수자) | 10,000 | 10,000 |
| 민지 | 10,000 | 10,000 |
| 재훈 | 10,000 + 9,000 | 19,000 |
| 수아 | 10,000 + 9,000 | 19,000 |
| 합계 | | 58,000 ✓ |

송금: `수아 → 동규 19,000`, `민지 → 동규 10,000`, `재훈 → 동규 1,000`

**재훈은 19,000을 부담하지만 택시비 18,000을 이미 결제했으므로 1,000만 보낸다.** 기타 항목의 결제자가 순잔액에 반영되는지 확인하는 케이스다.

### T10 · 술병 계산

4명, 1차 총액 91,000. 술값은 **소주 5병 × 5,000 + 맥주 3병 × 6,000 = 43,000** 으로 산출. 수아는 논알콜, 동규 결제. unit=10

| | 금액 |
|---|---|
| 동규 (흡수자) | 26,320 |
| 민지 | 26,340 |
| 재훈 | 26,340 |
| **수아 (논알콜)** | **12,000** |
| 합계 | 91,000 ✓ |

비주류 48,000을 4명이 12,000씩, 주류 43,000을 음주자 3명이 14,333.33씩.

`DrinkItem` 합계가 `alcoholAmount`를 정확히 대체하는지 확인하는 케이스다. **술병 입력은 금액 산출 방식일 뿐 계산 규칙은 바뀌지 않는다.**

### T11 · 전체 통합 — 면제 + 기타 항목 + 다중 결제자

5명. 1차 87,000 (술 35,000) **동규 결제**, 2차 42,000 (술 30,000, 동규·민지·재훈만) **민지 결제**, 택시비 20,000 (수아·지원 부담) **민지 결제**, **지원 면제**. 지원은 1차 참석·논알콜. unit=10

| | 금액 |
|---|---|
| 동규 (흡수자) | 35,750 |
| 민지 | 35,750 |
| 재훈 | 35,750 |
| 수아 | 41,750 |
| **지원 (면제)** | **0** |
| 합계 | 149,000 ✓ |

지원이 면제이므로 1차 분모가 4명이 되고, 택시비 20,000도 **수아 혼자** 부담한다.

송금: `수아 → 동규 41,750`, `재훈 → 동규 9,500`, `재훈 → 민지 26,250`

민지는 62,000(2차 42,000 + 택시 20,000)을 결제하고 35,750을 부담하므로 26,250을 받는다.

## 4. 입력 검증

**검증 시점은 둘로 나눈다.** 저장 시점(주최자가 차수를 입력하는 중)에 전체 검증을 걸면 **아직 아무도 체크하지 않았으므로 참석자가 0명이라 입력 자체가 막힌다.**

| 조건 | 저장 시 | 확정 시 | 처리 |
|---|---|---|---|
| `total <= 0` | ✓ | ✓ | 거부 |
| `alcohol < 0` | ✓ | ✓ | 거부 |
| `alcohol > total` | ✓ | ✓ | 거부 |
| `payerId`가 참여자 목록에 없음 | ✓ | ✓ | 거부 |
| `bearerIds`에 참여자 목록에 없는 id | ✓ | ✓ | 거부 |
| `bottleCount <= 0` 또는 `unitPrice <= 0` | ✓ | ✓ | 거부 |
| `roundingUnit`이 10, 100 외의 값 | ✓ | ✓ | 거부 |
| `attended == false && drank == true` | ✓ | ✓ | 거부 (모순) |
| 참여자 2명 미만 | — | ✓ | 거부 |
| 차수의 참석자가 0명 | — | ✓ | 거부 |
| 면제자를 뺀 차수 참석자가 0명 | — | ✓ | 거부 |
| `alcohol > 0` 인데 음주자 0명 | — | ✓ | 거부 — 배분 대상이 없음. "술값을 0으로 하거나 음주자를 지정하세요" 안내 |
| 면제자를 뺀 기타 항목 부담자가 0명 | — | ✓ | 거부 |
| 참여자 전원이 면제 | — | ✓ | 거부 |
| **모든 참여자의 최종 금액 ≥ 0** | — | ✓ | **unit을 10으로 강등 후 재계산. 그래도 위반이면 거부** (T7) |

### 에러 응답에는 위치 식별자를 담는다

`"입력이 잘못되었습니다"`는 차수를 5개 입력한 주최자에게 아무 도움이 되지 않는다. **어느 차수, 어느 항목이 문제인지 반드시 반환한다.**

```json
{ "code": "NO_DRINKER_WITH_ALCOHOL",
  "detail": "2차에 술값 30,000원이 있는데 술 마신 사람이 없습니다.",
  "roundId": 2 }
```

계산 엔진은 **예외를 던지지 말고 `Result` 타입을 반환한다.** 순수 함수가 유지되고 테스트가 쉬워진다. HTTP 상태 코드 매핑은 API 계층의 몫이다.

## 5. 구현 체크리스트

- [ ] 원부담 누적에 **정확한 유리수**를 썼다 (`Double`·`BigDecimal` 모두 아님 — §2.1)
- [ ] 모든 테스트에서 `합계 == 전체총액`
- [ ] 흡수자가 동률일 때 결과가 결정론적이다
- [ ] 송금 목록이 결정론적이다 (같은 입력 → 항상 같은 순서)
- [ ] `breakdown`이 차수별로 채워진다 (W2 화면에 필요)
- [ ] §4의 모든 검증 케이스가 거부된다
- [ ] 면제자의 최종 금액이 항상 0이다
- [ ] 면제자가 흡수자로 선정되지 않는다
- [ ] `DrinkItem`이 있으면 `alcoholAmount`를 덮어쓴다
- [ ] 기타 항목의 결제자가 순잔액에 반영된다 (T9)

### 불변식 테스트 (property test)

T1~T11은 **아는 케이스**만 막는다. 랜덤 입력 수만 건에 대해 아래 세 가지가 항상 참인지 검증한다.

- [ ] `Σ 최종금액 == 전체총액` — 어떤 입력에서도
- [ ] `모든 최종금액 ≥ 0` — 흡수자 포함 (T7 회귀)
- [ ] 같은 입력 → 항상 같은 출력 (금액·흡수자·송금 순서 전부)

이 셋이 통과하면 §2.1의 유리수 요구가 지켜졌는지도 함께 검증된다. `BigDecimal`로 구현하면 첫 번째와 세 번째 사이에서 어긋난다.
