## 결정과 가정

CTO가 참석자당 총무 +10, 총무 본인 제외, 제외 후 이미 받은 보상 유지로 결정했다.
참석은 한 차수 이상 SELF/HOST SOBER/DRANK로 해석했다. 빈 응답/전부 불참/AUTO는 지급하지 않는다.
동일 술자리·총무 계정·참여자는 단위/차수 추가에도 한 번만 지급한다. 다른 총무는 자기 담당 차수 응답으로 따로 받는다.
수동 감사·완료 보너스와 기존 응답 일괄 소급은 없다. 기존 칭호 구간은 유지한다.

## 자체 점검

- 중복: DB 복합 PK와 수혜 사용자 잠금 안의 지급 이력 조회. 반복 응답·제외·재추가는 이력을 지우지 않는다.
- 동시성: 단위→술자리→사용자 순서. 회원 신규 좌석 INSERT 전 가입자/총무 계정을 ID 순으로 잠가 교차 가입 시 FK 공유→배타 승격 순환을 막는다.
- 실패 원자성: 별도 서비스 MANDATORY로 호출부의 응답 트랜잭션에 참여한다. 이력 INSERT 후 잔액 증가 실패도 롤백되며 테스트에서 BIGINT 한도 실패를 주입한다.
- 누적: UPDATE spoon_count=spoon_count+:amount를 사용해 읽어온 옛 잔액으로 덮어쓰지 않는다. 서로 다른 술자리 지급도 같은 수혜 계정 행에서 직렬화한다.
- 권한: 기존 본인/총무 응답 인가 뒤 내부 호출하며 새 공개 지급 API가 없다. 총무와 수혜 계정은 서버 저장 값으로 찾는다.
- 조회: 한 응답의 고정 개수 조회이며 참여자 목록마다 조회하지 않는다. 술자리 목록의 IN 배치 쿼리는 유지한다.
- 보존: 이력은 참가자/수혜 사용자 FK CASCADE. 술자리 만료는 누적 잔액을 감소시키지 않는다. 같은 이름은 식별 키가 아니다.
- 호환: 기존 spoonCount DTO를 사용한다. 신규 migration 022/032만 추가하고 기존 적용 파일은 수정하지 않았다. 새 의존성·prod 기본값·Core 계산 변경 없음.
- 구조: 순수 AttendanceSpoonPolicy(Java/Kotlin 독립)와 JDBC/트랜잭션 AttendanceSpoonService를 분리했다. 기존 HTTP/JDBC 인프라는 공유한다.
