# 숫자 직접 인식 검증 · 2026-10-19

기준은 `dbcc997884c6fcf62cc218554237333a614b9025`, 원격 main 문서 기준은
`3eb525464a32a3415c4d3c0db9dd6bfd9bcc3420`이다. 사용자 진행 요청에 따라 Python 숫자 인식만 보완했다.
새 모델 종류·패키지·API 필드는 추가하지 않았다. Spring·core·DB·앱·운영은 변경하지 않았다.

## 발견한 원인과 선택

이전 [추가 원본 기록](expanded-public-validation.md)의 T는 청도맥주 수량 1이 빠졌다.
원래 숫자 칸 `(1341,977,1462,1061)`에 앞줄 수량 2의 잉크가 위쪽 경계에 걸려 있었다.
잘린 잉크 거절은 정상 동작했지만 한 행의 금액 상자 높이만으로는 원근 사진의 수량 영역을 분리하지 못했다.

금액 중심만으로 경계를 좁힌 중간 실험도 대상 1의 아래 여백이 부족해 거절됐다.
따라서 같은 행의 숫자 열에서 읽힌 상자 중심의 중앙값을 사용하고, 인접 금액 행의 중심 사이 중간점으로
기존 영역을 더 제한했다. T의 대상 영역은 `(1341,994,1462,1054)`로 앞줄 잉크와 대상 수량이 분리됐다.
잘린 잉크/빈 칸/정수/점수 기준을 완화하거나 수량을 가격에서 역산하지 않았다.

이렇게 위치를 아는 칸은 검출기를 재호출하지 않고 공개 `TextRecognition.predict()`에 직접 전달한다.
설치된 PaddleOCR 3.7.0 공개 래퍼와 [공식 인식 API](https://www.paddleocr.ai/v3.3.1/en/version3.x/module_usage/text_recognition.html)를 대조했다.
모델명은 `korean_PP-OCRv5_mobile_rec`로 명시한다. 기본 모델명이나 비공개 파이프라인 객체에 기대지 않는다.
전체 OCR과 별도 인식 인스턴스를 쓰므로 **같은 가중치여도 추가 메모리 비용**이 있다. ARM 메모리는 미실측이다.

## 유지한 제한

- 최초 전체 OCR 한 번 + 빈 칸만 최대 8개·16회 직접 인식. 기존 숫자·부호·불확실한 토큰은 덮어쓰지 않는다.
- 인접 행 계산은 빈 숫자 칸이 있는 행에만 수행한다. 한도에 걸리면 남은 칸은 누락으로 남긴다.
- 단가·수량·금액 헤더 위치와 이미 읽힌 금액이 필요하다. 잘린/빈/균일/가로선 칸은 보내지 않는다.
- 가로 범위는 유지해 부호·소수점을 잘라내지 않는다. 4배 확대·여백 16/32px·0.90 이상 전체 정수와 이견 거절 유지.
- 단가·총액·주류 개수를 추측하지 않는다. NUMERIC_REGION_RECOGNIZED·requiresConfirmation=true 유지.
- API schemaVersion 2·기존 확인 사유/오류 계약 유지, API.md v16에 구현 경계를 기록했다.

## 남은 검증

여러 줄 상품명·상품코드·품목 없는 전표·두 문서가 섞인 사진은 이번 숫자 보완으로 지원하지 않는다.
두 개발 사진 밖에서의 누락·오인식률과 직접 촬영 대표 표본 30~100장이 필요하다. 같은 원본의 압축본은
개선용과 평가용으로 나누지 않고 한 묶음에 두며, 매장/원본이 다른 별도 평가를 유지해야 한다.
추가 학습·다른 모델 비교는 아직 하지 않았다. API/원격 CI와 독립 사진 정확도를 구분한다.
운영/ARM·Spring/앱 연결·타인 리뷰·병합·배포도 미완료다.
