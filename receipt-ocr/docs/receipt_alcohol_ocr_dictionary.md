# 영수증 OCR 주류명 사전 및 수량 판정 규칙

> **정산어택 적용본 v1.1.0:** CTO 제공 문서를 팩트체크한 뒤 2026-10-14 수정했다.
> 브랜드만으로 용기를 추정하지 않고 모든 결과를 총무 확인용 후보로 반환한다.
> 원본 문서의 권고는 제품 요구사항을 대체하지 않는다. 실행 사전은 [drinks.md](../data/drinks.md),
> 현재 구현 계약은 [RECEIPT_OCR](../../docs/RECEIPT_OCR.md)이다.
> 아래 테스트 표는 목표 정책이며 모든 POS 양식을 지원한다는 뜻은 아니다.
> 현재 파서는 정확한 사전 이름 + 명시 단위/용량/수량 또는 3개 숫자 열만 지원한다.
> 일반 키워드 토큰 매칭·자동 수량 역산·실제 영수증 정확도 보장은 구현하지 않는다.


> **목적:** 영수증에서 주류 관련 상품명·주종·판매 수량·용기·용량을 안전하게 구조화한다. **`500cc`를 `500병`으로 해석하거나, 수량이 없는 결제전표에서 병 수를 추정하는 것을 금지한다.**
>
> **적용:** 한국어 식당·주점 POS 상세 영수증, 카드 매출전표, 촬영·스캔 이미지에서 추출된 OCR 결과.
>
> **문서의 성격:** 제품·브랜드 존재와 주류 분류는 하단 공식 출처로 검증했다. 반면 **OCR 오인식 변형 예시, 매칭 규칙, 보류 조건, 테스트 데이터는 이 프로젝트를 위한 설계 제안**이지 공식기관이 정한 규정은 아니다. 아래 목록은 국내 모든 주류의 완전한 목록이 아니다.

## 0. 절대 불변 규칙 (Must)

1. **텍스트에 없는 사실은 채우지 않는다.** 명시적인 상품 수량이 없다면 `quantity = null`이다. `1`을 기본값으로 넣지 않는다.
2. **용량과 수량을 독립적으로 저장한다.** `500cc = 500mL`는 용량이며 `500병`이 아니다. `도수 25`, `25도`, `25%`도 수량이 아니다.
3. **브랜드를 알더라도 판매 용기는 추측하지 않는다.** `참이슬`을 찾았다는 이유만으로 `병 1개`를 설정하지 않는다. `테라`라고 해서 무조건 병맥주가 아니다.
4. **수량(`quantity`)과 병 수(`bottle_count`)를 분리한다.** 상품 수량 `2`가 확실해도 용기가 불명확하면 `bottle_count = null`이다.
5. **단위가 다른 항목을 병 수로 합산하지 않는다.** 생맥주 잔·캔·피처·하이볼·소맥·세트는 병과 구별한다.
6. **제품의 접두·접미어를 먼저 확인한다.** `테라 제로`, `카스 0.0`, `클라우드 논알콜릭`, `진로 토닉워터`, `별빛청하`, `테라 라이트`를 각각 `테라`, `카스`, `클라우드`, `진로`, `청하`, `테라`로 무조건 축약하지 않는다.
7. **계산으로 수량을 복원하지 않는다.** `단가 × 수량 = 금액`이 맞아 보이더라도 영수증에 수량이 없으면 null이다. 금액/통상 판매가로 병 수를 역산하지 않는다.
8. **수량·용기·주종의 근거가 없거나 충돌하면 검토 대상이다.** `REVIEW_REQUIRED`로 남기며 사용자 확인 없이 자동 확정하지 않는다.
9. **결제전표 여부가 아니라 실제 인쇄된 상품행 여부를 확인한다.** 카드전표에도 상품 내역이 있을 수 있고, 총 결제액만 있을 수도 있다.
10. **주류로 보이는 문자열보다 명확한 제외·예외 문자열이 우선한다.** `하이트제로0.00`, `테라 제로` 등을 일반 맥주로 자동 합산하지 않는다. 다만 `새로 제로슈거`나 `진로 제로슈거`는 무알코올 음료라는 뜻이 아니다.

## 1. 명칭과 데이터 개념

### 1-1. 주종과 판매 형태를 혼동하지 말 것

- **주종(주류 분류):** 식약처 식품안전나라가 설명하는 맥주·탁주·약주·청주·소주·위스키·과실주 등 주류 분류와 연결될 수 있다. 아래 코드는 **OCR 앱 내부 분류 코드**로, 법정 식품유형과 완전히 일치하는 코드가 아니다.
- **용기:** `BOTTLE`(병), `CAN`(캔), `GLASS`(잔), `PITCHER`(피처), `PACK`(팩/묶음), `UNKNOWN`(판정 불가). **제공 방식은 별도 필드** `serving_type = DRAFT / UNKNOWN`으로 둔다. 생맥주 피처는 `DRAFT`와 `PITCHER`를 동시에 표현한다.
- **용량(volume_ml):** `500cc`, `500ml`, `0.5L`는 모두 500mL이지만 병인지 잔인지 결정하지 않는다.
- **판매 수량(quantity):** 주문/판매한 품목 개수. 원문에서 수량의 위치·단위가 확인돼야 확정한다.
- **병 수(bottle_count):** **명시적으로 병 단위인 주류**의 개수만 확정한다. 다른 경우는 보통 null; 캔·생맥주임이 명확할 때 병으로 판매된 수는 0으로 둘 수 있으나, 합계에서는 수량 불명 항목과 구별해야 한다.
- **주의:** `생막걸리`의 **생(生)**은 일반적으로 비살균 제품명 표시이지 맥주처럼 탭으로 따른 `DRAFT` 판매를 뜻하지 않는다. `클라우드 생 드래프트`처럼 상품명에 `드래프트`가 들어 있어도 실판매 용기는 별도 확인한다.
- **마신 양:** 영수증은 '주문·결제된 수량'의 근거이지 **누가 얼마나 실제 마셨는지**의 근거가 아니다. 여러 사람이 나눠 마신 경우 개인 음주량을 확정할 수 없다.

### 1-2. 내부 분류 코드

| `category` | 의미 | 자동 처리를 위한 주의 |
|---|---|---|
| `SOJU` | 일반 소주 제품군 | 증류식/희석식의 법적 상세분류는 라벨 등 검증 필요 |
| `BEER` | 맥주 제품군 | 생맥주와 병맥주는 판매 형태 필드로 구별 |
| `MAKGEOLLI` | 막걸리·탁주 제품군 | 병/PET/캔 모두 가능 |
| `CHEONGJU_YAKJU` | 청주·약주 | 세부 법적 유형 혼동 금지 |
| `WINE` | 와인 제품군 | 잔/병/카라페 구분 |
| `WHISKY_SPIRIT` | 위스키·증류주 제품군 | 위스키 샷(잔)은 병이 아님 |
| `COCKTAIL_MIXED` | 하이볼·소맥·칵테일 등 혼합 음료 | 일반적 제공 형태와 실제 용기를 동일시하지 말 것 |
| `OTHER_ALCOHOL` | 기타 주류·주류 유사 상품 | 법적 유형 확정 시 추가 검증 |
| `NON_ALCOHOL` | 확인된 무알코올·비알코올 음료 | 주류 병 수·음주량에 자동 합산하지 않음 |
| `UNKNOWN` | 판정 불가 | 검토 큐로 전송 |

**중요:** `생맥주`, `병맥주`, `캔맥주`는 별도의 법정 주종이 아니라 매장 판매·제공 방식 표시다. `하이볼`, `소맥`은 제조·판매 형태를 표현하는 메뉴명으로 분류할 수 있지만, 영수증의 메뉴명만으로 실제 들어간 소주/맥주/위스키의 양을 나눠 계산하지 않는다.

## 2. 공식 자료로 확인한 주류명 사전 (Seed Dictionary)

### 2-1. 읽는 법

- **표준명:** `canonical_name`의 초기값. 서로 다른 제품을 함부로 합치지 않는다.
- **안전 별칭:** 공백·대소문자·일반적인 표기 차이 등을 포함한다. 별칭은 **상품명 영역 전체 또는 토큰 경계 매칭**으로 처리한다.
- **주의:** 아래 표에서 **용기 정보를 비워 둔 것은 의도적**이다. 제조사에 병 제품이 존재한다고 해서 해당 영수증에서 병으로 팔렸다는 뜻이 아니다.
- **출처 코드:** `S1` ~ `S8`은 맨 아래에 있다. 제품이 존재한다는 증거이지 개별 영수증 판매 단위의 증거가 아니다.

## 3. OCR 정규화·매칭 우선순위

### 3-1. 정규화 (원문은 보존)

1. 원문 `raw_text`·이미지 페이지·행 좌표·OCR 신뢰도는 **처리 중 메모리에서만** 유지한다. 현재 구현은 요청 후 사진·원문을 파일·DB·로그에 보관하지 않는다.
2. 매칭용 복사본에서 유니코드 폭 차이, 영문 대소문자, 연속 공백, `㎖/mℓ/ml`, `ＣＣ/cc` 등을 표준화한다. **화폐 기호, 숫자 위치, 행/열 구획은 보존**한다.
3. OCR 오류 수정 후보(`O↔0`, `I↔1`, `S↔5`, 한글 자모 혼동)는 **상품명 후보 영역 안에서만** 만들고, 원본 수치·도수·수량에는 일괄 적용하지 않는다.
4. 긴 상품명·제외어를 우선 매칭한다. 예: `카스 0.0` → `카스 프레시`, `진로 토닉워터` → `진로`, `진로골드` → `진로`, `화요25` → `화요`.
5. 동일 행에 여러 후보가 있으면 자동 확정하지 말고 `MATCH_CONFLICT`로 보류한다(명백한 상품 세트는 별도 로직).
6. 하나의 영수증에 같은 제품 행이 두 번 나타날 때만 **독립된 두 상품행**으로 다룬다. 합계/영수증 복사/재출력/취소행을 중복 구매로 간주하지 않는다.

### 3-2. 경계 매칭 정책

- `includes("진로")`처럼 아무 위치에서나 검색하는 로직 **금지**.
- 상품명 영역에서 완전 일치 또는 토큰 경계 일치 우선. `진로 토닉워터`는 제품명 전체를 우선 판정.
- `테라`가 `테라스`, `소주`가 `소주잔`, `카스`가 주소·상호에서 발견됐다고 상품이 되지 않음.
- 별칭이 두 브랜드에 충돌하면 **짧은 별칭 제거** 또는 운영자 검증 후 채택.
- 신뢰되지 않는 OCR 교정 예: `켈리`→`캘리`를 자동 등록하지 않는다. 실측 오류 데이터가 있을 때만 별칭을 추가한다.

### 3-3. 문서와 영역 판별 순서

```text
원본 사진/스캔
  └─ OCR 문자 + 줄·단어 좌표 + 표/열 정보
       ├─ 결제 정보(상호, 승인번호, 카드번호, 총액, 부가세 등)
       ├─ 상품행 영역(품목명 / 수량 / 단가 / 금액)
       └─ 기타(광고·주의문·환불정보)
             ↓
   [상품행 있음?]
       ├─ 아니오 → PAYMENT_ONLY / item_count: unknown / 수량 추정 금지
       └─ 예 → 상품명 후보 추출
                   ↓
              제외어·제품 확장형 매칭
                   ↓
              주종 → 용량 → 용기 → 명시 수량 각각 파싱
                   ↓
              근거 검증 → PARSED_CANDIDATE 또는 REVIEW_REQUIRED
```

`PAYMENT_ONLY` 영수증도 **결제금액·상호·결제일시** 등 별도 데이터는 저장할 수 있지만, 주류 판매 병 수는 null이다.

## 4. 단위·숫자 해석 사전

### 4-1. 숫자 주변 표현의 의미

| OCR 표현 | 의미 | 잘못된 해석 방지 |
|---|---|---|
| `500cc`, `500 CC`, `500ml`, `500mL`, `500㎖` | **용량 500mL** | `quantity=500`, `bottle_count=500` 금지 |
| `1L`, `1리터` | **용량 1,000mL** | `quantity=1`로 해석 금지 |
| `1.5L` | **용량 1,500mL** | 1.5병 금지 |
| `17도`, `25%`, `ABV 4.5%` | 도수 | 수량 금지 |
| `1병`, `병 1개`, `2병`, `3BOTTLES` | 명시된 병 수 | 해당 **상품행에 연결될 때만** 수량·병 수 확정 |
| `2캔`, `캔 2개` | 명시된 캔 수 | 병 수는 아님 |
| `2잔`, `잔 2`, `GLASS x 2` | 명시된 잔 수 | 병 수는 아님 |
| `피처 1개`, `피쳐1` | 피처 1개 | 피처 크기 임의 환산 금지 |
| `6캔입`, `6PACK`, `6개입` | 상품 포장 구성 | **주문 수량 6개**가 아님; 판매 수량과 별도 관리 |
| 상품명 옆 `x2`, `×2`, `수량 2`, 수량 열의 `2` | 판매 수량 2 | 표 구조·상품행 연결이 확인될 때만 확정 |
| `5,000`, `12,000` | 단가/금액 **후보** | 금액을 수량으로 간주 금지 |
| `승인번호`, `사업자번호`, `카드번호`, `테이블 12` | 문서 식별 정보 | 상품 수량 금지 |
| `1+1`, `2+1` | 판촉 표기 | 구매/증정 개수 자동 추측 금지 |

### 4-2. 안전한 단위 인식용 정규식 예시 (후보 추출용)

> 실제 구현에서는 정규식을 무조건 원문 전체에 적용하지 말고 **상품명 필드 / 수량 열 / 단위 표현**의 영역 정보와 함께 사용한다. 정규식 자체가 문맥을 판정해 주지는 않는다.

```text
숫자 전체 토큰 + 명시 단위를 먼저 추출하고, 숫자 전체를 검증한다.
수량: 쉼표 형식이 올바른 양수 정수 1~1000. 소수·음수·부호·잘못된 쉼표는 거절한다.
용량: mL/cc와 L을 구별하고 L은 정확히 1000배 한다. 현재 정수 mL만 지원한다.
단위: bottle/bottles, can/cans, glass/glasses도 지원한다.
1.5병 → 수량 미상(5병으로 복구 금지)
-2병 → 수량 미상(2병으로 복구 금지)
12,500ml → 용량 12,500mL(500mL로 일부 매칭 금지)
1.50ml → 현재 정수 mL 지원 밖이므로 검토(50mL로 복구 금지)
```

실행 가능한 패턴·전체 토큰 검증은 [product.py](../receipt_ocr/product.py)에 두고
단위 테스트로 검증한다. 문서에 별도 정규식을 복제해 두 구현이 갈라지게 하지 않는다.

- `cc`와 `mL`는 영수증에서 **용량 표기**로 다루며, `1cc = 1mL`를 적용한다.
- `mL`를 `L`로 환산하는 것은 수치 정규화일 뿐 **병/잔 환산이 아니다**.
- 수량은 행의 `quantity` 컬럼이나 `2병` 등 명시적인 상품 수량 근거로만 읽는다.
- 용량·도수·가격 숫자가 여러 개 등장하면 **우선 보류**한다. `화요25 375ml 2`에서 25는 제품/도수, 375는 용량, 마지막 2는 수량 열인지 확인되어야만 수량이다.
- **수량이 표시되지 않았다고 `0`을 넣지 않는다.** `0`은 실제 0, `null`은 알 수 없음을 뜻한다.

### 4-3. 병 수 집계 조건

병 수 합산은 다음 조건을 모두 충족할 때만 허용한다.

```text
is_alcohol == true
AND is_item_row == true
AND is_cancelled_or_returned == false
AND container == BOTTLE
AND quantity is explicitly confirmed
AND quantity > 0
```

- `container = BOTTLE` 근거: `소주 2병`, `병맥주 수량 2`, 별도의 품목 열에 `병` 표기와 명시적 수량 등.
- `container = UNKNOWN`: **병 수 null**. 소주 일반 판매 관행이나 대표 용량을 근거로 병을 확정하지 않는다.
- `container = GLASS/PITCHER/CAN` 또는 `serving_type = DRAFT`: 병으로 산정하지 않는다. 판매 수량과 용기로 구별한다. 현재 API는 별도 잔/캔 집계 필드를 반환하지 않는다.
- `PACK`: 묶음 내 병 수·판매 수량이 모두 명시되고 관계가 모호하지 않을 때만 포장구성 기반 추가 집계를 검토한다. 초기 버전은 `REVIEW_REQUIRED` 권장.
- 총계 집계에서 null을 0으로 바꿔 `총 0병`이라고 표시하면 안 된다. 예: **`확인된 병 2개 + 병 여부 불명 3항목`**처럼 구분 표시한다.

## 5. 정산어택 확인용 응답 스키마

현재 구현은 사진·원문을 저장하지 않는다. 아래는 합성 상품행의 **후보 응답**이며 실제 매출이 아니다.
`생맥주 500cc`의 수량 열에 2, 단가 4,500, 금액 9,000이 명시된 경우다.

```json
{
  "schemaVersion": 2,
  "total": 9000,
  "drinks": [{
    "name": "생맥주 (브랜드 미상)",
    "category": "BEER",
    "unit": "UNKNOWN",
    "servingType": "DRAFT",
    "volumeMl": 500,
    "quantity": 2,
    "bottleCount": 0,
    "unitPrice": 4500,
    "lineAmount": 9000,
    "confidence": 0.99,
    "reviewReasons": ["UNKNOWN_CONTAINER"]
  }],
  "warnings": ["ITEMS_NEED_REVIEW"],
  "requiresConfirmation": true
}
```

생맥주라고 잔 2개로 추측하지 않는다. `unit`은 용기, `servingType`은 제공 방식이다.
`bottleCount=0`은 이 생맥 항목이 병 집계 대상이 아니라는 뜻이며 영수증 전체 병 수를 보장하지 않는다.
모든 후보는 총무 확인 후 기존 차수 입력으로 반영한다. Python은 DB 저장·정산·송금을 수행하지 않는다.

| 필드 | 의미 |
|---|---|
| `name` | 사전 표시명. 카스·참이슬 단독은 세부형 미상 |
| `category` | 내부 주종 후보. 법정 식품유형 확정값이 아님 |
| `unit` | BOTTLE/CAN/GLASS/PITCHER/PACK/UNKNOWN |
| `servingType` | DRAFT/UNKNOWN; 용기와 별개 |
| `volumeMl` | 명시된 정수 mL 또는 null |
| `quantity` | 명시된 양수 정수 판매 수량 또는 null |
| `bottleCount` | 병+수량 근거가 있는 후보 개수. 미상·충돌은 null |
| `unitPrice`, `lineAmount` | 헤더에서 읽은 정수 원 또는 null |
| `confidence` | 품목행의 최소 OCR 점수. 정확할 확률을 보증하지 않음 |
| `reviewReasons` | 검토 사유. 경고가 없어도 자동 확정하지 않음 |

원문·카드번호·승인번호·좌표·증빙 이미지 참조는 응답/파일/DB/로그에 보관하지 않는다.
검수 자료 수집·학습·감사 로그를 도입할 때는 보관 기간·마스킹·삭제 정책을 별도로 정한다.

### 5-1. 검토 사유 코드 (권장)

| 코드 | 트리거 |
|---|---|
| `NO_ITEM_LINES` | 결제전표에 상품명/품목행이 없음 |
| `MISSING_QUANTITY` | 품목은 있으나 수량 없음 |
| `UNKNOWN_CONTAINER` | 병·캔·잔 등의 근거 없음 |
| `AMBIGUOUS_BRAND` | 일반 단어와 브랜드 충돌 |
| `UNKNOWN_PRODUCT` | 사전에 없는 제품 |
| `MATCH_CONFLICT` | 복수 제품 매칭 충돌 |
| `POSSIBLE_NON_ALCOHOL` | 무알코올/제로 표기 일부만 인식되어 제품 미확정 |
| `COLUMN_AMBIGUITY` | 수량·단가·금액 열의 구분 불명확 |
| `LOW_OCR_CONFIDENCE` | OCR 문자열 또는 숫자 인식 품질 불충분 |

| `PERSONAL_CONSUMPTION_UNKNOWN` | 구매 내역은 확인되나 개인 섭취량 계산 불가 |

## 7. 서비스 구현 시 권장 처리 정책

### 7-1. 단계별 로직

1. **OCR:** 문자/수치/위치 추출. 원본 이미지와 행 좌표는 요청 처리 중 메모리에서만 사용한다.
2. **문서·레이아웃 분류:** 상품행 있는 상세영수증인지, 결제정보만 있는 전표인지, 판정 불가인지 구분.
3. **사전 매칭:** 제외어 → 긴 제품명 → 정확한 브랜드 별칭 → 일반 주종 키워드 → 미상 순서.
4. **수량·단위 별도 파싱:** 상품명·용량·도수·판매 수량·단가·금액을 **각기 다른 필드**로 저장.
5. **안전 검증:** 상품행-수량 근거·용기 근거·충돌 여부를 확인.
6. **후보 반환:** 증거 충분 시 `PARSED_CANDIDATE`, 불충분하면 `REVIEW_REQUIRED`로 표시한다. **두 경우 모두 `requiresConfirmation = true`이며 총무 확인 후에만 입력에 반영한다.**
7. **사전 개선:** 운영자가 확인한 실제 영수증의 오인식 패턴만 버전 관리해 추가. 현재 구현은 입력 사진·원문과 정정 감사 로그를 저장하지 않는다. 검수 자료 수집은 별도 동의·마스킹·보관 기간·삭제 정책을 정한 뒤 도입한다. 영구 보존을 기본값으로 두지 않는다.

### 7-2. OCR 신뢰도 정책

- OCR 엔진이 제공하는 숫자형 confidence는 **인식 품질의 단서**일 뿐, 주류 브랜드/용기/수량 추론의 진실값이 아니다.
- OCR 신뢰도가 높아도 정보 자체가 빠져 있으면 **자동 채우지 않는다**.
- 운영에서 임계값을 둔다면 샘플 영수증 검증으로 정한다. **업계 공통 보장 정확도 또는 임의의 고정 신뢰도(예: 95%)를 공식 기준처럼 사용하지 않는다.**
- 사용자 확인 UI에서는 기기에 있는 원본 사진과 `감지: 맥주·500mL` / `수량: 확인 필요`를 함께 보여 주는 방향을 검토한다. 현재 Python은 OCR 원문을 반환하지 않으며 앱 UI는 후속이다.

### 7-3. 학습/사전 업데이트용 레코드 예시

```yaml
rule_id: NEW_RECEIPT_ALIAS_001
canonical_name: "참이슬 Fresh"
observed_ocr_text: "참이슬후레쉬"
match_scope: "ITEM_NAME_ONLY"
category: "SOJU"
source_type: "MANUALLY_VERIFIED_RECEIPT"
verified_by: "reviewer"
verified_at: "YYYY-MM-DD"
notes: "별도 승인된 검수 자료에서 실제 사례 축적 시 등록; 미확인 오타 자동 생성 금지"
```

**운영 팁:** 이후 사전이 커지면 Markdown을 유지관리용 문서로 두고, 동일한 ID를 가진 정규화 데이터(`YAML/JSON/DB`)로 변환·검증하는 빌드 단계를 추가한다. **Markdown 단독으로 정확한 파서나 학습 모델이 완성되는 것은 아니다.**

## 정산어택 실행 데이터와 계약의 차이

- 이 문서는 정책·출처·검수 자료이고 실행 사전은 별도 Markdown 표다.
- 원문·행 좌표·증빙 참조는 외부 JSON에 포함하지 않는다. 정책 문서의 개념 명칭은 snake_case, 실제 응답 필드는 camelCase이며 §5와 내부 API 문서가 계약이다.
- 내부 API v2는 기존 `unit`을 용기로 사용하고 `servingType`, `volumeMl`, `bottleCount`를 별도로 반환한다.
- 미상은 null 또는 UNKNOWN으로 둔다. 모든 결과는 사람이 확인한다. Python은 정산을 수행하지 않는다.
- 법정 주종은 확정하지 않는다. 내부 분류 코드는 정산 입력 후보를 표시하기 위한 분류다.
- 총액은 합계·총액·총금액·결제금액·총결제금액·받을금액 라벨의 정수 원만 읽는다.
  공급가액·부가세·받은돈·거스름돈을 합산해 총액을 만들지 않고, 서로 다른 총액 후보는 null로 보류한다.
