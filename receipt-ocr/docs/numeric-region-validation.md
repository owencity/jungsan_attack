# 작은 수량 숫자 재인식 검증 · 2026-10-15

## 해결한 문제

기준 `335cd93`은 공개 영수증 R의 작은 수량 1·할인 0을 놓쳐 quantity/lineAmount를 null로 반환했다.
[이전 기록](public-sample-validation.md)의 실패와 정답은 그대로 유지한다.
수량을 기본 1로 채우는 대신 실제 숫자 칸의 픽셀을 같은 모델로 다시 읽었다.
원본 출처·SHA-256·정답 9개 필드는 이전 기록과 `examples/manifest.public-web.example.json` 그대로다.

## 구현과 제한

- 전체 사진 OCR은 한 번 실행하고, 명시 헤더와 기존 금액 토큰 좌표로 빈 수량·할인 영역만 찾는다.
- 이미 읽은 숫자·음수·소수·낮은 점수 토큰도 덮어쓰지 않는다. 겹치는 상품명·넓은 병합 헤더는 건너뛴다.
- 두 숫자 라벨이 붙은 상자는 글자 위치 비율로 나눈다. 비례 글꼴·원근·기울기는 이 위치 추정에 영향을 준다.
- 금액 토큰의 숫자 행 높이로 영역을 제한해 가로 구분선을 피한다. 회색조·대비 보정 후 4배 확대하고 여백 16/32px로 재호출한다.
- 원본 영역이 빈/균일하거나 잉크가 경계에서 잘렸거나 가로선뿐이면 호출하지 않는다. 좌우를 자르지 않아 부호·소수점을 보존한다.
- 0.90 이상의 전체 정수만 후보로 인정한다. 고신뢰도 판독끼리 다르거나 음수/소수/복수 텍스트면 거절한다.
- 다른 여백에서 미검출한 것은 고신뢰도 판독의 반증으로 보지 않는다. 같은 모델 두 번은 독립 모델 합의가 아니다.
- 최대 8칸·16회 추가 추론. 추가 모델·패키지·외부 API 없이 기존 CPU 모델을 재사용한다. 기동 모델 수는 늘리지 않는다.
- 할인 칸이 누락돼도 좌표로 확인된 수량·금액은 보존한다. 누락 할인이나 단가를 계산해 만들지 않고 ITEM_VALUES_MISSING을 유지한다.
- 채택된 품목에 NUMERIC_REGION_RECOGNIZED를 붙이고 항상 총무 확인을 요구한다. 원문·카드·사진을 응답/로그/DB에 추가하지 않는다.

공식 `predict`의 이미지 배열 입력을 같은 인스턴스에서 재사용한다.
[PaddleOCR 공식 입력·옵션 문서](https://www.paddleocr.ai/main/en/version3.x/pipeline_usage/OCR.html)를 대조했다.

## 실제 모델 점검

R 원본은 이제 카스/DRAFT/300mL·수량 1·항목 2,000원·총액 18,500원을 읽는다.
단가 열이 없어 unitPrice=null, 용기 표기가 없어 unit=UNKNOWN, 생맥이므로 bottleCount=0이다.
정답을 인식 결과에 맞춰 낮추지 않았다.

원본 외 대조 이미지는 같은 사진에서 메모리 안에서 만들었으며 새 독립 영수증으로 세지 않는다.
수량 칸을 지운 경우 quantity=null, 음수로 바꾼 경우도 양수 수량이 되지 않았다.
| 같은 사진의 검사 종류 | quantity | lineAmount | total | 처리시간(초) |
|---|---|---|---|---|
| 원본 | 1 | 2000 | 18500 | 16.066 |
| 수량 칸 지움 | null | 2000 | 18500 | 13.838 |
| 수량을 -2로 변경 | null | null | 18500 | 14.731 |
| JPEG 품질 50으로 재압축 | 1 | 2000 | 18500 | 14.020 |

원본 evaluator: samples=1, failedSamples=0, totalExactRate=1.0, allDrinkFieldsExactRate=1.0,
warningSampleCount=1, meanSecondsExcludingStartup=13.826초.
이전에 실패했던 같은 **1장 개발 사례의 9필드 일치가 0/1 → 1/1**이 된 것이며 일반 정확도 100%가 아니다.
재압축본은 할인 0이 끝내 누락돼 ITEM_VALUES_MISSING을 유지하지만 좌표로 확인한 수량·항목 금액은 보존했다.
빈 수량에 1을 채우거나 음수의 일부를 양수로 복구하지 않았다. 모든 결과는 requiresConfirmation=true다.

이전 공개 이미지 J/N/R도 최종 코드로 다시 실행했다. J는 total=59000·가려진 주류는 빈 후보,
N은 MULTIPLE_RECEIPTS_SUSPECTED·빈 후보를 유지했고 R은 수량 1·금액 2000·총액 18500이다.
각 단건 처리시간은 5.104초·4.789초·12.985초였다. 위 대조 검사와 별도 실행이며 운영 성능 비교가 아니다.

## 자동 회귀와 자체 점검

- 기존 72개 + 숫자 영역 회귀 20개, **92 tests / OK (0.428초)**. 테스트 삭제·비활성화 없음.
- 빈/균일/잘린 칸·가로선·헤더 없음/상충/낮은 점수·누락 금액·부호/소수/범위·판독 이견·기존 숫자 보호·8칸 예산을 검사했다.
- 부분 수량/금액 보존·상충하는 명시 수량·중복 수량 근거·0원 거절·이미지/토큰 불변·추론 실패 전파·재귀 없음도 검사했다.
- `:server:compileKotlin`: BUILD SUCCESSFUL in 3s, 6 tasks up-to-date. Java/Kotlin/Core/DB/운영은 변경하지 않았다.
- 새 의존성 없음. 기존 서비스 키·업로드 크기·픽셀·단일 추론 슬롯 정책 유지. 예외는 기존 OCR_UNAVAILABLE 경로로 전파한다.

## 평가 해석

오류를 발견하고 수정한 한 사진과 그 파생 대조 이미지다. 독립 표본 정확도·병 수 전체 정확도·운영 채택 근거가 아니다.
여러 매장 직접 촬영, 비례 글꼴·기울기·극저화질·다중 줄·넓은 병합 헤더·사진당 많은 누락 칸은 여전히 검증 범위가 부족하다.
CPU 추가 추론으로 지연이 늘 수 있으며 이 PC의 단건 시간을 OCI ARM/운영 처리량으로 일반화하지 않는다.
병 용기를 브랜드에서 추측하거나 사진 인식만으로 저장/정산하는 기능은 추가하지 않았다.
