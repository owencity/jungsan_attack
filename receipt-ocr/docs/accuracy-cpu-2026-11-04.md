# 웹 주류 영수증 파서 개선과 CPU 비교 · 2026-11-04

사용자는 보유 사진이 없어 웹에서 확보한 원본으로 이어간다. 이번에는 새 수집 장수를 늘리지 않고,
기존 인쇄 주류 13개(일반 12 + 중간계산서 1개)의 실패 원인을 확인하고 Python 추출을 수정한다.
사진·정답·모델 가중치를 바꾸지 않고, 다른 사진을 사용한 11월 3일/이전 캠페인의 시간을 개선 비율로 비교하지 않는다.

## 평가 범위

- 수정 전 코드: `4e33613454df2afd9407b1bc1fac3622af572683`.
- 정답: [고정 manifest](../examples/manifest.web-pubs.example.json)의 총액·종류·수량·명시 단가 또는 null·항목 금액.
- 이름·용량·용기·병 수를 포함한 모든 필드 정확도가 아니다. 사진을 본 뒤 수정했으므로 개발 대조군이다.
- 같은 매장/원본 파생본과 개발 사진을 새 매장 평가에 섞지 않는다. 일반 정확도나 출시 가능 비율을 뜻하지 않는다.
- 원본·OCR 원문은 기존 ignore 폴더에만 있고 Git에는 구조화 결과·해시·집계만 보존한다.

## 원인을 확인하고 바꾼 것

1. 총액 표현에 `총계`, `총주문액`을 추가한다. 콜론은 최대 2개까지 허용하고 금액의 점·부호·잘못된 쉼표를 고치지 않는다.
2. 새 합계 표현과 할인 문맥이 충돌하면 값을 비운다. 할인액을 빼서 결제 총액을 만들지 않는다.
3. `상품`, `가격` 헤더를 처리하고, 단일 상품명 다음 줄에 6자리 코드·완전한 숫자 열이 가까이 정렬된 경우만 연결한다.
4. 실제 인쇄 표기 `장수막걸리`, `참이슬빨간것`만 정확한 사전 항목으로 추가한다. 세부형·용기·병 수는 추정하지 않는다.
5. 한국어 모델·CPU 2스레드·가속 비활성을 유지하고, 검출 긴 변의 상한 1280을 기본값으로 대조한다. 명시적 None은 이전 설정이다.

`판매금액`은 총액 표현으로 추가하지 않았다. K399에서는 세전 금액이어서 기존 합계와 충돌했다.
소주를 다른 글자로 읽었거나 합계 라벨을 잃은 사례는 유사 이름·숫자 추측으로 성공 처리하지 않는다.

이 비교에는 새 추론이나 속도 측정이 없고, 전체 네이티브 재실행과 구분한다.

새로 전체 선택 조건을 만족한 사진은 C49059·C49470·C47325이고 기존 K345는 유지됐다.
HWARO·C48674는 총액만 개선됐다. 필드별 전체 정답·비알코올 일반 정밀도로 확대하지 않는다.

## CPU 비교와 최종 검증

아래 측정은 동일 원본·고정 정답·같은 소스의 순차 실행으로 기록한다.
기동 시간과 첫 요청·반복 요청은 구분하고, 실패·시간 초과를 분모에서 빼지 않는다.
기존 실행은 CPU 2스레드·MKL-DNN 비활성·검출 상한 추가 없음이다. 설치된 PaddleX 설정의 인식 배치는 6이며
문서의 최신 기본값을 현재 환경의 실행값으로 가정하지 않는다.

[측정 기록](cpu-comparison-results.json)에 옵션·소스/정답 해시·원본별 시간·성공 조건·오류를 보존했다.
Python 3.12.6, Windows 11, PaddleOCR 3.7.0 / PaddleX 3.7.2 / PaddlePaddle 3.3.1의 로컬 CPU 실행이다.

첫 선별은 K345·K235·C48674·C49623에서 설정별 1회다. CPU 4스레드의 중앙값은 15.552초로
기존 13.6245초보다 느렸고, MKL-DNN True는 추론 4건 모두 NotImplementedError여서 채택하지 않았다.
검출1280은 해당 선별에서 11.2995초였지만 실제 크기가 바뀌지 않은 대조 사진의 시간도 변동해 그 비율을 개선율로 쓰지 않는다.

큰 사진 R/T와 C49623·K345를 같은 순서로 2회 반복했다. R/T 원본은 디코딩 후 긴 변2400이며
이 둘만 주류 9필드 정답이다. 나머지는 부분 정답이라 4개 전체를 9필드 정확도로 표현하지 않는다.

| 4원본 × 2회 | 기존 설정 | 검출1280 |
|---|---:|---:|
| 처리 중앙값 | 16.7695초 | 13.7315초 |
| 두 번째 반복 중앙값 | 17.1995초 | 14.603초 |
| 최대 | 19.839초 | 17.421초 |
| 모델 기동(통계 별도) | 5.196초 | 5.416초 |
| 전체 선택 조건 일치 | 6/8 | 6/8 |
| 실행 오류 | 0/8 | 0/8 |

R/T의 주류 9필드는 두 설정·두 반복에서 모두 유지됐다. K345는 토큰 해시도 같고 C49623은 양쪽에서 실패했다.
이 제한된 비교의 중앙값 차이는 약18.1%이며 일반 지연 보장·운영 ARM 결과가 아니다. 검출 크기가 바뀌지 않은
K345의 시간도 15.467/16.382→15.606/15.093초로 변동했다. 초기의 별도 반복 실행 하나는 비교 범위 조정으로
중단·제외했음을 기록하며, 알고리즘 실행 실패나 성공으로 바꾸지 않는다.

## 최종 실제 재실행

[최종 결과](native-regression-results.json)는 코드 `5fa7c8d4dc93305307561ac3c27f5d959838e4a7`의 기본 검출1280으로,
웹 주류13개 뒤에 기존 혼합16개를 한 엔진에서 순차 처리했다. 원본·정답 manifest 두 개는 변경하지 않았다.

- 29개/28묶음 실제 추론 실행 오류 0개, 전체 선택 조건 일치12개·불일치17개. CLI 종료코드는 불일치를 보존한1이다.
- 웹 주류13개는 총액7개·주류 부분 필드5개·전체 선택 조건4개로 토큰 재사용 대조와 같다. 처리 중앙값11.532초다.
- 기존 혼합16개는 전체 선택 조건8/16을 유지했고, 이전에 맞던 개별 검사 조건이 실패로 바뀐 경우0개다.
- R/T의 전체 주류9필드도 다시 유지됐다. 메뉴판M1의 주류 후보2개 오인식 등 기존 실패는 해결했다고 세지 않는다.
- 전체29개 처리 중앙값11.147초·최대28.342초이며, 서로 다른 양식·부분 정답·부정 대조를 섞은 일반 정확도나 속도가 아니다.
- 자동 테스트137개/OK(0.604초). 테스트 삭제·비활성화 없음. 단위/API 테스트 통과와 실제 영수증17개 불일치는 별개다.
- 서버 컴파일은 BUILD SUCCESSFUL in14s, 6tasks up-to-date다. Java/Kotlin 변경·새 엔드포인트·스키마 변경은 없다.
- 자체 점검과 별도 에이전트의 할인/행 연결 검토를 수행했다. 지적된 할인 미인식·총계 보호 누락을 수정하고14개 합성 조건으로 다시 확인했다.

기존 CPU2·가속False를 유지하고 검출 상한1280을 프로토타입 기본값으로 채택한다. 큰 사진의 제한된 비교와
29개 개발 회귀 근거이며 새 매장 일반화·운영 ARM 성능을 보장하지 않는다.

재실행은 기존 manifest를 각각 사용한다. 모델 캐시는 기존 `.models/paddlex`와 `.models/huggingface`를 지정한다.

```powershell
.venv\Scripts\python -m unittest discover -s tests
.venv\Scripts\python tools\validate_capture_campaign.py .samples/web-2026-11-03 --manifest examples/manifest.web-pubs.example.json --output reports/web-after.json
.venv\Scripts\python tools\validate_capture_campaign.py .samples/public-web --manifest examples/manifest.capture-campaign.example.json --output reports/old-after.json
```

각 CLI는 알려진 불일치가 남아 종료코드1로 끝난다. 이를 실행 오류나 전체 성공으로 바꾸지 않는다.

## 남은 한계와 다음 작업

- 웹 주류 명세 원본 30~50개 목표는 미달이다. 지금 13개는 개선에 사용했으므로 새 매장/촬영자 자료를 별도로 확보한다.
- HWARO의 다중 줄 상품·명시 `개` 수량, 원근/행 병합, OCR 자체의 글자·총액 라벨 누락은 남는다.
- API의 `schemaVersion=2`, `null/UNKNOWN`, `requiresConfirmation=true`와 추측 금지 정책을 유지한다.
- 실제 운영 ARM·동시 요청·업로드 전송·휴대폰 촬영/앱 체감 시간은 이 로컬 비교에 포함되지 않는다.
- Spring 연결은 별도 [초안 PR #38](https://github.com/owencity/jungsan_attack/pull/38)에 보존돼 있고 실제 Python/운영 연결은 미검증이다.
  이번 변경은 Python 개선이며 Spring 활성화·앱 구현·운영 배포 완료가 아니다.

문서 기준 main은 `8d27496270e6c8adcb78b4580d68c150f9c3cce6`이다.
열린 FC005·009·010·011·014·015·020·021·026과 후속 문서 PR의 FC027~033을 확인했다.
후속 FC029의 총무 확인 방향과 같이 OCR은 입력 후보만 반환하고 자동 저장·정산하지 않는다.
알림·계좌·인증·정산·앱 실기기 후속은 이 작업으로 닫지 않는다. 자체 점검·별도 에이전트 점검은 외부 리뷰와 구분한다.
